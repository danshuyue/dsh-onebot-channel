# dsh-onebot-channel

> 把 QQ 私聊与群聊接进 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 会话。
> 基于 [OneBot 11](https://github.com/botuniverse/onebot-11) 协议：入站走 WebSocket 事件推送，出站用 `qq_send` 工具回话。

[![npm](https://img.shields.io/npm/v/dsh-onebot-channel.svg)](https://www.npmjs.com/package/dsh-onebot-channel)
[![license](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![node](https://img.shields.io/badge/node-%3E%3D22.19-green.svg)](https://nodejs.org)

让「在 QQ 里发消息」变成 DSH 会话里的一个回合，agent 直接回话。

```
QQ 客户端
   ↓  OneBot 11 协议端（SnowLuma / LLOneBot 等）
   ↓  本插件：WS 事件推送为主，HTTP 轮询兜底
路由表：这个 QQ 号 / 群绑的是哪个会话
   ↓  agent.followup()  唤醒会话
会话跑一个回合（agent 看到「（QQ 私聊·用户本人 QQ …）…」）
   ↓  agent 调 qq_send 工具
OneBot send_private_msg / send_group_msg
   ↓  按换行切条（她自己写几行就几条），带随机延时
回到 QQ
```

## 分支说明：`feat/qq-focus-router`（0.18.0 → 0.18.3）

> 本文档由该分支的开发者补写，**给上游作者审核用**。若上游接受，这个分支可以直接转 `main`。

### 这个分支解决什么问题

原插件是**严格会话绑定**：`routes.private[QQ号] = { sessionId }` 写死一个会话，
你从 QQ 发的话永远只进那一个。

于是多工作区并行时有三个说不通的地方：

1. **看不见别处**。DSH 里同时开着好几个工作区的会话，
   想知道「那边干到哪了」只能回桌面端点开看。QQ 那头完全没有入口。
2. **回不去**。别的会话能通过 `sendapi`（`POST 127.0.0.1:39273/send`）
   单向推消息给你，但你回不过去 —— 只能回到绑定的那个会话。
3. **分不清**。几个会话同时往同一个 QQ 推，「这句是哪边说的」没有标记。

另外还有一个与路由无关、但同样是「白烧钱」的问题：
**12 个工具的 schema 每轮都进上下文**，合计 10272 字符，
其中表情包 / 语音 / 戳一戳这些**常规情况根本不用**。

### 变更特点

#### 一、跨工作区进度：只读、零 token、不唤醒会话

新增 `lib/progress.js`，读 DSH 自己的投影缓存 + 工作区注册表，聚合出
「哪个会话在跑、第几轮、待办剩什么、上下文压力多少」。

数据源（实测本机）：

| 来源 | 内容 |
|---|---|
| `~/.dsh/storages/session_projcache/sessions/<id>.json` | **主来源**。每会话一个文件，`sessionStats` / `title` / `todos` / `goal` / `tokenUsage` / `contextPressure` / `permissions` |
| `~/.dsh/storages/session_projcache.json` | 旧汇总布局，**已不再写**（本机停在两个月前），只作兜底 |
| `~/.dsh/storages/workspace.json` | 工作区 → 会话的映射，跨工作区枚举靠它 |

**三条铁律**（违反任何一条都会出真事故）：

- **绝不 `agents.resume()`**。resume 会真的建出 agent，可能抢走 GUI 已打开会话的写句柄。
  读进度只用 `agents.get()`（只查活着的）+ 读盘。
- **绝不写盘**。投影缓存是 DSH 的。
- **读失败一律降级成「没有数据」**，绝不抛 —— 不能让一个坏 JSON 拖垮投递链路。

性能：冷启动 82ms，命中缓存 0ms（只读最近 200 个投影文件，`PROGRESS_SCAN_LIMIT`）。

#### 二、QQ 侧命令层：不进会话、不产生回合、不烧 token

新增 `lib/commands.js`，在插件内部消费，回复直接走 `sendToQQ`（→ `callOneBot` 唯一出口）。

| 命令 | 作用 |
|---|---|
| `/进度`（`/p` `/status`） | 列正在跑 + 最近活跃的会话，按工作区分组，带编号 |
| `/看 <n>` | 看一个会话的详情：待办、token、上下文压力、权限 |
| `/去 <n>` | 把接下来的话投给那个会话（10 分钟内有效） |
| `/回` | 回到默认绑定 |
| `/在哪` | 我现在在跟谁说话、下一条消息会进哪、依据是什么 |
| `/帮助` | 命令列表 |

设计红线：

- **绝不吞用户的话**。只认「整条消息以 `/` 开头 + 命令名精确命中」，
  不认识的 `/xxx` 原样投给会话。
- **编号不做持久承诺**。编号表 10 分钟 TTL，过期就要求重发 `/进度`，绝不按新列表解释旧编号。
  幽灵编号比「请重发」糟糕得多 —— 它会静默把话投给错误的会话。
- 命令执行完**仍要推进游标**，否则轮询会把同一条命令反复重投。

#### 三、四级路由：引用 > 焦点 > 默认 > 不投

这是整个分支最核心的设计决定。新增 `lib/focus.js`。

**明确否决了两个看起来更省事的方案**：

| 方案 | 为什么不要 |
|---|---|
| **总台会话**（一个会话代理全部工作区） | 它不是那个会话，只能转述，永远慢一层；每句话先烧总台 token；上下文几十条就漂移；真要干活还得转发，等于绕远 |
| **最近会话兜底**（谁刚说话就回给谁） | 插件里 `sessionCandidates()` 本来就是这条路，源码注释写着「消息凭空进了别的对话」。48 个工作区并行时，「最近」是掷硬币。**更糟的是误判时没有任何提示** —— 消息静默进错会话，那头的模型还认真干活 |

所以只认三个**显式**信号，按优先级：

1. **引用（长按回复）某条带标签的消息** → 回给发出那条消息的会话。
   最明确的意图表达，零推断。靠 `message_id → sessionId` 索引实现。
2. **`/去 <编号>` 设过的焦点** → 带 TTL，闲置超时自动回默认（防跨天串台）。
3. **`routes` 里的默认绑定** → 与改动前逐字一致。

三个都没有 → **返回空，让调用方明说「发 `/进度` 挑一个」**。
`focus-sim` 里有一条专门钉死这个：变异成「兜底到最近会话」必须变红。

#### 四、出站会话标签：`〔工作区·会话〕`

多会话并行时，让人在 QQ 那头分清「这句是哪边说的」。
**只在「当前会话 ≠ 该 QQ 号的默认绑定会话」时加**，日常单会话聊天一个字都不会多。
标签来源从投影缓存反查，查不到就不加，绝不编名字。

> ⚠️ 这个功能初版方向搞反了（加在入站、给用户自己的话加前缀），
> 线上实测才发现。见下方「这个分支踩过的坑」。

#### 五、工具箱分档：按功能组启停，省掉一半 schema

不常用的工具**根本不注册**（schema 不生成），而不是注册后用 `tools.restrict()` 屏蔽
（`restrict()` 需要 `agent.ctx`，全局调用会抛；冷启动的 agent 是插件自己 resume 出来的，时序难保证）。

| 档位 | 包含 | 默认 | schema 字符 |
|---|---|---|---|
| **发送消息** | `qq_send` | ✅ 恒开 | 2880（不可关） |
| **沉默权** | `qq_pass` `qq_skip` `qq_wait` `qq_close` | ✅ 开 | 2588 |
| **表情包** | `qq_emoji_search` `qq_face_pick` `qq_face_preview` `qq_face_rename` `qq_collect_face` | ⬜ 关 | 3776 |
| **语音识别** | `qq_voice` | ⬜ 关 | 542 |
| **发送语音** | `qq_send` 的 `voice` 参数 | ⬜ 关 | 231 |
| **戳一戳** | `qq_poke` | ⬜ 关 | 486 |

实测：**全开 10272 字符 → 默认 4875 字符，省 5397（52.6%）**。

两个必须注意的耦合：

- **关掉的档不能在别处留下工具名**。`qq_send` 的 description 里有 5 处提到
  `qq_face_pick` / `qq_emoji_search` / `qq_skip` 等。留下任何一处，
  模型就会去调一个没注册的工具 → 拿到 `UNKNOWN_TOOL` → 换个写法再试，
  **正好是「关开关反而更烧 token」**。所以描述按 features 动态拼接。
- **失败路径上的工具名最隐蔽**。`face-resolve.js` / `preview.js` 的错误信息里
  原本也点名了工具，那些地方平时测试跑不到，但模型调错名时会读到。
  已改成不含工具名的通用说法（最小耦合，不给这两个模块穿 features 参数）。

代价：**改完要重启 DSH 才生效**（注册发生在 `apply` 里），设置页已明写。

### 这个分支踩过的坑（给后续维护者）

「引用即路由」上线前经过三轮线上实测，**每轮都发现一个 bug**，
而且三个 bug 是**同一个模式的不同表现**：把「空 / 缺省 / 没给」当成「有值」，
并且失败时不报错、日志也看不出来。

| 版本 | 症状 | 根因 |
|---|---|---|
| 0.18.1 | 索引根本没记 | `sendToQQ` 末尾无条件写 `data.message_ids = sentMessageIds`，而它只在**分条发送**时才有内容 —— 单条发送时是 `[]`。于是 `Array.isArray(ids) ? ids : fallback` 拿到空数组，fallback 永不生效 |
| 0.18.2 | 发出去的消息没有标签 | `tagFor` 挂在了 `poll.js` 的**入站**路径上，给「用户自己发进来的话」加前缀。方向反了 —— 需要知道「这句是哪边说的」的人是用户，他自己发的话不需要标签 |
| 0.18.3 | 引用后仍回默认会话 | `qq_send` 没传 `user_id` 时 target 是 `{ kind: 'private' }`，**没有 id**。索引键 `targetKey()` 记成 `private:`，查询侧算的是 `private:1321833118`，两边永远不等 |

**教训**：前两轮的测试断言都是「**有没有**」（有没有记、有没有标签），
没有一条断言「**值对不对**」。第三轮才补上「`targetKey` 必须等于 `private:<peerUin>`」。

同类模式值得警惕的地方还有：

- 判断「在跑」时，`openStep` 有值不代表在跑 —— 崩溃的会话会留下永久残留。
  现在加了新鲜度检查（10 分钟内没写盘就当 idle），否则 `/进度` 第一条永远是个僵尸。
- 会话目录的 mtime **不反映写入**（往已有文件追加内容不改父目录 mtime）。
  判「最近活跃」必须看日志文件或投影文件的 mtime。

### 兼容性说明

- **v1 只接私聊**。群聊的入站路径**一个字都没改**（还是 `pickSessionId`），
  群窗口 / 攒批 / 门控那套状态机原样保留。
  原因：群聊切会话会让 `window.js` 的 pending 和 `batchHolds` 指向错误目标，
  那是另一套需要单独设计的改动，不该混在这次里。
- **不新增数据文件**。焦点和编号表落在现有的 `~/.dsh/qq-bridge-state.json` 里
  （新增 `focus` / `cmdTable` 两段），按「仍在监听集合里」自洁，与 `groups`/`privates` 同规矩。
- **老配置文件自动兼容**。新配置项都有默认值，`{...DEFAULTS, ...raw}` 自动补齐；
  `toolFeatures` 走 `normalizeToolFeatures()` 容错（实测 11 种非法输入全部安全回落到默认）。
- **`qq_send` 不传 `options.features` 时按「全开」兜底**，
  保证老调用方（测试、第三方代码）拿到的行为与 0.17.3 逐字一致。

## 安装

```bash
dsh plugin --profile desktop add dsh-onebot-channel
```

装完去 **设置 → QQ 桥接** 填协议端地址和 token，把 QQ 号 / 群绑到会话上。

> 配置存在 `~/.dsh/qq-bridge.config.json`，**不在插件目录里** —— 重装插件不会丢。

**前置条件**：需要先跑一个 OneBot 11 协议端，并把插件的 `onebotHttp` / `token` 指过去。
插件不读你的 QQ 密码，只跟协议端说话。

## 她不会让你干等（2026-11-03）

两条互补的机制，解决「消息发出去半天没动静」：

**① 要干活时先出一声（提示词层）。** 插件注册一段常驻系统段落，告诉她：
判断这一条需要长作业（读文件、跑命令、多步推进）时，**先 `qq_send` 一句**再埋头干。
普通聊天不受影响 —— 每句都加「稍等我看看」只会啰嗦。

> 常驻意味着**不用每个新会话手动贴 `docs/QQ对话说明.md`**；它不进会话历史、
> 不占对话 token，重启后仍在。宿主没有 `systemPrompt` 服务时自动跳过，不影响收发。

**② 真出故障时插件替它说话（代码层）。** 这些情况 QQ 那头原本一个字都收不到：

| 情形 | 插件做什么 |
|---|---|
| 回合以 `reason.kind === 'error'` 收尾（接口报错 / 上下文超限） | 发一条带 `[系统]` 的通知：「她的回复没能发出来，可以再发一条」 |
| 崩溃后被补了 `interrupted` 收尾 | 同上 |
| 等满 `outboundEntryTtlMs` 仍没有 `turn/end`，**但 agent 还在跑** | 说一句「还在处理」，并**保留这条回复**继续等（最多 2 次，之后按丢失处理） |
| 等满 TTL 且 agent 已经不跑了 | 明说「中断了，没能发出来」，丢弃条目免得堵住后续转发 |

**绝不误报的沉默**：`aborted` 一律不通知 —— 你自己点了停止、DSH 正在卸载、
上层编排取消，那些都是「有意为之」，不是故障。发错一条比少发一条更糟。

通知走 `callOneBot` 唯一出口，所以**白名单照旧生效**，不会因为「这是系统通知」就发给白名单外的号。
同一个目标 60 秒内只播一条（接口连着挂时不刷屏），每个队列条目每种类型也只播一次。

## 工具

它们仍然可用，只是要先去设置页打开那一档。历史查询、说说发布和手动记忆工具按既有决定未注册：

### 工具箱：按功能档开关（0.17.4）

工具 schema 是**每次请求**都进上下文的固定开销（全开实测约 10.3 千字符 / 5 千 token 量级）。
所以设置页「配置 → 工具箱」把不常用的能力按用途分档，**关掉的那一档根本不注册**（schema 不生成）：

| 档位 | 包含 | 默认 | 关掉省 |
|---|---|---|---|
| 发送消息 | `qq_send` | 恒开 | —— 关了这个插件就没意义，所以**不给开关** |
| 沉默权 | `qq_wait` `qq_pass` `qq_skip` `qq_close` | 开 | 约 2.6 千字符 |
| 表情包 | `qq_emoji_search` `qq_face_pick` `qq_face_preview` `qq_face_rename` `qq_collect_face` | 关 | 约 3.8 千字符（最大一块） |
| 语音识别 | `qq_voice` | 关 | 约 0.5 千字符 |
| 发送语音 | `qq_send` 的 `voice` 参数 | 关 | 约 0.3 千字符 |
| 戳一戳 | `qq_poke` | 关 | 约 0.5 千字符 |

按默认值装好之后约省 4.8 千字符（剩余约 5.5 千）—— 具体数字由设置页**实测**给出，本文此处只是量级。

三条要紧的：

1. **改完要重启 DSH**。工具在插件 `apply` 里注册，改 `toolFeatures` 不会热生效。
2. **表情包必须整档启停**。档内五个工具互相指名（`qq_face_rename` 让你先调 `qq_face_pick`，
   `qq_face_preview` 让你看完去 `qq_collect_face`），拆开就会留下指向不存在工具的话术。
3. 关掉一档之后，`qq_send` 的说明会**跟着变短**：提到那一档工具的话术整段消失，
   `voiceOut` 关掉时 `voice` 参数**从 schema 里移除**（而不是留着参数调用时报错）。
   失败路径上的报错（收藏表情没匹配上等）也按开关换措辞 ——
   否则模型会去调一个不存在的工具，拿到 `UNKNOWN_TOOL` 后换个写法再试，反而更烧 token。
   `lib/face-resolve.js` / `lib/preview.js` 的报错则统一改成**不点名任何工具**的通用说法。

```jsonc
// 发消息 + 经典小表情
{ "text": "搞定了", "emoji": "OK" }

// 发收藏夹里的商城大表情
{ "text": "看这个", "custom_emoji": "猫" }

// 查官方表情目录
{ "query": "比心" }        // → 比心（编号 319）
{ "all": true }            // → 列出全部目录（398 个，10 个包）

// 看表情包 —— 文件名是 MD5 哈希，只有看图才起得了名
{ "index": 1 }

// 收藏表情包
{ "message_id": "-313561868" }                    // 直接收某条消息里的那张（最省事）
{ "message_id": "-313561868", "image": 1, "desc": "猫脑过载" }
{ "index": 1, "desc": "猫脑过载" }                // 或按「收到的图片」目录序号
{ "recent": 1, "desc": "猫脑过载" }               // 或最近收到的那张
```

历史查询、说说发布和手动记忆工具目前未注册；它们的历史示例已从本节移除。

说说可见性：`1` 所有人 · `4` 仅好友 · `16` 仅自己 · `64` 指定好友 · `128` 分组。

### 你不一定非要回话（沉默权）

QQ 桥接和真人聊天，最不像的地方是「真人会不回、会晾着、会说完了就走」。0.7.1 给模型补上了这三种**不说话**的出口，让对话有节奏、不粘人：

| 场景 | 怎么做 | 工具 |
|---|---|---|
| 对方明显还没说完（「我跟你说」「等下」「还有」） | 等一会儿，看下文再说 | `qq_wait` |
| 没话说 / 不想接 / 话题翻篇了 | 划走 —— 这一回合什么都不发 | `qq_pass` |
| 双方都收尾了（嗯 / 好 / 哈哈 / 晚安），再补一句就多余 | 收摊，记下聊到哪儿、下次怎么接 | `qq_close` |

**划走 ≠ 删掉刚写的话**（0.9.3 修正）：模型经常「先写一句正文 → 再觉得太催了 → 调 qq_pass」，
早先的实现会把正文一起吞掉，于是会话里她明明说了一句话、QQ 上却什么都没有（用户报的「她发消息了我没收到」）。
现在：正文里有真话就照发，只有纯动作（「（尾巴摆了摆）」）或纯标点时 `qq_pass` 才真的按下不发。

`qq_close` 有硬约束：如果对方还有提问没回答，桥接会拒绝收摊，逼模型先把话接完再走。`qq_close` 写下的「下次怎么接」会在下次开场时自动带回，避免冷启动尬聊。

更细的判断逻辑（收尾评分、节奏底座、自动静默）见 [docs/QQ对话说明.md](docs/QQ对话说明.md)。

### 戳一戳（0.16.5）

QQ 的「拍一拍」是一种**比消息轻得多**的叫你一声。以前插件对它完全没有反应 ——
根因不是「没实现回戳」，而是**入站根本没接**：

`handleWsEvent` 开头是 `if (event?.post_type !== 'message') return`，而戳一戳是
`post_type: 'notice'` 事件。于是所有 notice 在那一行被无条件丢掉。
现场证据：线上 WS 收到 115 个事件、其中 29 条是消息 —— 剩下 86 个全被吞掉，
日志里 `grep notice` 计数是 **0**。

现在两头都通了：

| 方向 | 行为 |
|---|---|
| 别人戳她 | 起一轮，正文里写明「谁戳了谁 + 是用户本人还是群友」；同一处 10 秒内连戳只回一次（`pokeCooldownMs`） |
| 群友互戳（没戳她） | 只记日志，不唤醒她 |
| 她自己发起的戳 / 戳自己 | 忽略（防自问自答） |
| 她主动戳人 | `qq_poke` 工具，走 `group_poke` / `friend_poke` |

⚠️ **两种事件形状的 `user_id` 语义不一样**，这是真机抓包才发现的坑：

```
群戳：  { group_id, user_id:<戳人者>,   target_id:<被戳者> }
私聊戳：{ user_id:<会话对端>, sender_id:<戳人者>, target_id:<被戳者> }
```

私聊戳的 `user_id` **不是**戳人者（SnowLuma 内部是 `peerUin`）。照抄 NapCat 文档
直接读 `user_id` 会把「谁戳的」认错。统一判据是 `target_id === self_id`，
两种形状下都成立。`tests/poke-sim.mjs` 里专门锁了这条。

### 收藏表情包：GIF 原样保留（0.16.4）

群友发的表情包大多是真动图。以前「收进收藏夹」这条路有两个问题叠在一起：

| 问题 | 现象 | 修法 |
|---|---|---|
| 传的是 `file://` | 协议端读的是**它自己那台机器**的盘。协议端跑在别的机器 / VM 上时，每次都 `ENOENT` —— 不是 GIF 收不进去，是**什么图都收不进去** | 一律改走 `base64://`，把字节塞进请求体，跟两边文件系统解耦 |
| 只能从「收到的图片」目录取源 | 群友刚发的表情包还没落进目录，手上只有正文里的 `[#消息编号]` | 新增 `message_id`（+`image=N`）：`get_msg` → 下载 → 收藏，不用等缓存 |

实测（SnowLuma 2.2.1，跨机）：1 077 407 字节、**202 帧**的 GIF 经 `base64://` 收进收藏夹，
从 `p.qpic.cn` 取回来仍是 `image/gif`、1077407 字节、MD5 与本地文件**完全一致** —— **每一帧都在，动画没丢**。

> 帧数这里踩过一个坑，记一下：最初用「裸扫 `0x21 0xF9`」数帧，得到 213，比真实的 202 多 11 个 ——
> 多出来的全落在 LZW 压缩数据子块里（那是偶然出现的字节序列，不是帧边界）。
> 现在 `gifFrameCount()` 走 GIF 块结构遍历（遇扩展块读子块链、遇图像描述符才 +1），
> 实测 202 正确。**这个错误一度被当成验收结论写进 README，所以留痕。**

体积上限 8 MB（`images.js:IMAGE_MAX_BYTES`）：base64 会把请求体放大 4/3，
超限直接报错，比拖到超时好排查。

### 收藏表情：关键词找回并优先使用（0.16.11）

回复确实需要视觉反应时，先按 QQ 收藏备注里的名称和关键词匹配商城大表情；没有合适项时再考虑经典小表情。备注建议写成「简短名称 | 2-4 个关键词」，如「委屈小猫 | 委屈 撒娇 求安慰」。多关键词会按命中数优先选择。

### 收藏表情要能用得上（0.16.14）

**标签决定能不能搜到。** 收藏备注是以后按情绪找回它的唯一线索，所以收藏时 `desc` 必须写成「名称 | 2-4 个情绪词」。写成剧情（「他甩了我那天」）就永远搜不到了 —— 想被别人在什么心情下翻出来，就写那个心情。

碰到搜不到的**老收藏**，用 `qq_face_rename` 看图改名：不带 `desc` 调一次会把那张图直接送到她眼前，看清是什么情绪之后，再用 `desc` 写成「名称 | 2-4 个情绪词」。实测本机 22 个收藏里 21 个的备注是句子，按「委屈 / 无语」搜一律落空。

要配表情时先调 `qq_face_pick`（按情绪列候选，只查不发），挑一个再传给 `qq_send` 的 `custom_emoji`。

**表情填错不连累文字。** `custom_emoji` 匹配不上时只跳过表情、话照发，返回值里会带 `custom_emoji_missed` 说一声。只有「只发一个表情、没有文字、表情也没匹配上」才算真失败 —— 那种情况确实没东西可发。

明确的 QQ 商城/动画表情可主动收藏；普通图片仅在明显是可复用的梗图或反应图时收藏，不收照片、截图、文件和聊天记录卡片。每条消息最多收一张；图已显示在上下文中时可直接按消息编号收藏。

### 连续对话的顺序与额度（0.16.12）

窗口批次不会抢在开窗那条 `@` 前面：`@` 投递成功前，攒着的续聊一律不 flush。首次投递失败时会退还这一天的开窗额度，同一个 `@` 重试成功后重新计入，然后才放行批次。

这道门控会落盘，所以进程重启不会让顺序重新乱掉；它最长保留 90 秒（`OPENING_HOLD_TTL_MS`），超过就当那条 `@` 不会再来了、直接放行批次，不会把群永久锁在攒批状态。

### 想结束话题时怎么收（0.16.15）

对方说「好吧 / 行吧 / 就这样吧 / 随你吧」这类**让步**时，`qq_close` 不会再被拦 —— 这些是附和，不是提问。以前「吧」结尾一律判成疑问，于是永远收不了尾。

真的收不了尾（对方还在问、还在求）时，`qq_close` 会返回**状态码**（`open-question`）而不是一句话，界面上显示成 `[系统] …` 状态提示。**它不是聊天内容，不会被发到 QQ 上** —— 这一点在出站层还有第二道闸：这一回合 `qq_close` 被拒过，正文一律不转发。

想结束但拿不准时，用 `qq_pass` 划走。**划走之后 `qq_close` 会直接放行**（因为这一回合你已经处理过对方了），只是不记「上次聊到哪儿」。

连续被拒 3 次会自动收摊（`close-refused-x3`）—— 宁可这次收得不体面，也不会无限循环下去。对端也是 AI 时这一点尤其重要。

### 「这条不用回」有专门的出口（0.16.16）

自己判断出某条消息不用回时，调 `qq_skip`：**这一回合什么都不发，连正文也不发**。

为什么需要单独一个工具：`qq_pass` 的规则是「正文里写了真话照样发」（那是为了不吞掉她真说的话），而判断「不用回」时她最容易写下的恰恰是那句判断本身——「这条不用回了」「对方好像想结束」。那段话以前会被自动转发出去，对方看到的就是她在自言自语地分析对话；**对端是 AI 时会顺着它继续回，话题反而停不下来**。

| 工具 | 语义 | 正文发不发 |
|---|---|---|
| `qq_skip` | 这条不该有回复 | **不发** |
| `qq_pass` | 我看了，这次先不开口 | 有真话就发 |

`qq_skip` 只压「自动转发正文」这一条路；已经用 `qq_send` 发出去的话不受影响。标志是一次性的，不会吞掉下一回合。

### 忙的时候不再排队：改用 steer（0.16.19）

用户实测：「会卡排队。排队的消息都是旧的，因为本次会话其实正常的推进且持续回复。」「表现为 `qq_wait` 和 `qq_msg_history` 交替工作……而 @ 触发进入了队列中进行排队。」

根因在宿主那一侧的两个队列上——`followup` 进 **`next-turn`**，只在**回合边界**被认领、**一次只认领一条**；`steer` 进 **`next-step`**，当前回合的下一个步骤边界就认领、**整队全取**。

而插件原来只有一条路：`agent.followup()`。她一个回合里 `qq_wait` 40 秒、翻历史、分条发好几条，这期间进来的每条消息都只能排队，回合结束后**一条开一个新回合**——等轮到它们时早就是旧话，而且她**已经在当前回合里用 `qq_msg_history` 看过这几条了**，于是对着同一段话再回一遍。

现在按 agent 状态分流：**忙 → `steer`（插进当前回合的下一步），闲 → `followup`（行为与改动前逐字一致）**。宿主没有 `status` / `steer` 时自动退回 `followup`，不丢消息。历史查询工具当前未注册；这里的工具名是当时报告中的上下文。

配套：`waitTurnMaxMs`（默认 60 秒，0 = 不限）限制**一个回合里 `qq_wait` 的累计时长**——回合长度是排队问题的上游，只夹「单次」不够（她可以连打四次 40 秒）。额度按 QQ 号/群记，**每次有新消息投给她就重置**；用完了不报错，`qq_wait` 立刻返回当前情况并提示「现在开口，或者收掉这一轮」。

### 投递队列的 8 个顺序缺陷（0.16.17）

独立审核在 0.16.13 那套「@ 前先投积压」里又挖出 8 条，全部修掉。它们有个共同点：**107 条断言全绿时它们都在**，因为原有测试只验「主路径走没走」，没验并发、退避和失败后重试。

其中三条最要命：

- **`@` 会插到正在投的批次前面**。「满 3 条立即投」是常态，而 `@` 到达时如果正好在投，旧实现直接返回「跳过」不等它——所以「旧话后到」在最常见的场景下**原样复现**。现在会等那一批投完再重试。
- **退避被完全绕过**。`@` 触发的那条路不看 `pendingRetry`，于是每来一条 `@` 就把同一个失败批次重打一次（实测 5 次 `@` → 重打 5 次）。
- **没投出去的批次会被当成投成功**。handler 返回 `skipped` 时消息被剔出队列，同时又被从 `@` 的上下文里剔掉——两边都剔，**消息彻底消失**。

另外五条：插件卸载后旧 handler 仍被调用、`lastDeliveredSeq` 会回拨导致旧话重复、关窗后盘上的 `pending` 会在重启时复活、`message_seq: null` 撞成 `seq:0` 让第二条消息被静默丢弃、窗口循环正常投掉的批次没从 `@` 上下文里剔除。

### `@` 会先把攒下的消息投完（0.16.13）

窗口内攒着的续聊（不满 3 条、未到 8 秒）不再越过新来的 `@`：`@` 到达时会先把这批投出去，再投 `@` 本身。这样模型总是按真实顺序看到「旧话 → 新话题」，不会一边回新话题、一边突然收到几轮之前的旧话又把话题拉回去。

这批话只投一次：投完之后它们不会作为 `@` 的未读上下文再出现一遍；而夹在它们中间、没进队列的群友发言（她没看过）仍然保留在上下文里。

批次正文会自己说明攒了多久，例如「这是刚才攒下的 2 条，时间跨度约 9 秒；如果你已经在聊别的话题，这些可能已经过时，优先回最新的」——让模型有判断依据，而不是让它自己推时间戳。

积压投递失败时不阻塞 `@`：`@` 是用户在明确叫她，必须优先保证；失败的那批留在队列里等重试。

### @ 之后继续聊（0.16.3）

群里 @ 她后默认开启限时对话窗口：触发者和配置的用户本人的后续消息、任何人的 @，以及引用她窗口内回复的消息可继续进入对话；其他普通群聊仍会跳过。窗口消息按批次处理，空闲超时、时长上限、回复数或预算到达后自动关闭。设置位于「对话节奏」，可配置开关、静默时间、单窗回复数及每日开窗额度。

活动时段默认 `12:00-14:00`、`18:00-09:00`，跨午夜有效；时段外仍照常回复直接 @，但不打开连续对话窗口。

### @ 人（0.14.0）

群里回话时点名叫人。跟引用一样，**@ 只挂在第一条消息上** —— 分条发送时后面几条不带 @，
否则同一个人会被连点 N 次，群里看到的就是刷屏。

| 场景 | 行为 |
|---|---|
| 群里有人 **@ 她** | 自动 @ 回那个人（引用 + @ 一起带） |
| 群里没 @ 她（其他触发） | 不 @ |
| 模型想 @ 别人 | 传 `qq_send` 的 `at` 参数（QQ 号） |
| 私聊 | `at` 参数被忽略（私聊没有 @ 这个概念） |

段顺序实测（SnowLuma 2.2.1，回读确认服务端原样保留）：

```
reply → at → text
```

也就是**先引用、再 @、最后正文**，跟 QQ 客户端自己的排列一致。

**不 @ 自己**：`at` 填本机号会被忽略并记日志 —— 那是无意义动作，还容易写错成「@ 机器人自己」。

**为什么不给 @ 单独做白名单**：这条消息本来就只能发到已放行的群，群里所有人都看得见它；
@ 只是多一次提醒，不构成新的越权面。真正的越权面在「发给谁」，那道闸由 `allowlist.js` 管。

### 引用回复（0.13.0）

QQ 的引用是**逐条消息**的属性，所以插件按这个规则来：

- **默认自动引用**「触发这次回复的那条」——被 @ 的那句，或私聊里最新那句。
- 模型想明确引用别的，就传 `reply_to`（填正文里 `[#数字]` 的那个数字）。
- **分条发送时只引用第一条**，后面几条是裸消息 —— 跟 QQ 客户端原生行为一致，
  也避免刷屏。

正文里的锚点长这样（每条消息一个，紧跟在时间戳后面）：

```
（2026-10-31 20:15）[#-2123597213]（QQ群 123456·群友「张三」（QQ 789，不是用户本人））帮我看看这个
```

群上下文里如果某条消息**引用了别人**，会再标一个箭头：

```
[#114105673]群友「李四」: 把个人战改一改就是狼人杀 → #1519605856
```

`→ #1519605856` 表示李四这句话是引用 1519605856 那条说的。

**为什么用 `[#id]` 而不是整句说明**：这段文字每回合都进上下文，
写长了就是纯烧 token（当年「表情标记说明」被重复 92 次的教训）。
所以只放一个极短标记，含义在 `qq_send` 的工具描述和
[docs/QQ对话说明.md](docs/QQ对话说明.md) 里各说一次。

**装饰段失败不会吞掉回复**：引用的那条可能已被撤回，@ 的号可能已退群，
表情 id 可能协议端不认 —— 任何一种都可能让整条消息发送失败。

出站按「装饰性从强到弱」**逐级剥离**，每一级只去掉一种段再试一次：

```
reply + at + text   ← 原样
      at + text     ← 去掉 @
           text     ← 再去掉引用
```

（表情也在这条链上，排在最后。）每一级都记日志。
宁可少一个 @ 或引用，也不能让回复凭空消失 —— 这是「表情幽灵 id」那次踩出来的原则。

⚠️ 踩过的坑：最初把三级降级写成串行的 `if`，判断条件读的是**已经剥过的**变量，
结果 @ 和引用在同一次重试里被一起去掉 —— 既试不出到底是哪种段把消息搞挂的，
也白白丢了本来能用的引用。现在按原始段逐级剥离，`tests/at-sim.mjs` 钉住了这个行为。

### 分几条，也由她定

不传 `segments` 时按句末标点自动切（老行为）；传了就按她给的分段原样发 —— 真人会自己决定「这句分三条还是一条说完」，而不是被标点机械切开。

```jsonc
// 一句话拆成三条，逐条发出、中间带停顿
{ "segments": ["我跟你说", "那个事搞定了", "不过还差一点"] }
```

传 `segments` 时 `text` 被忽略；空字符串段自动丢掉；段内的 `[表情:呲牙]` 挂在该段末尾。

### 她记得你是谁（关系持久化）

称呼、活跃度和「关于他的几条事实」落在 `~/.dsh/qq-bridge-memory.json`，**重启不丢**：入站会自动记昵称和活跃度；开启 `memoryEnabled` 后，记忆卡会随消息逐步补充。下次被叫醒时，这些会以一小段 `（关于他：称呼：…；记得：…）` 带进正文。

一张卡最多 8 条事实、注入正文约 180 字上限 —— 它是**每回合常驻**的，不控长度就是烧 token。不想要这段就设 `memoryEnabled: false`。

### 先记账，再决定什么时候回（标记已读的中间态）

原来 WS 通路是「来一条投一条」：对方连发三句，就开三个回合、被连问三遍。
`replyQuietMs` 治不了这个 —— 它只是把**每一个回合**各推迟一遍，三条消息仍然是三个回合。

现在私聊多了一层合并窗口（`mergeWindowMs`，默认 2500，设 `0` 关闭）：

```
来信 → 立刻记账（markSeen + 游标推进，等于「已读」）→ 入池攒着
     → 窗口到点（或攒够 mergeMaxMessages / 到达 mergeMaxWaitMs）→ 一批放行 → 一个回合
```

- 「已读」指的是**内部记账**，不是推给 QQ 的回执（OneBot 没有已读回执接口）。
  它的作用是不让轮询把同一条再拎一遍，同时保证「攒着没回」这件事在状态里是明确的。
- 投递失败会把记账撤回去（`mergeSnapshots`），轮询或下一批还能重试 —— 不是静默丢消息。
  唯一的代价：进程在窗口内被强杀（不是正常卸载）时，那一两条「已读」记账已经落盘，会丢掉。
  窗口只有 2.5 秒，正常卸载会记日志并保留痕迹。
- 只作用于私聊。群里是 @ 才投递，一条 @ 就是一件事，攒起来反而怪。
- 跟 `replyQuietMs` 会叠加（2.5s 窗口 + 5s 静默 = 7.5s），两个都想开时建议只留一个。

### 没人叫她，她自己想起来找你（主动搭话）

默认**关**（`proactiveEnabled`）。打开后每 60 秒看一次该不该开口，
真正开口还要过四道闸：

| 闸 | 默认 | 配置 |
|---|---|---|
| 静默时段 | 23:00–08:00 不打扰 | `proactiveQuietFrom` / `proactiveQuietTo` |
| 空闲够久 | 6 小时 | `proactiveIdleHours` |
| 当日配额 | 1 次 | `proactiveDailyMax` |
| 没被回应的退避 | 2ⁿ 倍，封顶 4 倍 | `proactiveBackoffMax` |

关键点：这一层**不自己写文案**。它只是往同一个会话里投一条内部来信：

```
（主动搭话：距上次说话已经 7 小时。上次聊到「…」，可以从「…」接着聊。
想说什么就说……但这事你自己定：没什么想说的就 qq_pass，不用硬找话。）
```

于是「说」还是「不说」仍然由模型判断，转发 / 分条 / 抑制标记全部复用原链路。
硬拼一句「在吗」发出去，就退化成定时问候机器人了 —— 这是这条设计的红线。

状态落在 `~/.dsh/qq-bridge-proactive.json`（重启不丢，否则每次重启都重新「攒够 6 小时」或把日配额清零）。
设置页有「现在试一次」，跳过所有闸立刻投一次（开关关着也能试）。

**对谁开口**：`proactiveTargets` 是白名单，元素形如 `private:1000000001`。

- **空数组 = 所有已绑会话的私聊**（默认，也是升级上来的老行为）；
- 非空 = 只对名单里的人算，名单外的连「该不该说」都不判；
- 只认私聊，群里不主动（`candidates()` 只取 `routes.private`，且必须有 sessionId）。

设置页里是「所有已绑私聊 / 只对勾选的人」两选一 + 每人一行勾选框。从「所有人」取消一个人会自动展开成显式名单 ——
因为空数组的语义是「全员」，直接把「取消某个人」写成空数组会得到完全相反的结果。
每行还有「对TA试一次」（`POST /proactive-now {only}`），可以只对某个人手动开一次口，不用来回改名单。

**手动触发会轮转**：候选按「最久没被主动过」排序（从没主动过的排最前），
所以连点「现在试一次」会依次换人，不会三次都砸在同一个人身上（0.9.2 修的就是这个：
之前固定打候选列表第一个，另一个人永远轮不到）。按钮旁边会写明这次轮到谁。

**只回动作 = 沉默**：主动搭话回合里，如果她只回了「（尾巴摆了摆）」这类纯动作描写，
转发链会把它当沉默丢掉（日志记一笔），不会真的发到他手机上 ——
普通聊天里「（笑）好呀」这种带真话的照常发。

### 设置页能调什么

顶上一排是功能分区，一次只显示一块；「保存」和「重新载入」始终在右上角。

| 分区 | 内容 |
|---|---|
| **概览** | 连接状态 + 统计块（私聊/群绑定、今天主动几次、记住几个人、待合并条数、推送是否连通），以及「现在在跑什么」的自然语言摘要；数字都可点进对应分区 |
| 绑定 | 私聊 / 群聊各自一行：QQ 号、名字、绑定会话。**私聊**那行还有「前缀」；群聊没有 —— 群头由插件按发送者身份自动拼，见下方「三种前缀」。 |
| **对话节奏** | `replyQuietMs` 回复前静默、`mergeWindowMs` 合并窗口（+ 上限 / 条数）、`waitMaxMs` 等待上限（单次）、`waitTurnMaxMs` 单回合等待总量（0 = 不限）、`closureEnabled` 允许判断收尾、`notifyTurnFailures` 回合故障通知、`autoForwardReply` 自动转发、`backfillOnStart` 上线补历史（+ 页数 / 投递条数）、`splitMode` **怎么分条**：按换行（她自己决定说几条）/ 按句末标点（一句一条）；群聊连续对话窗口：`windowEnabled`、`windowIdleMs`、`windowMaxReplies`、`windowPerPeerDaily`、`windowPerGroupDaily`、`windowMaxMs`，活动时段为 `waterWindows`；戳一戳：`pokeEnabled`、`pokeCooldownMs`。 |
| **主动搭话** | 上卡：`proactiveEnabled` 开关、`proactiveIdleHours` 空闲门槛、`proactiveDailyMax` 日上限、静默时段、退避上限。下卡「对谁开口」：所有人 / 只对勾选的人 + 每人上次主动时间与「为什么现在还不说」 |
| **关系记忆** | `memoryEnabled` 开关、记住了谁（称呼 / 事实条数 / 说过几句）、一键清空 |

| **高级** | 分条（字数 / 条数 / 碎片阈值 / 间隔）、轮询间隔、补漏间隔、**私聊**默认前缀、图片副本目录、语音产物目录（目录外会拒绝）、只在 @ 时响应、冷启动会话。 |

#### 三种「前缀」，别混（0.18.4 起界面里也写了）

界面里叫「前缀」的东西有三个，作用域完全不同 —— 这是最容易看错的地方：

| 名字 | 在哪 | 管什么 | 生效范围 |
|---|---|---|---|
| **私聊默认前缀**（`textPrefix`） | 高级 | 她收到私聊消息时，正文前那行来源标记 | 所有**没在绑定表里单独填过**前缀的好友 |
| **绑定表里的前缀**（`routes.private[id].prefix`） | 绑定 → 私聊那一行 | 同上，但只给这一个好友换 | 那一个好友；填了就盖掉上一行 |
| **命令前缀**（`qqCommandPrefix`） | 对话节奏 | QQ 里发 `/进度`、`/去 3` 的触发符 | 你发的命令，跟前两行完全无关 |

**群聊没有前缀可配**，这是故意的：群头是插件按发送者身份自动拼的 ——

```
（QQ群 975663147「咸🐟集体养殖中心」·群友「暮秋槐」（QQ 1071787454，不是用户本人））
```

它的作用只有一个：**让她分得清哪句是你说的、哪句是群友说的**。这个信息必须由插件保证准确，
交给用户手填反而可能填错，所以群聊那一格现在是说明文字、不是输入框。

> 0.18.3 及以前：群表也渲染了输入框、`api.js` 也照存，但群路径**从不读** `route.prefix`
> （全仓库只有私聊路径调 `prefixOf`）。填了等于没填 —— 那种「看起来能调、实际不生效」的假配置
> 比没有更坏，所以两边一起撤掉了（`tests/ui-wiring.mjs` 的 3b/3c 两节钉住）。

**私聊前缀的拼法**：插件会在你填的值后面接身份标记。以「）」结尾就切掉它再接，否则直接接：

| 你填 | 她实际看到 |
|---|---|
| `（QQ 私聊）` | `（QQ 私聊·用户本人 QQ 1321833118）晚上好啊` |
| `【阿明】` | `【阿明】·用户本人 QQ 1321833118）晚上好啊` ← 括号只剩半边，所以建议以「）」结尾 |

概览里「现在在跑什么」的第一行是**这版代码的版本号 + 进程 pid + 启动时间**（0.10.1 补）。
改完代码发现行为没变，先看一眼这行：版本没涨、启动时间还是上午 —— 说明主进程仍在跑旧代码，重启即可，不用怀疑改错了。
第二行「连接」会同时列出 HTTP 地址与 WS 连接状态（0.15.0 补），排查「消息收不到」时先看它。

**不给控件的**：`token` / `wsToken`（凭据，前端不回显；留空即保持原样）、`fallbackToLiveSession`（会绕过路由表）、
`allowSendToAny`（安全逃生阀）、`enabled`（只在加载时读一次，放按钮会误导成即时生效 —— 页面只在它为 `false` 时显示告警）。
这批「故意不给控件」的字段在 `tests/ui-wiring.mjs` 里有白名单和理由，新加配置忘了接 UI 会直接测试失败。

**不接**：群信息检索、撤回消息、表情回应、发图片到空间。

## 发表情

两条路都通：

**① 正文里写标记**（推荐，一句话能带多个）

```
搞定了[表情:OK][表情:庆祝]
```

→ QQ 上收到的是 `搞定了` + 两个真表情（标记本身不出现）。支持中文名和编号，
表情**附在它前面那句话的后面**。这条路不依赖工具调用，**自动转发**也生效。

**② `qq_send` 的参数**

```json
{ "text": "搞定了", "emoji": "OK" }        // 经典小表情
{ "text": "看这个", "custom_emoji": "猫" } // 商城大表情
```

区别：经典小表情能跟文本**拼在同一条消息**里；商城大表情协议端只能**单独发一条**。

⚠️ 收藏表情走的是协议端扩展 action（SnowLuma 的 `send_custom_face`），**不是 OneBot 11 标准** ——
换协议端（NapCat / LLOneBot）可能没有，届时经典表情照常能用。

### 表情编号的坑

内置表情表共 **275 个**（编号 0~348），但它是 OneBot 生态的**社区通用编号**，不是 QQ 官方编号，
两者对不上（2026-10-27 实测）：

- 275 条里有 **109 条**在 QQ 官方目录（398 个）里查无此 id —— 「幽灵 id」
- 另有 **11 条**名字对得上但 id 错位（「晕」内置记 17、官方实际是 34）

拿幽灵 id 去发，协议端报 `OIDB error 11000: id N sysemojis cfg not found`，
**整条消息发不出去** —— 不是丢个表情，是连文字一起没。

所以出站做了三层防护：查 QQ 官方目录解析 → 校验 id 真的存在 → 校验不过就**跳过表情、文字照发** →
发送层再兜一层（带表情失败则去掉表情重发文字）。

**宁可少发一个表情，也不能让整条回复凭空消失。**

## 配置

`~/.dsh/qq-bridge.config.json`（UTF-8 无 BOM）。改完**不用重启**，下一轮轮询就生效。

> 它决定注册哪些工具，而注册发生在插件 `apply()` 里。

## 安全边界

**13 个高风险 action 物理拦截** —— 拦截点在 `callOneBot()`，所有协议端调用的唯一出口。
不是「提示词里写别调用」，而是**调用即抛错、连 HTTP 都不发**。

| 类别 | action |
|---|---|
| 交出账号凭证 | `get_cookies` `get_credentials` `get_csrf_token` `get_clientkey` `get_rkey_server` `request_decrypt_key` |
| 踢下线 / 改状态 | `bot_exit` `set_online_status` `set_diy_online_status` `set_input_status` |
| 越权社交动作 | `send_like` `set_qzone_ban` |
| 删说说 | `delete_qzone_msg`（发说说允许，删不允许） |

清单在 `lib/blocked.js`，要放开哪项改那个集合 —— 但凭据那六项别动。

> `add_custom_face` 原先在封禁清单里，2026-10-27 放开了：
> 协议端**没有**「收到图片自动收藏」的逻辑，收藏夹不显式写就是空的，
> `custom_emoji` 那条路永远走不通。现在改成走受控工具 `qq_collect_face` ——
> 只允许收藏插件自己收到过的图。

**出站两道闸门（2026-10-28）** —— 都挂在 `callOneBot()` 这个唯一出口上，绕不过去：

| 闸门 | 管什么 | 实现 | 拦住了什么 |
|---|---|---|---|
| 目标白名单 | **发给谁** | `lib/allowlist.js` | `qq_send` 的 `user_id`/`group_id` 是 agent 随便填的 → 群里一句 prompt injection 就能让她往任意 QQ 号发消息 |
| 内容审计 | **发什么** | `lib/sensitive.js` | 回复里顺嘴写出 `C:\Users\...`、`token=xxx` → 本机路径和凭据直接进群 |

白名单从**已有的配置**派生，不新增一份（避免两处漂移）：
私聊 = `peerUin` ∪ `ownerUin` ∪ `routes.private` 的键；群 = `groupUins` ∪ `routes.group` 的键。
自动转发的目标全部来自路由表，所以永远不会被误伤。

- 想临时放开：`allowSendToAny: true`（⚠️ 等于把上面那个风险还回去，只在排障时开）。
- 白名单**全空**时（还没配 `peerUin`）不拦，只记一条警告 ——
  闸门的语义是「限制已配置的服务范围」，不是「没配好就把插件锁死」。
- 内容审计**故意不匹配**裸的 32 位十六进制串：表情包文件名就是 MD5，
  加了这条会把正常表情和消息整条拦掉。详见 `lib/sensitive.js` 的注释。

**说说发布功能当前未启用**；相关确认配置仅供保留的内部实现使用，当前没有生效入口。

## 排障

```
~/.dsh/qq-bridge-load.log      插件日志（超 2 MB 自动轮转）
~/.dsh/qq-bridge-state.json    游标
~/.dsh/qq-bridge.config.json   配置
```

```bash
grep "\[config\]" ~/.dsh/qq-bridge-load.log | tail -1   # owner= 有没有 → 新版加载了吗
grep "\[poll\]"   ~/.dsh/qq-bridge-load.log | tail -3   # 群在监听吗
grep "\[group\]"  ~/.dsh/qq-bridge-load.log | tail -5   # skip (no at)? 未配置会话? seeded?
grep "error"      ~/.dsh/qq-bridge-load.log | tail -5   # fetch failed = 协议端挂了
```

**收不到消息**：① 协议端在跑吗 ② `selfUin` / `peerUin` 对吗 ③ 这个号在 `routes.private` 里吗
④ 会话开着吗（没开靠 `resumeColdSession` 冷启动）

**撞到白名单** —— 工具报「出站被白名单拦截：好友 xxx 不在允许范围内」：

```bash
grep "\[allow\]" ~/.dsh/qq-bridge-load.log | tail -3   # 白名单为空时会有警告
```

这是**硬闸，不是 bug**：`qq_send` 只能发给「插件正在服务的对象」
（`routes` 里的好友/群 + `peerUin`/`ownerUin` + `groupUins`）。
要么把目标加进设置页的会话绑定，要么临时 `allowSendToAny: true`（不推荐）。

**日志里写着「收到消息事件」但会话里没动静** —— 看下一行是不是「重复消息（已处理），跳过」。
这是去重误杀：旧版本拿私聊的 `message_seq` 判新旧，但私聊的 seq 是两套编号混着的
（自己发的 71xx 连续、对方发的 50xxx/20xxx 跳号且不单调），会把新消息当成旧消息丢掉。
0.6.1 起私聊改用时间戳判新旧（群聊仍用 seq），这个问题不会再有。

```bash
grep "收到消息事件" ~/.dsh/qq-bridge-load.log | tail -3   # 消息进来了吗
grep "重复消息"     ~/.dsh/qq-bridge-load.log | tail -3   # 被去重误杀了吗
```

**群里没反应**：① 监听列表里有这个群吗（日志 `[poll] group loop started, watching [...]`）
② `groupOnlyWhenAt` 开着的话必须先 @ ③ 首次启动会 seed，启动前发的消息不会被回复，再 @ 一次

**同一条回复连着发了好几遍**：日志里搜「已转发过，跳过重复发送」。
这是「没等她发完就发下一条」触发的 —— agent 跑回合期间 `session.seq` 不推进，
两条消息拿到同一个游标 → 认到同一个回合 → 同一条回复发两遍。0.6.2 起按
「属于我自己的那条 user/message」定位回合，同一个回合只发一次。

**重复收到同一条**：删掉 `qq-bridge-state.json`，游标归零后会重新对齐（不会重放）。

### 设置页找不到「QQ 桥接」入口

服务端 API 和工具都正常、但设置页没入口 —— 通常是插件**没进 boot graph**，
浏览器侧拿不到 client bundle。

```bash
# DSH 的 web 端口（Electron，端口不固定）
Get-NetTCPConnection -State Listen | Where-Object { $pids -contains $_.OwningProcess }

# 拉 boot manifest —— 这条 SSE 直接吐出完整的插件清单
curl -s http://127.0.0.1:<port>/plugins/events | head -1
# → data: {"type":"graph","graph":{"entries":[{"id":"...",...}]}}
```

entries 里没有自己的插件 id = 没进 graph。常见原因是 `package.json` 的 `name`
跟插件的**安装目录名**不一致（DSH 按目录名找包，并校验 name 相等）。

### 本地改了源码怎么推进 DSH

| `~/.dsh/profiles/desktop/node_modules/dsh-onebot-channel/` | **DSH 运行时真正 import 的目录** |

之前只同步前者 → 运行副本一直是旧的 → 现象是「日志写着工具注册成功，agent 那边只有 `qq_send`」。

`sync.mjs` 还会**反向**把工作区里的说明文档拉回仓库 `docs/`（工作区那份才是 agent 真正读到的那份）。

跑完 **重启 DSH** 才生效 —— 插件是进程启动时加载的。

> ⚠️ 改 `package.json` 的 `name` 时必须跟**安装目录名**一致，否则设置页入口会消失。
> `sync.mjs` 会在同步前校验，对不上直接拒绝同步。

## 启动顺序：为什么入站要等一等

SnowLuma 的 OneBot 端口（HTTP 3000 / WS 3001）是**等 QQ 登录成功之后才 listen 的**。
而 DSH 常常比 QQ 先起来（开机自启的典型顺序），中间会差上 1~2 分钟。

这段窗口里如果直接起轮询和 WS，就是对着没开的门反复敲 —— 满屏 `timeout` 和 `1006` 断连，
真正出问题时反而在日志里找不到线索。

所以插件的启动分成两段：

| 阶段 | 时机 | 做什么 |
|---|---|---|
| 立即 | 插件加载时 | 按「工具箱」分档注册工具（默认 5 个）、设置页 API、主动发消息接口、回复转发队列 |
| 延后 | OneBot 探活通过后 | 启动私聊/群聊轮询、WS 事件推送、主动搭话的钟 |

- **工具先注册**：工具是出站能力，跟 QQ 登录无关。早给 agent，QQ 迟迟不登录时它也不至于「一个工具都看不到」。
- **探活用 `get_login_info`**：它要真的进了 QQ 才应答，是「能干活了」的准信儿。退避 1s→5s，总超时 150s。
- **超时就照样启动**：与其让桥接彻底不动，不如让轮询自己重试（错误分级保证不吵）。
- **错误分级**：`ECONNREFUSED` / `fetch failed` / 超时这类「门还没开」的错误，
  不写 `state.lastError`（设置页那个字段是给「插件坏了」看的）、不逐条刷日志，只在状态翻转时记一条；
  `retcode` 不对、HTTP 5xx 这类真问题照旧上报。
