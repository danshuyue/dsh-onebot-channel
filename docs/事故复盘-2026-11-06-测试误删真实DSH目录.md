## 根因链

1. `progress-sim.mjs` 的 `reset()` 会执行：
   - `rmSync(join(DATA, 'storages', 'session_projcache'), { recursive: true })`
   - `rmSync(join(DATA, 'storages', 'workspace.json'))`
   - `rmSync(SESSROOT, { recursive: true })`（整个 `$HOME/.dsh/sessions`）
   - 最后 `writeWorkspaces([], [])` 写入 `{ unit: { name: 'workspace', version: 1 }, ... }`
2. 这次没有隔离 HOME：Windows 上 `os.homedir()` 跟 `USERPROFILE`，只设 `HOME` 无效。
   - `run-isolated.mjs` 同时设置 `HOME`/`USERPROFILE`，走它是安全的。
   - 直接 `node tests/progress-sim.mjs` 时 `DATA` 指向真实 `C:\Users\Yansunsky\.dsh`。
3. DSH 2.0.22（core 0.2.2-rc.1）的 `@deepseek-ai/dsh-workspace` 声明 `version: 2`，
   没有 `compatibleVersions: [1]`，v1 的 `workspace.json` 被直接拒绝：
   `StorageError: unit 'workspace': stored version 1 is not accepted by version 2`。
4. `workspaceRegistry` 起不来 → `sessionController` / `workspace-controller` /
   `ui-deliverables` / task-board / git-graph / session-archive 全部
   `pending (waiting for service: workspaceRegistry)`。
5. 渲染端 `@deepseek-ai/dsh-experimental-client-ui-cot-translation` 等 `sessionController`，
   一直停在 `loading` → `web boot: 1 entry did not activate` → 3 次 reload →
   `runtime.failed {stage:"renderer-startup"}`。

## 为什么安全模式能起来

安全模式把 profile / storages / sessions 复制到
`C:\Users\Yansunsky\.dsh\recovery\safe-runtime-*`，使用独立的 DSH home，
读到的 `workspace.json` 是好的（v2）。代价是安全模式里的改动不会写回真实 home。

## 教训

- **文档里的“别那么干”拦不住人/agent；必须让程序拒绝。**
- 对会删数据的测试，守卫要用**白名单**（必须证明自己在沙箱里），
  不要用黑名单（“不是真实 HOME 就放行”）。
- Windows 上 `HOME` ≠ `os.homedir()`：改 `HOME` 不会改变 Node 的 homedir，
  必须同时改 `USERPROFILE`；判断真实目录用 `os.userInfo().homedir`。
- 存储 schema 不兼容时，错误会以“某个 UI entry did not activate”这种间接形式出现——
  看到 `web boot: N entry did not activate` 要先翻 host 日志找第一个 `StorageError`，
  不要只盯渲染层。
