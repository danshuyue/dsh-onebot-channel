## 2. C3：一行判据，断了一条规则

**症状**：群里有人引用她刚说的话，她收不到（`skip (no at/window)`）。

**根因**：`tool.js` 里调用 `noteReply` 的条件自己重新推了一遍 `message_ids`：

```js
// 旧（错）
Array.isArray(result?.data?.message_ids) ? result.data.message_ids.length > 0 : ...
```

单条发送时协议端回 `message_ids: []` → 三元第一个分支命中、求值 `false`
→ `noteReply` **一次都不被调用** → `selfMessageIds` 恒空 → 「引用她」恒不成立。

**修法**：直接用上面已经兜好的 `messageIds`（`outbound.js:1026` 的自动转发路径就是这么写的，
只有 `qq_send` 这条平行路漏了）。

**⚠️ 这条的变异验证（M1）就是把实现还原成旧代码** —— 测试立刻变红，
证明根因判断成立。这一步不能省：2026-11-08 的 0.20.2 就是在没有这步验证的情况下
白加了一套账本（写完之后才发现根因假设是错的）。

## 3. C1：时间戳到秒 + 间隔直接算给她

**症状**：她判断「对方回得慢，20–45 秒一句，还一口气发几条」，实际是 15~20 秒一句、
偶尔两条同一秒到。

**根因（两条信息同时缺失）**：
1. 群上下文那几行**根本没有时间戳**（只有主消息那一行有，且只到分钟）；
2. 唯一的那个还只到分钟 —— 1 秒和 45 秒在分钟刻度上完全一样。

**修法**：
- `stampOf()` 输出 `（2026-11-09 02:11:25）`（加秒）；
- 新增 `gapOf(prev, now)` → `+15s` / `+1m20s` / `+2h`，**直接写差值**，
  不让她自己做减法（实测她做错的就是这个）。

**效果示例**（测试里的真实输出）：

```
（2026-11-09 00:11:15）[#1]你自己: @1836323387你今天是摸鱼摸到几点？
（2026-11-09 00:11:30） +15s [#-2]群友「思念酱」: 摸到锅都凉了，两点多
（2026-11-09 00:11:31） +1s [#-3]群友「思念酱」: 你还真来聊啊
（2026-11-09 00:12:10） +39s [#4]你自己: 你算半个同事了
```

## 4. C2：她能看见自己了

**根因**：`fetchGroupHistory()` 与 `fetchGroupHistoryFor()` 都按
`sender.user_id !== selfUin` **整条剔除她的发言**。于是上下文是
「几段别人的旁白 + 大片空白」，拼不出对话回合感 —— 空白只能归因成「对方慢」。

**修法**：
- 数据源**不再过滤自己**，`nameOfSender()` 把她标成「你自己」；
- 身份提示补一句「标『你自己』的是你先前已经发出去的话，别当成别人说的，也别再重复一遍」；
- **但「处理新消息」那一步仍然排除自己**（`isSelfMessage`），否则她说一句会被当成新消息再处理一次 → 回环；
- WS 路径同样：自己发的消息**只进缓冲**当上下文，不往下处理。

⚠️ 这是一处容易改错的地方：**「进上下文」和「当成新消息处理」是两件事**。
只删数据源过滤而忘了补 `isSelfMessage`，会形成回环。

## 5. C4：窗口期内整段对话都进队列

**根因**：入窗判定复用 `isWindowEligible()`，它只认「触发人 / @ 她 / 引用她」。
设计稿 §3 写的「别人接话也算」被压成了「引用她」一条窄路，而那条路还被 C3 堵死。

**修法（关键设计决定）**：**不改 `isWindowEligible` 的语义，另开一条通道**。

| 函数 | 回答的问题 | 口径 | 代价 |
|---|---|---|---|
| `isWindowEligible` | 算不算在跟我说话（要不要**开一个回合**） | 窄 | 一次模型调用 |
| `shouldQueueForWindow` | 要不要进**上下文队列** | 宽 | 就是一段文字 |

两件事混在一起，就是这次故障的根源。

**上限（用户 2026-11-09 定的）**：
- `groupContextCount`（默认 5）= **一次性 @** 的软上限；
- `groupContextMax`（默认 20）= 任何路径的**硬顶**；
- `windowQueueMax`（默认 20）= 攒批队列的**容量**，超了丢最老的；
- `windowQueueAll`（默认 true）= 关掉就退回旧行为。

⚠️ **`groupContextCount = 0` 必须保留原义（= 不带上下文）**。
`Number(x) || 20` 会把 0 吞成 20，等于「用户关掉了上下文，插件却开始塞 20 条」。
所以逐字段判 `undefined`，不用 `||`。见 `resolveContextLimit()`。

## 6. C5：诊断包新增 `conversation` 节

**用户原话**：「我觉得应该带上具体的聊天记录和这段时间的会话的思考过程工具调用等详细信息。」

**新模块 `diaglog.js`**：
- `recordBody()` —— 投给模型的正文原文（`deliver.js` 唯一投递点）
- `recordTool()` —— 工具名 + 参数摘要 + 返回摘要 + 耗时
- `exportDiagLog()` —— 最近 2 小时的记录

**怎么做到「一次覆盖全部工具」**：在 `env.js` 的 `waitForTools()` 里给
`tools.register` 包一层。那是**所有工具注册的唯一入口**，
包一处就自动覆盖现在和将来的工具（逐个改 15 处既有漏的风险，也让新工具默认不记录）。

**⚠️ 包装器踩到的坑（voiceout-sim 抓到的）**：
宿主调工具是 `execute(args, exec)`，第二个参数 `exec` 带 `agent.session`，
`qq_send` 靠它算 `callerSessionId`（拼标签 + 记引用索引）。
第一版包装器写成 `(args) => inner.call(this, args)` —— **把 exec 吃掉了**，
5 条断言立刻变红（`索引里记的是发起调用的会话（实际 undefined）`）。
改成 `(...callArgs) => inner.apply(this, callArgs)` 之后恢复。

**循环依赖**：`env.js` → `diaglog.js` 是单向的；`diaglog.js` **不 import env**
（否则互引，模块求值顺序不可靠）。它自己的兜底日志用 `console.error`。

### 怎么跑

```bash

node tests/run-isolated.mjs            # 全量（74 个）
```
