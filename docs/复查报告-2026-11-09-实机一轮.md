## 三、发现的问题：窗口批次漏改（已修）

### 3.1 现象

导出的 8 条正文里，**窗口批次那 7 条全都没有**：
- 秒级间隔（`+15s` / `+1s`）
- 「你自己」标注

而 0.21.0 的核心目标正是「让她看见节奏、看见自己」。

### 3.2 根因

0.21.0 只改了 `deliverGroupMessage`（一次性 @ 走的路），
**漏了 `deliverWindowBatch`**（窗口续聊走的路）。

而群里一轮对话里，只有**第一条 @** 走前者，**其余全部**走后者。
等于本次修复最核心的两条信息，在 95% 的正文里都没生效。

### 3.3 为什么测试没抓到

`group-self-context-sim` 只覆盖了一次性 @ 那条路的正文渲染。
**这是一次「断言只覆盖实现的一部分」**——比假绿更隐蔽，因为它测的东西是真的，
只是测的不是最常用的那条路。

教训已写进代码注释和新测试的文件头：
> **一个渲染逻辑有多条路径时，每条都要有断言。**

### 3.4 修法与验证

`deliverWindowBatch` 的每行渲染与群上下文对齐：

```js
const prev = index > 0 ? list[index - 1] : null
const gap = prev === null ? '' : gapOf(timeOf(prev) * 1000, timeOf(message) * 1000)
const gapPart = gap === '' ? '' : `${gap} `
const name = selfUin !== '' && senderUin === selfUin ? '你自己' : ...
```

新增 `tests/window-batch-render-sim.mjs`（**12 断言**）+
`tests/window-batch-render-mutation.mjs`（**3 变异，全部被抓住**）。

> ⚠️ 这两个测试用的是**源码切片断言**而不是集成投递。原因：
> `deliverWindowBatch` 的集成跑法需要 `getConfig().routes.group` 落到目标群上，
> 而手写整份 cfg 会被 `loadConfig` 的默认值合并吞掉（实测 `routes` 变空、投递直接 failed，
> 白折腾半小时）。切片断言照 `voice-fail-sim` 的先例做，能精确钉住那段代码，
> 且被变异验证证明「删掉实现就变红」。

### 4.2 红的部分（环境所致，但必须记录）

本轮复查时 `group-context-sim` 与 `group-self-context-sim` **变红**：

```
✗ 应该投递 2 条（两条 @），实际 0
```

已确认**不是我这次改动引入的**（把 `poll.js` 回滚成改动前，它们照样红）。原因是：

1. 这两个测试**从真实 `~/.dsh/qq-bridge.config.json` 备份出发**再改；
2. 而你的真实配置**在本轮之后变成了**群 `716197431`、`groupUins=['716197431']`；
3. 测试改 `groupUins` 后，`state.js` 会**丢弃不在 `groupUins` 里的窗口游标**
   （这是设计如此，见 `state.js` 的注释）；
4. 于是窗口开不出来 → 投递 0 条 → 全线红。

**这是「测试依赖真实配置形状」的债**，不是功能回归。
真正在跑的功能（本机 0.21.1）是好的 —— 日志里 7 个批次全部投递成功就是证据。

> 修这个债的办法：把这两个测试也改成**自带完整沙箱配置**（像
> `window-queue-all-sim` 那样），不再从真实配置出发。
> 但那需要重写它们的 setup，本轮时间不够（关机在即），**留给下次**。
