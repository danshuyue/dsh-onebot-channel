## 三、发现的问题：窗口批次漏改（已修）

### 3.1 现象

导出的 8 条正文里，**窗口批次那 7 条全都没有**：
- 秒级间隔（`+15s` / `+1s`）
- 「你自己」标注

而 0.21.0 的核心目标正是「让她看见节奏、看见自己」。

### 3.2 根因

0.21.0 只改了 `deliverGroupMessage`（一次性 @ 走的路），
**漏了 `deliverWindowBatch`**（窗口续聊走的路）。

而群里一轮对话里，只有**第一条 @** 走前者，**其余全部**走后者。
等于本次修复最核心的两条信息，在 95% 的正文里都没生效。

### 3.3 为什么测试没抓到

`group-self-context-sim` 只覆盖了一次性 @ 那条路的正文渲染。
**这是一次「断言只覆盖实现的一部分」**——比假绿更隐蔽，因为它测的东西是真的，
只是测的不是最常用的那条路。

教训已写进代码注释和新测试的文件头：
> **一个渲染逻辑有多条路径时，每条都要有断言。**

### 3.4 修法与验证

`deliverWindowBatch` 的每行渲染与群上下文对齐：

```js
const prev = index > 0 ? list[index - 1] : null
const gap = prev === null ? '' : gapOf(timeOf(prev) * 1000, timeOf(message) * 1000)
const gapPart = gap === '' ? '' : `${gap} `
const name = selfUin !== '' && senderUin === selfUin ? '你自己' : ...
```

新增 `tests/window-batch-render-sim.mjs`（**12 断言**）+
`tests/window-batch-render-mutation.mjs`（**3 变异，全部被抓住**）。

> ⚠️ 这两个测试用的是**源码切片断言**而不是集成投递。原因：
> `deliverWindowBatch` 的集成跑法需要 `getConfig().routes.group` 落到目标群上，
> 而手写整份 cfg 会被 `loadConfig` 的默认值合并吞掉（实测 `routes` 变空、投递直接 failed，
> 白折腾半小时）。切片断言照 `voice-fail-sim` 的先例做，能精确钉住那段代码，
> 且被变异验证证明「删掉实现就变红」。

## 六、第三次发现（最严重）：`apply` 抛 ReferenceError

### 6.1 现象

```
[apply] THREW ReferenceError: registerQzoneTool is not defined
    at Module.apply (lib/index.js:189:5)
```

### 6.2 根因

合并远端 6 个提交时，远端动过 `lib/index.js`（**-73 / +22 行**）。
它在 import 行里删掉了 `registerQzoneTool`，但**第 189 行的调用还在**：

```js
// 第 53 行（合并后，缺 registerQzoneTool）
import { registerSendTool, registerEmojiSearchTool, registerCollectTool, ... } from './tool.js'
// 第 189 行（还在调用）
void registerQzoneTool(ctx)
```

### 6.3 后果

`apply` 在注册工具那一步直接抛错 → **轮询、WS、工具注册全部起不来**。
插件表面上「装好了」，实际是哑的。

### 6.4 这解释了此前的两个「谜」

我在 §4.2 里猜「测试红是因为真实配置形状变了」——**猜错了**。
真实原因是这条 ReferenceError：测试进程一跑 `apply` 就崩，
所以 `group-context-sim` / `group-self-context-sim` 永远投递 0 条。

**这也是我今晚第二次被同一个教训打中**：
上一次（0.21.0 的窗口批次漏改）是「测试没覆盖到那条路」，
这一次是「报错被当成环境问题、没去看真实堆栈」。
修法：**先看日志里的 THREW，再猜环境**。

### 6.5 修法与验证

把 `registerQzoneTool` 加回 import 列表。两个此前红的测试**立刻变绿**。
