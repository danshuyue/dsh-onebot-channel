### 问题 1：关掉每一档之后，还有没有残留文字指向被关掉的工具名？

**qq_send 的 description / parameters / render 三条路径：已做干净，实测无残留。**

```
全关配置 {silence:false, emoji:false, voiceIn:false, voiceOut:false, poke:false} 下：
  description 里残留的工具名：无
  render(失败路径) 里残留：无
  voice 参数：不存在
```

对照代码位置（`lib/tool.js`）：
- 沉默权段（`qq_skip`/`qq_wait`/`qq_close`/`qq_pass`）由 `if (features.silence)` 包裹 —— `lib/tool.js:68` 一带

**但有 4 处残留，分布在别的文件里，是描述之外、模型同样会读到的文字：**

| 位置 | 内容 | 何时到达模型 | 是否已修 |

| `lib/proactive.js:344` | 「就 qq_pass，不用硬找话」 | 主动搭话回合，**每次都拼进投给模型的正文** | ❌ **未修** |

### 问题 3：关掉「表情包」后 `custom_emoji` / `emoji` 还在吗？模型会怎么用？

**两个参数都还在。** 这是个**有意的取舍**（`lib/tool.js` 注释里写明了理由），但我实测发现它的实际后果比注释预期的更差。

- `emoji`（经典小表情）：**必须保留**。它走的是 `resolveFaceIdSafe` + 内置表 `lib/emoticons.js`，**完全不依赖表情包档的 5 个工具**。关掉它等于砍掉一个不花额外 token 的能力。
- `custom_emoji`（收藏贴纸）：保留，但描述换成「当前没有开启表情包功能，无法列出收藏夹 —— 只有你**确定**备注里有这个词时才用，不确定就不要传，别盲猜」。

#### 实测：盲猜的后果不是「白费一次调用」，而是**静默发出错的表情**

`findCustomFace`（`lib/custom-faces.js:130-137`）取打分第一名且 `score > 0` 就返回。打分规则（`lib/custom-faces.js:97-120`）里，**单个词的部分命中就有分**（desc +3 / summary +2 / emojiId +1）。

用真实收藏夹形状（备注是句子，如「穷光蛋思考中」「这是你的私人癖好」）实测：

```
猜「思考」→ score=1001 → 发出「穷光蛋思考中」
猜「私人」→ score=1001 → 发出「这是你的私人癖好」
猜「问号」→ score=1001 → 发出「问号呆脸」
猜「好」  → score=1001 → 发出「这是你的私人癖好」   ← 致命
猜「被打死」→ score=0  → 不匹配，返回 null
单字命中率：好/要/中/用/的/一/不/是 → 5/8 命中
```

**判断（这是本审计最重要的负面结论）**：
- 关掉表情包档后，模型**看不到**收藏夹里有什么（`qq_face_pick` 没了），但它手里仍有一个能按关键词命中的 `custom_emoji`。
- 「猜『好』发出『这是你的私人癖好』」这种语义事故，**不会报错、不会出现在返回值里**，只有 `note('tool', ...)` 一行日志。用户看到的就是她莫名其妙发了张不合适的图。
- 注释里说「猜不中只会白费一次调用」——**这个预期是错的**：实测 5/8 的常见单字是「猜中但猜错」。

**建议（不阻塞交付，但要知情接受）**：这条要么接受、要么把 `custom_emoji` 在表情包档关闭时**一起从 schema 移除**。后者的代价是「用户自己攒的收藏夹彻底用不上」，但换来的是不会发错图。二选一，不要停在中间态还宣称「猜不中只是白费一次调用」。

### 问题 4：有没有哪个工具的内部实现依赖了被关掉的工具？

**查过，没问题。没有工具在 `execute` 里调用另一个 `qq_*`。**

依据：
- 全仓 `tools.register` 只出现在 `lib/tool.js`（12 处）和 `lib/env.js` 的 `waitForTools`（服务获取），没有任何工具内部转发到另一个工具。
- `lib/tool.js` 的 12 个 `execute` 各自只调用底层模块函数：`sendToQQ` / `findCustomFace` / `resolveFaceIdSafe` / `sendVoiceToQQ` / `rankCustomFaces` / `pickPreviews` / `transcribeVoice` / `sendPoke` / `collectFace` 等。
- `qq_send` 内部确实用到「表情包档」的底层模块（`lib/custom-faces.js` 的 `findCustomFace`、`lib/face-resolve.js` 的 `resolveFaceIdSafe`），但那是**模块函数**不是**工具**，关掉档位不会让它失效 —— 这正是问题 3 里 `custom_emoji` 仍然能工作的原因。

### 问题 5：配置容错 —— 手改 `toolFeatures` 会不会崩 / 静默变全开或全关？

**查过，没问题。所有非法输入都安全回落到默认值，既不会崩，也不会静默变成全开。**

实测（直接调真实的 `normalizeToolFeatures`）：

| 输入 | 输出 |
|---|---|
| `undefined` | 默认值（silence:true，其余 false） |
| `null` | 默认值 |
| `"yes"`（字符串） | 默认值 |
| `1`（数字） | 默认值 |
| `[]`（数组） | 默认值 |
| `{}` | 默认值 |
| `{emoji:true}` | 只开 emoji，其余默认 |
| `{emoji:"true"}` | **emoji 回默认 false**（字符串不算布尔，正确） |
| `{emoji:1}` | 回默认 false（正确） |
| `{silence:false}` | 只关 silence（正确） |
| `{unknown:true, emoji:true}` | 未知键被丢弃，emoji:true 生效 |

依据：`lib/config.js` 的 `normalizeToolFeatures()` —— 只认 `typeof === 'boolean'`，且 `loadConfig()` 里对 `config.toolFeatures` 统一收一次，下游无需各判。

**这里原本有个真实风险，已被正确处理**：`loadConfig()` 用的是 `{ ...DEFAULTS, ...raw }` 浅合并，嵌套对象会被**整个替换**而不是逐键合并。实测裸合并的行为是 `{toolFeatures:{emoji:true}}` → 只剩 `{emoji:true}`，缺的键会变 `undefined`。`config.js` 在合并后立刻调 `normalizeToolFeatures` 补齐，所以这个坑被堵住了。**这个补丁是必要的，删掉它就会踩坑。**

### 问题 6：设置页保存后 config 里实际写进去的是什么形状？会不会把没暴露的键冲掉？

**形状正确，不会冲掉未暴露的键。**

- 前端：`lib/client.js` 用 `onFeature(key)` 单独处理嵌套字段（不用 `onField`，那会把整个对象替换成 `true`），`Object.assign({}, next.toolFeatures)` 后再改单键 —— 正确。
- 后端：`lib/api.js` 新增 `OBJECT_FIELDS = ['toolFeatures']`，`applyTunables` 里用 `normalizeToolFeatures(body[key])` 赋值。**这是关键** —— 我实测过：如果只把 `toolFeatures` 加进 `publicConfig()` 而不加进任何 `*_FIELDS` 白名单，`applyTunables` 的 5 个循环都不会碰它，**勾选结果根本不会落盘**。实现方加了 `OBJECT_FIELDS`，这个坑避开了。
- 落盘形状：`normalizeToolFeatures` 保证永远是「5 个键、全是布尔」，不会写进多余键，也不会缺键。

### 问题 7：「改完需重启」有没有在设置页明确告知？

**告知了，但同一屏上还有一句相反的话 —— 这是缺陷 B。**

**做对的部分**：`lib/client.js` 的 `renderToolbox()` 里有 `qqb-warn` 区块：
> 「改完这一块要**重启 DSH** 才生效（工具是在插件加载时注册的，不像别的参数下一轮就生效）。」

**矛盾的部分**：`lib/client.js:488` 的保存成功提示仍然是硬编码：
> 「已保存，下一轮投递生效（推送链路会自己重连，**不用重启**）。」

这两句话会在**同一次保存操作后同屏出现**。用户改完工具箱点保存，先看到「不用重启」，再往上看到「要重启」。

**根因**：工具注册发生在 `apply()` 里（`lib/index.js:147-183`），而 `apply` 只在插件加载时执行一次。保存配置只改 `~/.dsh/qq-bridge.config.json`，不会重新执行 `apply`。所以工具箱开关**必须重启**，而其他参数走「每轮重读配置」所以不用。

**修法**：把 `client.js:488` 改成条件文案 —— 保存的 payload 里如果包含 `toolFeatures` 且值有变化，就追加「工具箱开关需要重启 DSH 才生效」。tool-switch-dev 在沟通过程中说会改，审计时点该行仍是旧文案（见 §3）。

### 问题 8：老配置文件（没有 `toolFeatures` 键）升级后行为？

**查过，没问题。** 三种情形：

1. **完全没有这个键** → `{...DEFAULTS, ...raw}` 里 `raw` 没这个键，保留 `DEFAULTS.toolFeatures`（5 个默认值）→ 走默认：沉默权开、其余 4 档关。

### 问题 10：有没有过度设计？5 档是不是应该更少？

**5 档是合理的，但有 1 档不该存在。**

**保留 4 档的理由（有数据）**：按实际可省的字符数排序，每一档都够大，值得一个开关：

| 档位 | 实测 schema 字符 | 占比 |
|---|---|---|
| 表情包（5 个工具） | 3776 | 37% |
| 沉默权（4 个工具） | 2588 | 25% |
| 语音识别 | 542 | 5% |
| 戳一戳 | 486 | 5% |
| 发送语音（仅 voice 参数） | 231~240 | 2% |

**不该独立成档的是「发送语音」**：
- 它只值 **231 字符**，是 5 档里最小的一块
- 它不是工具，是 `qq_send` 的一个参数，实现上要单独走一个 `features.voiceOut` 分支
- 它和「语音识别」在用户心智里是同一件事（「语音」），却拆成两个勾选框

**ponytail 视角的结论**：合并成「语音（识别 + 发送）」一档，可少一个复选框、少一个 feature 键、少一处 `if` 分支，代价是用户不能只关一半 —— 但 231 字符的粒度本来就不值得单独控制。**不过这个优化不阻塞交付**，属于「下次动这块时顺手合并」级别。

**没有过度设计的部分**（查过，明确说没问题）：
- 用「不注册」而不是 `tools.restrict()` —— 正确。`restrict()` 需要 scoped context，冷启动 agent 时序保证不了（`lib/config.js` 注释里记了这个决策）
- `toolSchemaSizes()` 不手写常量、运行时实测 —— 正确，而且**这是我这次审计最有价值的建议被采纳的产物**（见问题 F）
- 没有为工具箱新开设置页分区，塞进「配置」页 —— 正确，分区已有 7 个

### 问题 E（中）：沉默权档关掉后 `proactive.js` 仍点名 `qq_pass`

`lib/proactive.js:344` 和 `:347` 把 `qq_pass` 硬编码进 `composeNudge()` 的返回值，而该返回值会作为**正文**投给模型。

实测（直接调 `composeNudge`）：
```
（主动搭话：现在是 2026-11-05 16:59（周四），距上次互动已经 NaN 天。想说什么就说…
…就 qq_pass，不用硬找话。注意：正文里写的东西会原样发到他手机上…直接 qq_pass。）
```
其中出现的工具名：`qq_pass`

**后果**：把「沉默权」档关掉后，主动搭话回合里模型仍被告知「就 qq_pass」—— 但那个工具没注册。模型会去调、拿 `UNKNOWN_TOOL`、然后换个写法再试。**这正是本次功能要消灭的那类浪费，而且它出现在一个「本来就在省着用」的场景（主动搭话）。**

**为什么容易漏**：`composeNudge` 不是工具描述，是**投递正文**，grep `description` 搜不到它。本次改动把 `tool.js` 的 description 全部动态化了，但没人去查「还有谁在往正文里拼工具名」。

**修法**：`composeNudge` 收一个 `features`（或 `silenceEnabled`）参数，沉默权关掉时改成「什么都不说就什么都不写」。

### 问题 D（中）：`sendapi.js` 绕过工具箱开关

`lib/sendapi.js:40-62` 仍然接受 `custom_emoji` 和 `emoji`，走 `findCustomFace` / `resolveFaceSegment`，**完全不看 `toolFeatures`**。

- 这不是 bug（sendapi 是给「agent 之外的程序」用的本地接口，本来不受 agent 工具开关约束）
- 但它意味着：**关掉表情包 ≠ 全系统不能发收藏表情**。如果用户在设置页看到「关掉省 3776 字符」就以为这个能力被彻底关停，认知会有偏差。
- **建议**：设置页那行的说明补一句「只影响她能不能自己挑，不影响本地 HTTP 接口」—— 或者干脆不说，因为确实很少人用 sendapi。**优先级低**。

### 问题 F（已修正）：立论数字虚报约 6 倍

计划文档 `docs/开发提示词-跨工作区会话进度.md` 原称 `qq_send` 描述 10318 字符、12 工具合计约 5 万、每轮固定开销「3 万 token 量级」。

我的实测（`JSON.stringify({name,description,parameters}).length`，与实际进上下文的口径一致）：

| 口径 | 实测值 |
|---|---|
| 12 个工具 schema 合计 | **10272 字符**（纯 description 合计 5113） |
| `qq_send` | 2880（文档称 10318） |
| 默认配置（关 4 档）相对全开 | 省 **5251 字符**（10272 → 5021） |
| 全关相对全开 | 省 8193 字符（10272 → 2079） |
| `prompt.js` 常驻段落 | 299 字符（文档称 3488） |

**根因**：文档量的是「源码里 description 字段的行长度累计」，把缩进、`+` 拼接符、注释行都算进去了，而且量的是源码文本而非实际序列化的 schema。

**lead 已确认并修正文档**，且把「设置页数字必须运行时实测、不许手写常量」写进了规范。当前实现确实做到了 —— `lib/api.js` 的 `toolSchemaSizes()` 运行时实测并缓存，设置页显示的是 `data.toolSizes`。

**这条的价值**：如果照原数字写进设置页文案，就是在骗用户（承诺省 3 万，实际省 4.8 千）。
