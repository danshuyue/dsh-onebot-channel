# 「对话窗口」设计稿（@ 唤醒的缺陷修复）

> 状态：**只讨论，未开发**。基于 0.15.0 源码复核。
> 撰写时间：2026-11-01。
> **定位：这不是新功能，是现有 @ 行为的缺陷修复。**

---

## 0. 一句话

现在 @ 她 = 叫一声、答一句、然后她就哑了。
真实的群聊不是这样：@ 是**开口搭话**，之后是一段连续对话。

**对话窗口**：@ 打开一个窗口，窗口期内不用再 @，对话能自然继续；窗口有静默超时和硬上限，话说够了就关。

---

## 1. 现状：为什么 @ 之后会哑

`poll.js:373-378`：

```js
const atMe = isAtMe(message.message, config.selfUin)
if (config.groupOnlyWhenAt && !atMe) {
  note('group', `${groupId} skip (no at) seq=${seqOf(message)}`)
  return { status: 'skipped' }
}
```

`groupOnlyWhenAt` 默认 `true`。所以没 @ 的消息**只推进游标，永远不进会话**。

结果是：

```
群友：@她 在吗              → 投递，她答 ✅
群友：帮我看个东西          → 没 @ → 丢弃 ❌   ← 对话在这里断掉
群友：就是那个配置          → 没 @ → 丢弃 ❌
```

这不是「不够智能」，是**投递规则缺了一维**：它只认「有没有直接叫我」，不认「我们是不是正在说话」。

---

## 2. 窗口怎么开

**触发**：一条 @ 她的消息被正常投递 → 同时打开该群的对话窗口。

- `openedAt = now`
- `lastActivityAt = now`
- `triggerUin = 发消息的人`
- `repliesInWindow = 0`（这条 @ 的回复算第 1 条）

⚠️ **@ 本身的行为完全不变**：该回还是立刻回、该带引用还是带引用、该 @ 回去还是 @ 回去。
窗口只决定「**之后还能不能继续**」，不改动任何现有行为。

**这条要写成回归保护的验收项**：窗口功能上线后，@ 的单次回复行为必须与现在逐字一致。

---

## 3. 窗口里谁说的话算数

你选的是「**对触发者为主，但别人接话也算**」。落地成一条可判定的规则：

| 消息来自 | 算不算窗口内 | 理由 |
|---|---|---|
| 触发她的人 | ✅ 算 | 主对话方 |
| 任何人 @ 她 | ✅ 算 | 明确在叫她 |
| 任何人**引用她窗口内发过的某条** | ✅ 算 | 直接接她的话 |
| 其他人普通闲聊 | ❌ 不算 | 那是水群的事，不混进来 |

**为什么不干脆整群都算**：整群都算的话，窗口开着期间群里所有闲聊都会变成候选，
成本随群活跃度线性上涨，而且她容易插进别人的话题。上面这条规则把范围压在「正在跟她说的人」。

**「别人接话」的边界写死在这里**，不做模糊判断（比如「紧跟着说的」）——
模糊规则无法测试，也没法跟用户解释为什么这句话算了那句没算。

---

## 4. 节奏：攒一小批再判断

对话要快，但不能逐条判断（对方连发三条会被回答三次）。折中：

```
新消息到了 → 进窗口池
  ├─ 攒够 windowBatchMax 条（默认 3）→ 立刻判断
  ├─ 或距池里第一条过了 windowBatchMs（默认 8 秒）→ 判断
  └─ 池里没新消息 → 什么都不做（不空转、不烧钱）
```

**8 秒**这个值的理由：真人看到消息、想一下、打字，差不多就是这个量级；
比水群的 60 秒快得多，因为这是对话不是采样。

⚠️ **判断是「有没有新消息」驱动的，不是定时器驱动的**。
没人说话时窗口空转不产生任何请求——这点必须写进实现，否则一个 10 分钟的窗口会白跑 75 次判断。

---

## 5. 窗口怎么关

你选的是「滑动静默超时 + 总时长硬上限」。两个条件，任一满足就关：

| 条件 | 默认 | 含义 |
|---|---|---|
| `windowIdleMs` 内没有任何新消息 | 2 分钟 | 对方不说了，聊天自然结束 |
| 从 `openedAt` 起超过 `windowMaxMs` | 10 分钟 | 硬上限，防「群里一直有人说话，窗口永不过期」 |

**另加一条提前关闭**：她连续 `windowMaxPasses` 次（默认 2）都 `qq_pass` → 主动关窗。
理由：连续两次判断「不值得接」，说明这段对话她已经不想参与了，继续挂着只会反复判断烧钱。

**她调 `qq_close` 也立即关窗**（现成能力，`closure.js`）。

---

## 6. 回复形态：前 2 条 @，之后只引用

你选的是「前 1–2 条 @ + 引用，之后只引用」。

| 窗口内第几条回复 | 带 `at` | 带 `reply_to` |
|---|---|---|
| 第 1 条（就是那条 @ 的回复） | ✅ | ✅ |
| 第 2 条 | ✅ | ✅ |
| 第 3 条及以后 | ❌ | ✅ |

**为什么不一直 @**：连着三条 @ 同一个人，群里看到的就是三连击。
**为什么后面还要引用**：不引用的话，群里根本看不出她在回谁。

实现上：`atUin` 由窗口状态算，不再固定取「触发这次回复的人」。
现有逻辑在 `poll.js:471-473`，改成读 `repliesInWindow`。

---

## 7. 预算闸门（你全选了）

| 闸门 | 默认 | 作用 |
|---|---|---|
| `windowMaxReplies` | 5 | 一个窗口最多说几句。没有这个她能说十句，比不说话更劝退 |
| `windowPerPeerDaily` | 10 | 同一个人每天最多开几个窗口，防有人故意 @ 刷窗口 |
| `windowPerGroupDaily` | 20 | 同一个群每天最多开几个窗口，防「一群人轮流 @」把额度吃光 |
| 活动时间段外不开窗 | 复用 `waterWindows` | 半夜两点 @ 一句，不能就在群里聊起来 |
| 窗口开着时水群让路 | 恒开 | 两套逻辑不撞车 |

⚠️ **活动时间段只管「开窗」，不管「那次 @ 的回复」**。
也就是说：半夜 @ 她，她照样回那一条（现有行为），但不进入连续对话。
**不能让已经能用的事因为新功能而变差。**

---

## 8. 与水群的关系：引擎相似，设计分开

| | 水群 | 对话窗口 |
|---|---|---|
| 性质 | 新功能（主动行为） | **缺陷修复**（被动行为的延伸） |
| 触发 | 定时 / 随机 | 有人 @ |
| 节奏 | 60 秒一轮 | 8 秒一批 |
| 范围 | 群里最近的聊天 | 只认「正在跟她说的人」 |
| 默认 | **关** | **开**（因为它修的是现有缺陷） |
| 预算 | 每日 N 轮 | 每窗口 N 句 + 每日 N 窗 |

**实现上可以共用一个小工具函数**（「把一批群消息渲染成投递正文」），
但**不要合并成一个模块**——它们的触发、节奏、预算、默认值都不同，
合在一起会让两边都难改。这个判断写在这里，防止以后有人「顺手重构」。

## 9. 配置项与界面

### 9.1 哪些进界面、哪些写死

原则：**「能调」≠「必须暴露」**。调了也不会更好的写进代码，进 `tests/ui-wiring.mjs` 的
`DELIBERATE` 白名单并注明理由。

| 项 | 类型 | 默认 | 界面 | 说明 |
|---|---|---|---|---|
| `windowEnabled` | bool | **true** | **常显** | 总开关（缺陷修复，默认开） |
| `windowIdleMs` | num | 120000 | **常显** | 静默多久关窗（2 分钟） |
| `windowMaxReplies` | num | 5 | **常显** | 单窗最多说几句 |
| `windowPerPeerDaily` | num | 10 | **常显** | 每人每日最多开窗数 |
| `windowPerGroupDaily` | num | 20 | **常显** | 每群每日最多开窗数 |
| `windowMaxMs` | num | 600000 | 折叠 | 单窗硬上限（10 分钟） |

**共 6 个配置项。**

后四个不做成配置，直接写 `lib/window.js` 顶部常量：

```js
const WINDOW_BATCH_MS = 8000      // 攒批最长等待
const WINDOW_BATCH_MAX = 3        // 攒够几条立即判断
const WINDOW_MAX_PASSES = 2       // 连续几次 qq_pass 关窗
const WINDOW_AT_REPLIES = 2       // 前几条回复带 @
```

理由：进了 `DEFAULTS` 就必须决定「给不给控件」，不给还要进 `DELIBERATE` 白名单解释半天。
它们本来就不该被调，做成常量最省事——**不需要任何白名单条目**。

### 9.2 放在哪个栏

**放「对话节奏」，不新开栏、不放「高级」。**

```
对话节奏
├─ 回复手感（现有：分条模式 / 静默 / 合并 / 收尾 / 自动转发 / 回填）
└─ 群聊连续对话（新）
   ☑ 允许 @ 之后继续聊
   静默      2  分钟后关窗
   单窗最多  5  句
   每人每天  10 个窗口
   每群每天  20 个窗口
   ▸ 展开高级参数（单窗硬上限 10 分钟）
```

理由：

| | 评价 |
|---|---|
| ✅ 好处 1 | 它调的就是「回复手感」——跟同卡片已有的 `mergeWindowMs`、`replyQuietMs`、`splitMode` 是同一类东西 |
| ✅ 好处 2 | 它**不是主动行为**：她仍是被叫才开口，只是叫完能接着说。放「主动开口」会误导 |
| ⚠️ 代价 | 「对话节奏」这张卡会更长（现有 11 项 + 新增 6 项）。靠**卡内折叠**控制，不是靠分栏 |

**为什么不放「高级」**：高级是纯技术参数收容所（轮询间隔、分条字数），
放进去用户找不到，而这个功能**默认是开的**——用户必须能在需要时找到它关掉。

### 9.3 折叠组件

现有 UI 没有折叠模式（`qqb-adv` 只是 grid 布局，`client.js:86`）。
新增 `useState` 开关 + 条件渲染，约 20 行。跟水群那张卡共用同一个组件。

### 9.4 四个必改位置

`config.js` 的 `DEFAULTS` → `api.js` 的字段归类 →
`client.js` 的控件 → `ui-wiring.mjs` 的白名单。

## 12. 验收标准

**回归（最重要）**

- [ ] 窗口功能上线后，单次 @ 的回复与现在**逐字一致**（引用、@ 回去、分条、内容都不变）
- [ ] `windowEnabled = false` 时，行为与改动前完全一致

**开窗与范围**

- [ ] @ 她 → 开窗；随后触发者的消息不用 @ 也能进
- [ ] 别人 @ 她 → 进窗口
- [ ] 别人引用她窗口内发过的消息 → 进窗口
- [ ] 别人普通闲聊（没 @、没引用她）→ **不进**窗口
- [ ] 活动时间段外 @ 她：那一条照常回，但**不开窗**

**节奏**

- [ ] 池里没新消息时，不产生任何模型请求（空转测试：开窗后静默 1 分钟，请求数 = 0）
- [ ] 攒够 `windowBatchMax` 条立即判断
- [ ] 只来 1 条时，等满 `windowBatchMs` 才判断

**关窗**

- [ ] 静默超过 `windowIdleMs` → 关
- [ ] 从开窗起超过 `windowMaxMs` → 关（哪怕一直在说话）
- [ ] 连续 `windowMaxPasses` 次 `qq_pass` → 关
- [ ] `qq_close` → 立即关

**预算**

- [ ] 一个窗口说满 `windowMaxReplies` 句后，后续消息不再开回合
- [ ] 同一个人当日第 11 次 @ 不开窗（但仍正常回那一条）
- [ ] 同一个群当日第 21 次 @ 不开窗

**回复形态**

- [ ] 窗口内第 1、2 条回复带 `at` + `reply_to`
- [ ] 第 3 条起只有 `reply_to`，没有 `at`

**跨天 / 重启**

- [ ] 跨天重置 `openedToday` / `peersToday`
- [ ] 进程重启后窗口丢失，下次 @ 重新开（不报错、不重复投递）

## 13. 风险

1. **成本**：一段 10 分钟的活跃对话，按 8 秒攒批最多产生约 75 个批次。
   实际受「只有新消息才判断」约束会少很多，但仍是本项目里**单次最贵**的场景。
   建议上线后先观察一周，用 `qq-bridge-load.log` 里的 `[window]` 行统计实际批次数再调参数。
2. **`windowMaxReplies` 与 `qq_pass` 的关系**：说了 5 句之后窗口还开着（只是不再开口），
   还是直接关窗？**建议说满了就关**——说满 5 句还不收，对话本身已经不正常了。
3. **多群同时开窗**：三个群同时开着窗口时，三套攒批并行。需要确认 `poll.js` 的自调度防重入
   不会让它们互相阻塞。
4. **和 `groupContextCount` 的关系**：窗口内的批次已经自带上下文，
   不要再叠加「未读上下文」，否则重复。实现时窗口路径应该绕过那段逻辑。
5. **`tests/capability-sim.mjs` 目前是红的**（与本次无关，先记着）。

## 附：为什么定成默认开

水群、主动搭话、会话设定这些都是**主动行为**，默认必须关（会对外说话）。

但对话窗口修的是「**已经发生的行为**」——@ 她本来就会回，只是回完就哑了。
用户对这个功能的预期是「她应该能接着聊」，不是「多了一个新功能」。

所以默认开，理由跟「@ 回复本身默认开」一样：**这是修 bug，不是加功能**。

如果不想要，`windowEnabled = false` 一键回到现在的行为。
