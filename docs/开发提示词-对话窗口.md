## 2. 背景：现在为什么会哑

`lib/poll.js:373-378`：

```js
const atMe = isAtMe(message.message, config.selfUin)
if (config.groupOnlyWhenAt && !atMe) {
  note('group', `${groupId} skip (no at) seq=${seqOf(message)}`)
  return { status: 'skipped' }
}
```

`groupOnlyWhenAt` 默认 `true`。没 @ 的消息**只推进游标，永远不进会话**。

```
群友：@她 在吗          → 投递，她答 ✅
群友：帮我看个东西      → 没 @ → 丢弃 ❌   ← 对话在这里断掉
群友：就是那个配置      → 没 @ → 丢弃 ❌
```

问题不是「不够智能」，是**投递规则缺了一维**：只认「有没有直接叫我」，不认「我们是不是正在说话」。

## 3. 需求规格

### 3.1 开窗

一条 **@ 她** 的消息被正常投递 → 同时打开该群的对话窗口。

窗口状态：

| 字段 | 初值 |
|---|---|
| `openedAt` | 现在 |
| `lastActivityAt` | 现在 |
| `triggerUin` | 发消息的人的 QQ 号 |
| `repliesInWindow` | 0（随后那次 @ 回复会计成 1） |
| `passStreak` | 0 |
| `lastWindowSeq` | 0（第一次进窗口消息时设为该消息的 seq） |

⚠️ **@ 本身的行为必须完全不变**：立刻回、带引用、@ 回去、分条规则，一样都不能动。
窗口只决定「**之后还能不能接着聊**」。

### 3.2 窗口内哪些消息算数

| 消息来自 | 算不算 | 判定方式 |
|---|---|---|
| `triggerUin` 本人 | ✅ | `String(sender.user_id) === window.triggerUin` |
| 任何人 @ 她 | ✅ | 现有 `isAtMe()` |
| 任何人**引用了她窗口内发过的消息** | ✅ | `replyTargetOf(message)` 的 id ∈ 窗口内她发出的 message_id 集合 |
| 其他人普通闲聊 | ❌ | 以上都不满足 |

**「她窗口内发过的 message_id」怎么来**：`outbound.js` 发送成功后返回 `message_id`，
把它记进 `window.selfMessageIds[]`（上限 20）。窗口关闭时清空。

⚠️ 引用某条她**窗口之前**发的消息，**不算**。只认窗口内发出的。

### 3.3 投递分两条路

| 触发 | 投递方式 |
|---|---|
| @ 她 | **立即**（现有行为，走 `deliver()`） |
| 窗口内其它消息 | **攒批**：攒够 3 条 或 距第一条过了 8 秒，才投一次 |

攒批是**有新消息才启动计时**，不是定时器空转。池里没新消息时不得产生任何请求。

### 3.4 关窗（四选一，任一满足）

| 条件 | 常量 | 默认 |
|---|---|---|
| 距 `lastActivityAt` 超过 `windowIdleMs` | 配置 | 120000（2 分钟） |
| 距 `openedAt` 超过 `windowMaxMs` | 配置 | 600000（10 分钟） |
| 连续 `windowMaxPasses` 次 `qq_pass` | 常量 | 2 |
| 模型调 `qq_close` | — | 立即关 |

关窗时清掉：`selfMessageIds`、`pending`、计时器。**保留**当日计数（`openedToday` / `peersToday`）。

### 3.5 回复形态

| 窗口内第几条回复 | `at` | `reply_to` |
|---|---|---|
| 1 | ✅ | ✅ |
| 2 | ✅ | ✅ |
| 3+ | ❌ | ✅ |

`windowAtReplies = 2`（常量）。

实现：`atUin` 不再固定取「触发这次回复的人」，改由窗口状态算：

```js
const atUin = repliesInWindow < WINDOW_AT_REPLIES && senderUin !== '' && senderUin !== String(config.selfUin)
  ? senderUin : ''
```

现有逻辑在 `lib/poll.js:471-473`。

### 3.6 预算

| 闸门 | 配置 | 默认 | 行为 |
|---|---|---|---|
| `windowMaxReplies` | ✅ | 5 | 说满 5 句 → **直接关窗**（不是「还开着但不说话」） |
| `windowPerPeerDaily` | ✅ | 10 | 同一个人当日第 11 次 @ → 照常回那一条，但**不开窗** |
| `windowPerGroupDaily` | ✅ | 20 | 同上，按群算 |

### 3.7 活动时间段

复用 `waterWindows` 那套（如果水群已实现），否则先读一个同名配置；
**默认 `["12:00-14:00","18:00-09:00"]`，支持跨午夜**。

⚠️ **活动时间段只决定「开不开窗」，不影响那条 @ 的回复**。
半夜 @ 她，她照样回那一条（现有行为），只是不进入连续对话。
**不能让已经能用的事因为新功能变差。**

跨午夜判断（照抄 bili-scroll 的实现）：

```js
const start = minutesOf(win.start), end = minutesOf(win.end)
const cur = now.getHours() * 60 + now.getMinutes()
return start <= end ? (cur >= start && cur < end) : (cur >= start || cur < end)
```

## 4. 实现位置

### 4.1 新文件 `lib/window.js`

导出：

```js
export function windowOf(groupId)                    // 取窗口状态（关闭返回 null）
export function openWindow(groupId, triggerUin)      // 开窗（含预算检查，超预算返回 false）
export function touchWindow(groupId, seq)            // 有新活动：续命 + 推进 lastWindowSeq
export function closeWindow(groupId, reason)         // 关窗 + 记日志
export function noteReply(groupId, messageId)        // 回复发出：repliesInWindow++、passStreak=0、记 selfMessageIds
export function notePass(groupId)                    // qq_pass：passStreak++，够数就关窗
export function windowMessages(groupId)              // 取待投递批次
export function startWindowLoop(ctx)                 // 启动关窗巡检 + 攒批 flush，返回 stop 函数
export function resetWindowDay(groupId, dayKey)      // 跨天重置
```

### 4.2 改 `lib/poll.js` 的 `handleGroupMessage`

**判定顺序**（关键，别搞反）：

```js
const atMe = isAtMe(message.message, config.selfUin)
const win = windowOf(groupId)
const inWindow = win !== null && isWindowEligible(win, message)   // §3.2 的三条规则

if (config.groupOnlyWhenAt && !atMe && !inWindow) {
  return { status: 'skipped' }        // 原有行为
}
```

然后：

- `atMe` → 走**现有的**立即投递路径，投递成功后 `openWindow()` + `touchWindow()`
- `!atMe && inWindow` → **不立即投递**，push 进窗口池，`touchWindow()`，返回 `{ status: 'queued' }`
- `atMe && inWindow`（窗口里又 @ 她）→ 按 `atMe` 走立即投递，不重复入池

⚠️ **`status` 新增 `'queued'`**，`poll.js` 的调用方（两处：
`pollGroup` 约 700 行、`handleWsEvent` 约 879 行）要把它当成「已处理」，
**不能**当失败去回滚游标。

### 4.3 改 `lib/outbound.js`

在**一次回合确实发出了至少一条消息**的地方调 `noteReply(groupId, messageId)`。

⚠️ 计数点是「**这一回合说了一句话**」，**不是**「发了 N 条分段」。
分条发 3 条 = 1 次回复。别在 `sendOneToQQ` 里计数。

### 4.4 改 `lib/tool.js`

- `registerPassTool` 的 `execute` 末尾：调 `notePass(groupId)`（仅当 target 是群）
- `registerCloseTool` 的 `execute` 成功分支：调 `closeWindow(groupId, 'qq_close')`

### 4.5 改 `lib/index.js`

`apply()` 里 `startProactive(stopFns)` 旁边加 `startWindowLoop(ctx)`。
窗口功能默认开，**不要**加「配置不全就 return」的前置检查。

### 4.6 改 `lib/config.js` / `api.js` / `client.js`

见 §5。

## 6. 状态结构（有一个必踩的坑）

存 `~/.dsh/qq-bridge-state.json` 的 `windows` 键下：

```jsonc
{
  "windows": {
    "975663147": {
      "openedAt": 1793500000000,
      "lastActivityAt": 1793500060000,
      "triggerUin": "1071787454",
      "repliesInWindow": 2,
      "passStreak": 0,
      "lastWindowSeq": 857676780,
      "selfMessageIds": [857676790, 857676801],
      "dayKey": "2026-11-01",
      "openedToday": 3,
      "peersToday": { "1071787454": 2 }
    }
  }
}
```

### ⚠️ 坑：`loadState()` 会把这个键吃掉

`lib/state.js:77-83` 重建 `state` 时**只保留了** `lastId` / `lastSeq` / `lastTime` /
`privates` / `groups`。新加的 `windows` 在加载时会被**静默丢弃**——
表现是「明明开了窗，重启后窗口全没了」，而且日志里什么都看不出来。

**修法**：在 `loadState()` 的 `state = {...}` 里加一行：

```js
windows: raw.windows !== null && typeof raw.windows === 'object' ? raw.windows : {}
```

**并且**加自洁（跟 `groups` 一样）：`windows` 里不在监听集合的群要丢掉。

## 11. 已知坑（先看，省时间）

1. **`loadState()` 会吃掉新键** —— 见 §6。这是本次最容易翻车的地方，且**静默**。
2. **`status: 'queued'` 不需要特殊处理，但要加日志** —— 两个调用方
   （`poll.js:705` 的 `pollGroup`、`poll.js:880-884` 的 `handleWsEvent`）都只判断
   `'failed'`（回滚游标）和 `'delivered'`（记日志），其它值自然落到「继续看下一条」。
   所以 `'queued'` **不会**误触发回滚。但建议加一行 `note('window', ...)`，
   否则排查时看不出「这条进了池子却没投」。
3. **不要在 `sendOneToQQ` 里计回复数** —— 分条会发 3 次，会被数成 3 句。
4. **计时器要 `unref()` 并在 dispose 时清掉** —— 否则插件卸载后还有野定时器。
   bili-scroll 有过「定时器回调抛错把整个宿主进程带走」的事故（见其 `index.js:1545` 注释），
   回调里必须 `try/catch` 包死。
5. **`deliver()` 会带记忆卡和收尾提示** —— 窗口批次也走它是对的，别自己拼正文绕过。
6. **窗口路径不要再叠 `groupContextCount` 的未读上下文** —— 批次本身已经是上下文，会重复。
7. **配置校验要在保存时做** —— 活动时间段格式错了要当场报错，不要等到运行时不生效。
