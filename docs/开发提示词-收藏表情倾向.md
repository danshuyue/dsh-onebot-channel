## 2. 背景：为什么她不发收藏表情

### 2.1 缺陷一：提示词把收藏表情写成了"次选"，而且埋在长文中段

`lib/tool.js:55-58`，`qq_send` 的 description 中段：

```
表情选择：不是每句话都需要表情。需要用视觉反应时，先用 custom_emoji 从收藏夹找语义合适的表情包；
只有没有合适收藏时才用 emoji 或 [表情:名称] 的经典小表情。通常只选一种，不要叠加装饰。
收藏表情按备注关键词搜索；可传一个短描述，或 2-4 个空格分隔的关键词（如「委屈 撒娇 求安慰」）。
```

问题有三层：

1. **触发条件是被动式的**：「**需要**用视觉反应时」—— 模型得先自己意识到"这句需要视觉反应"。
   但模型的默认倾向是纯文字完成对话，它不会主动去想"这里是不是该配个表情"。
2. **位置太深**：夹在一大段 `qq_send` 说明的中间。模型每回合都在读这段，
   但注意力资源有限，中段的条件式说明基本被忽略。
3. **「不是每句话都需要表情」这句先说**：这是防滥用的，但它先出现，
   实际效果是给模型一个"少用"的初始偏置。

### 2.2 缺陷二：搜不到就 `throw`，一次失败基本断念

`lib/tool.js:138-147`：

```js
if (customEmojiName !== '') {
  const found = await findCustomFace(customEmojiName)
  if (found === null) {
    throw new Error(
      `收藏夹里没找到含「${customEmojiName}」的表情。`
      + '（收藏夹可能是空的 —— 需要先在 QQ 里收藏表情包；也可以改用 emoji 参数发经典小表情）'
    )
  }
  customEmojiId = found.emojiId
}
```

**`throw` 意味着整次 `qq_send` 失败**。模型精心想好的一句话 + 一个表情，
因为表情没匹配上，**话也发不出去了**。模型拿到的是一条错误。
下次它就会学到"别用 custom_emoji，容易失败"——**这是负向强化**。

对比经典小表情那条路（`lib/tool.js:127-136`），用的是 `resolveFaceIdSafe`，
解析不出来**只跳过表情、文字照发**。两条路的标准不一致，收藏表情这条明显更脆。

### 2.3 缺陷三：没有"看得到收藏夹"的入口

模型要选表情，得先知道**有哪些**。现在唯一的列举入口是
`qq_collect_face` 的 `list: true`（`lib/tool.js:698`），但：

- 工具名叫 `qq_collect_face`，描述写的是"把值得复用的表情包收进收藏夹"
- 模型要"挑一个表情发出去"，不会想到去调一个叫"收藏表情"的工具

结果：模型只能**盲猜关键词**。猜不中就 `throw`（见 2.2）→ 负向强化 → 再也不试。

### 2.4 三层叠加的净效果

```
模型想说一句话 → 想配个表情 → 盲猜关键词 → 大概率猜不中 → throw → 整句发不出去
→ 下次不猜了，纯文字
```

所以「没有倾向」不是模型不愿意，是**这条路走不通**。

## 3. 需求规格

### 3.1 提示词重写（治"倾向"）

把表情相关的说明从 `qq_send` 的中段**抽出来，放到 description 靠前的位置**，
并改成正向、主动的表述。

**改法**：在 `qq_send` description 里，把现在那段替换成下面这段，
位置提到「你不一定非得开口」之前（即 description 前 1/3）：

```
表情：真人聊天会发表情。当你这句话带着明显情绪（好笑、无奈、委屈、得意、无语），
或对方刚发了个表情包，先调 qq_face_pick 看看收藏夹里有没有合适的；
有就带上，没有就算了 —— 不要为了用表情而用表情。
经典小表情（[表情:呲牙] 这类）是另一条路，没有合适收藏时可用。

⚠️ 表情参数填错不会让文字发不出去：匹配不上时只跳过表情，话照发。
```

要点：

- **正向表述**：给具体情绪场景（好笑/无奈/委屈/得意/无语），不要说"需要时"
- **给一个动作**：`先调 qq_face_pick` —— 把"想一想"变成"查一下"
- **明确容错**：告诉它"填错不会连累文字"，消除 §2.2 的负向强化
- **防滥用**：「不要为了用表情而用表情」

### 3.2 新增工具 `qq_face_pick`（治"看不见收藏夹"）

这是本次的核心改动。一个**只读**工具，让模型能按情绪挑表情。

```
name: 'qq_face_pick'
description:
  '挑一个收藏表情 —— 按情绪/场景从 QQ 收藏夹里找一张合适的图，只返回候选，不发送。'
  + '\n\n什么时候用：这句话带着明显情绪，或对方刚发了个表情包，你想回一个。'
  + '\n\n用法：给一个短描述或 2-4 个关键词（如「委屈 撒娇」「无语」「好笑」），'
  + '它会把收藏夹里最像的几个列出来，你挑一个再传给 qq_send 的 custom_emoji。'
  + '\n\n不给关键词就列出全部收藏（最多 30 个）。'
  + '\n\n⚠️ 它只查不发。要真发出去，把选中的名字传给 qq_send 的 custom_emoji。'

parameters:
  query: string  可选；情绪/场景关键词，空格分隔
  limit: number  可选；最多返回几个，默认 5，上限 10

output:
  { ok, count, faces: [{ name, emoji_id, score }], message }
```

实现要点：

- 复用 `listCustomFaces(100)` 和 `findCustomFace` 的**打分逻辑**，但**返回前 N 个**而不是只返回第一个。
  → 需要在 `lib/custom-faces.js` 新增 `rankCustomFaces(keyword, limit)`，
   把 `findCustomFace` 内部的 `ranked` 数组暴露出来（现有函数改成调它，保持行为不变）
- **不传 query 时**：返回全部（最多 30），`score` 统一为 0
- **无匹配时**：`ok: true, count: 0`，`message` 说明"收藏夹里没有匹配的，可用经典小表情"
  —— **不要 `throw`**，这是查询不是命令
- 收藏夹为空时：`ok: true, count: 0`，`message` 提示"收藏夹是空的"

### 3.3 `qq_send` 的 `custom_emoji` 匹配失败要降级（治 §2.2）

**这是行为变更，需要明确决策**：现在 `throw`，改成**跳过表情、文字照发**。

```js
// 现在
if (found === null) throw new Error(...)

// 改成
if (found === null) {
  note('tool', `收藏表情「${customEmojiName}」没匹配到，跳过表情只发文字`)
  customEmojiMissed = customEmojiName   // 用于返回值告知模型
}
```

返回值里带上 `custom_emoji_missed`，让模型知道"这次表情没发出去"，
而不是让整句话失败。

⚠️ **必须保留可观测性**：日志里要有一行，返回值里要有一个字段。
静默降级是这个仓库的典型事故来源（见 `docs/踩坑记录.md` 的「假成功/静默降级」）。

⚠️ **`output.render` 要提示**：让模型看到"表情没匹配上，文字已发"，
否则它会以为表情发出去了。

### 3.4 收藏备注的质量（治"猜不中"）

`findCustomFace` 完全靠 `desc` / `summary` 关键词匹配（`lib/custom-faces.js:83-111`）。
如果收藏时备注只有名字没有情绪词，按情绪搜必然落空。

`qq_collect_face` 的 `desc` 参数说明（`lib/tool.js:622`）已经要求
「简短名称 | 2-4 个关键词」，但**没有强制**。

**改法**（二选一，建议选 A）：

- **A（推荐）**：收藏时如果 `desc` 不含 `|` 分隔符，在返回值 `message` 里
  **提醒一句**「建议补上关键词，方便以后按情绪找到它」。不阻断。
- **B**：给已有收藏做一次批量"补关键词"—— 太重，不做。

同时 `qq_face_pick` 的返回里，对 `desc` 为空的项标注 `（无关键词）`，
让模型知道这类不好搜。

### 3.5 不需要改的部分（别动）

- `findCustomFace` 的**打分算法本身**（`custom-faces.js:93-108`）是合理的，
  只是没人调它。别改权重。
- 经典小表情那条路（`resolveFaceIdSafe` / `emoticons.js` / `sys-faces.js`）完全不动。
- `qq_collect_face` 的收藏逻辑不动（只按 3.4 加一句提醒）。
- 收藏夹的存储格式不动。

## 11. 已知坑（先看，省时间）

1. **收藏表情必须是单独一条消息** —— 协议端 `send_custom_face` 是独立 action，
   不能跟文本拼进一个 `message` 数组。`custom-faces.js` 顶部注释写得很清楚。
2. **`fetch_custom_face_detail` 是 SnowLuma 扩展**，不是 OneBot 11 标准。
   换协议端可能没有 —— 所有调用都要能优雅降级成空列表（现有代码已经这样做了，别破坏）。
3. **`throw` 会让整次 `qq_send` 失败** —— §3.3 就是要改掉这个。
   但注意：`text` 为空且只有表情时，如果表情也失败了，那就真的什么都不发 ——
   这种情况要 `throw`（没内容可发是错误），别静默成功。
4. **`output.render` 的文案会被模型读到** —— 写"表情没匹配上"时不要写成一句像聊天的话
   （参考另一个任务里"判断结论被复述"的教训），用 `[系统]` 之类的前缀区分。
5. **README 有 `readme-sim` 校验** —— 新增工具必须同时改 **README + `tests/readme-sim.mjs`**，
