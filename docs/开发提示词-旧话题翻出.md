## 0. 一句话

`@` 之后的连续对话，本意是「此后几轮不用再 @ 也能聊」。
但对方**持续 @ 或间歇 @** 时，一些不带 @ 的句子会堆在队列里，
等当前这轮结束后才成批投递 —— 于是模型看到一批**属于几轮之前的旧话**，
接着旧话题往下聊，看起来莫名其妙。

**这是缺陷修复，不是新功能。**

## 2. 背景：为什么会翻出旧话题

### 2.1 两条投递路径的节奏完全不同

`handleGroupMessage` 里有两条互斥的路：

```js
// lib/poll.js:510-515 —— 不带 @ 且窗口内 → 进队列，等攒批
if (!atMe && inWindow) {
  const queued = enqueueWindowMessage(groupId, message)
  if (!queued) return { status: 'skipped' }
  touchWindow(groupId, seqOf(message))
  note('window', `queued ${groupId} seq=${seqOf(message)}`)
  return { status: 'queued' }
}

// lib/poll.js:529 之后 —— 带 @ → 直接投递，立刻唤醒
```

| 消息类型 | 路径 | 什么时候到模型 |
|---|---|---|
| **带 @** | 直接 `deliver()` | **立刻**（`agent.followup` 是同步唤醒，`deliver.js:136`） |
| **不带 @（窗口内）** | `enqueueWindowMessage` | 攒够 **3 条** 或等满 **8 秒** 才成批投递 |

### 2.2 于是产生了"时间错位"

模拟真实场景（对方持续 @）：

```
t=0s   对方: @她 你觉得 A 怎么样          → 直接投递 ✅ 模型开始回 A
t=1s   对方: 我觉得 A 还行                → 进队列 (pending=1)
t=2s   对方: 不过 B 更重要                → 进队列 (pending=2)
t=3s   对方: @她 那 B 呢                  → 直接投递 ✅ 模型开始回 B
t=8s   批次到期 → 把「A 还行」「B 更重要」一起投给模型
        ↑ 但模型这时候已经在聊 B 了，突然收到两条关于 A 的旧话
```

模型看到的是「对话窗口批次」里两条关于 A 的话，而它刚在 B 上——
于是它**把话题拉回 A**，或者把 A 和 B 混在一起答。用户看到的就是"莫名其妙地继续一个旧话题"。

### 2.3 为什么 8 秒攒批在这里是错的

`WINDOW_BATCH_MS = 8000` / `WINDOW_BATCH_MAX = 3` 的设计意图是
**「对方连着打几句，攒起来一起投，别一句一个回合」**（见 `docs/对话窗口-设计稿.md`）。
这个意图在"纯续聊"（没有新 @ 打断）时是对的。

但它没考虑**@ 会插队**：@ 走直达路径，等于在队列前面不断插入新话题，
而队列里的旧话还在按自己的 8 秒计时器等着。**两条路径没有任何顺序协调。**

### 2.4 关键约束：`deliver` 没有串行化

`lib/deliver.js:136` 是 `agent.followup(...)`，**同步调用，没有锁、没有队列**。
所以两条路径并发时，到达模型的顺序完全由时序决定，不由 seq 决定。

这意味着：**光在批次里加"这是旧消息"的标注是不够的**，
必须真的让旧消息不要在新 @ 之后才到。

## 3. 需求规格

### 3.1 核心原则：@ 是"话题边界"，它之前的待投消息必须先投完

这是本次最重要的一条规则：

> **当一条 @ 到达时，如果该群还有 pending 的窗口消息，先把 pending 投出去，再投这条 @。**

理由：pending 里的消息 seq **一定小于**这条 @ 的 seq（它们先到的）。
按 seq 顺序投递是唯一能让模型不困惑的顺序。

⚠️ 但这会带来一个新问题：**开窗 @ 的情况**。
第一条 @ 开窗时 pending 必然是空的（`openWindow` 里 `clearPending`），所以不受影响。
而 0.16.12 加的 `batchHolds` 门控正是处理"开窗 @ 还没投完，续聊已经进队列"的情况——
两者要**协同**，不能打架。见 §3.4。

### 3.2 具体做法：@ 到达时先 flush pending

在 `handleGroupMessage` 里，`atMe && inWindow`（即：窗口已开、这条是 @）的分支，
在 `deliver` 之前插入：

```js
// 伪代码，位置在 lib/poll.js:529 附近、真正 deliver 之前
if (atMe && win !== null) {
  await flushPendingBeforeAt(ctx, groupId)
}
```

`flushPendingBeforeAt` 的职责：

1. 若 pending 为空 → 立刻返回（零开销，绝大多数情况）
2. 若 `batchHolds` 有该群的门控 → **不 flush**（那是开窗 @ 的门控，
   属于 0.16.12 的既有语义，别抢它的活）
3. 否则：取走 pending，调用现有的 `deliverWindowBatch`，成功则从 pending 移除，
   失败则保留（不阻塞这条 @，但要记日志）

⚠️ **失败不阻塞**：如果 pending 投递失败，**不要**让这条 @ 也失败。
@ 是用户明确在叫她，必须优先保证。pending 留着下轮重试。

### 3.3 批次正文要标明"这是刚才的，不是现在的"

即使做了 §3.2，仍可能有 pending 在新 @ 之后投出去的情况（比如 @ 来得太快）。
所以批次正文的头部要改。

现在（`lib/poll.js:706`）：

```
（QQ群 123「群名」·对话窗口批次）

[这段时间的群聊]
```

**改成**：

```
（QQ群 123「群名」·对话窗口批次）
（这是刚才攒下的 N 条，时间跨度 X 秒；如果你已经在聊别的话题，这些可能已经过时，优先回最新的）

[这段时间的群聊]
```

`X` 用 `pendingSince` 算：`Math.round((Date.now() - pendingSince) / 1000)`。

理由：给模型一个**显式的判断依据**，而不是指望它从时间戳自己推。
这条即使 §3.2 生效了也该保留 —— 它是兜底。

⚠️ 措辞要克制：不要写成"这些已过时，请忽略"（那会让模型直接丢弃有效内容），
而是"可能已经过时，优先回最新的"。

### 3.4 与 0.16.12 的门控协同（关键，别搞坏）

0.16.12 引入了 `batchHolds`：开窗那条 @ 投递完成前，批次不 flush。
`shouldFlush` 里有这段：

```js
function shouldFlush(key, now) {
  const hold = batchHolds.get(key)
  if (hold !== undefined) {
    if (now - Number(hold.at) < OPENING_HOLD_TTL_MS) return false
    releaseOpeningHold(key)
    note('window', `opening hold expired group=${key}; releasing batches`)
  }
  // ...
}
```

**协同规则**：

- `flushPendingBeforeAt`（§3.2）必须**先检查 `batchHolds`**，有门控就跳过。
  否则会出现：开窗 @ 还没投完，它自己触发了一次 flush —— 顺序又反了。
- 建议在 `lib/window.js` 导出一个小函数 `hasOpeningHold(groupId)`，
  让 `poll.js` 能干净地问一句，而不是直接摸内部 Map。

### 3.5 考虑：是否缩短 `WINDOW_BATCH_MS`？

**建议不改。** 8 秒的意图是"别一句一个回合"，这个意图是对的。
真正的问题是 @ 插队，靠 §3.2 解决。

如果你实测发现 §3.2 之后仍有明显错位，可以再考虑降到 4-5 秒，
但**要先报告**，因为那会改变"攒批"的手感（模型会更频繁地被唤醒、更碎）。

### 3.6 边界：什么时候**不** flush

- pending 为空 → 不 flush（零开销）
- 有开窗门控 → 不 flush（§3.4）
- 正在 `flushing` 该群 → 不 flush（`flushDue` 已有这个保护，复用即可）
- 私聊路径 → 完全不涉及（`handlePrivateMessages` 里没有窗口）

## 11. 已知坑（先看，省时间）

1. **`deliver` 没有串行化** —— `agent.followup` 是同步唤醒（`deliver.js:136`）。
   两条路径并发时到达顺序由时序决定。这是本缺陷的根源，也是为什么 §3.2 必须
   **真的等 pending 投完**，而不是加个标注了事。
2. **`window.js` 不能 import `poll.js`** —— `window.js:4-6` 的注释说明了原因（循环依赖）。
   所以 §4.2 的 `flushPendingNow` 只负责"取走"，投递由 `poll.js` 做。
3. **`flushDue` 有 `flushing` 保护** —— 同一个群不会并发 flush。
   你的 `flushPendingBeforeAt` 也要尊重它，否则两个 flush 会同时跑。
4. **`pendingSince` 的语义是"这批的第一条进队列的时间"** —— 不是最后一条。
   §3.3 的秒数按它算是对的（跨度）。
5. **`takeWindowMessages` 会真的移除，但它绕开门控，别用于批次投递** ——
   它直接从 pending 取走，不经过 `shouldFlush`。现有 `flushDue` 用的是
   `windowMessages`（快照）+ 成功后按引用剔除，走的是门控那条路。
   你实现 §3.2 的 `flushPendingNow` 时，**必须复用 `flushDue` 的写法**
   （快照 → 投递 → 按引用剔除 → 失败回填），而不是调 `takeWindowMessages`，
   否则会静默绕开 0.16.12 的开窗门控。
6. **0.16.12 的 `batchHolds` 用 id 精确匹配** —— 见 `openingIdOf` 的注释。
   你在 §3.4 只读不问 id，用 `hasOpeningHold` 就够。
7. **`windowEnabled=false` 时整条窗口链路都不该被触发** —— 检查 `windowMode` 的判定。
8. **不要在 `sendToQQ` 里计回复数** —— 分条会发 3 次。
