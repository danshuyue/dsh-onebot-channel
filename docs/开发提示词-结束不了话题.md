**这是缺陷修复，不是新功能。**

## 2. 背景：现在为什么结束不了

### 2.1 三个工具的真实语义

| 工具 | 实际行为 | 关不关窗口 |
|---|---|---|
| `qq_send` | 把话发出去 | 不关 |
| `qq_pass` | `suppress()` 一次 + `notePass()`；两次连续 pass 才关窗 | 需连续 2 次 |
| `qq_close` | `saveClosing()` + `closeWindow()` | **关** |

也就是说：**唯一能立刻关窗的出口是 `qq_close`**。

### 2.2 `qq_close` 在最该成功的时候最容易失败

`lib/tool.js:1034-1042`（`closureEnabled` 开着时）：

```js
const verdictResult = assessClosure({ mine, theirs })
if (verdictResult.openQuestion) {
  return {
    ok: false,
    closed: false,
    verdict: '对方还在问/还在求，这会儿不能收摊 —— 先把话说完再说',
    score: verdictResult.score,
    reasons: verdictResult.reasons
  }
}
```

注意这是 **`return` 一个结果对象，不是 `throw`**。工具调用成功返回，
模型拿到的就是一段文字：`对方还在问/还在求，这会儿不能收摊 —— 先把话说完再说`。

### 2.3 于是判断结论被当成了话

模型拿到这段返回值后，有两种常见走法，**都不对**：

1. 它把「这段话」理解成「我该说的内容」，写进正文 → 自动转发链把这个元判断发到 QQ 上。
   用户看到的是"她把自己该不该结束的纠结念出来了"。
2. 它理解成「我还不能停」，于是继续找话聊 → 话题被强行续命。

更糟的是 §2.4。

### 2.4 对端也是 AI 时的死循环

对端 AI 收到「我是不是该结束了…」这类元话语，会顺着这个层面回应（"那我们下次再聊"、
"你先忙吧"之类的元讨论），于是：

```
A: 那我就先不打扰了
B（她）: 对方还在问，这会儿不能收摊 —— 先把话说完再说   ← 判断结论被发出
A: 好的，那我不问了，先这样吧                          ← 对端顺着元讨论回应
B（她）: （同上，再次把判断念出来）
→ 无限循环，谁都不肯先停
```

`assessClosure` 的 `openQuestion` 硬规矩在这里起了反作用：只要对端还在说话
（哪怕是「好的」这种附和被误判成 question），她就永远收不了，只能不停把判断念出去。

### 2.5 为什么「没 @ 结束话题」会走到这条路

用户不 @ 时，消息走窗口批次路径（`poll.js:510` 的 `enqueueWindowMessage`），
攒批后投给模型。模型这一回合的出口只有三个工具。
它想表达"聊完了"时，最自然的选择就是 `qq_close` —— 于是撞上 §2.2。

## 3. 需求规格

### 3.1 硬规矩：判断结论绝不允许出现在正文里

这是本次的**第一优先级**。不只是 `qq_close`，任何工具返回值里的元判断都不该被模型复述。

两条独立的防线，**都要做**：

**防线一（工具侧）：`qq_close` 拒绝时不返回"话"，只返回"状态"**

- `ok: false` 时，`verdict` 字段改成**短状态码**而不是自然语言句子。
  例如 `'open-question'`，配合 `reasons` 数组给结构化理由。
- 自然语言解释放进 `output.render` 里，用**方括号包住**并以极简形式呈现，
  让模型一眼看出「这是系统状态，不是我要说的话」。例如：
  `[系统] 未收摊：对方还有未闭环的问题`。
- 关键：`render` 出来的文本必须**明显不像聊天内容**。方括号 + 「系统」前缀是
  这个仓库既有的约定（见 `[这段时间的群聊]`、`[转发消息]` 的用法）。

**防线二（出站侧）：`qq_close` 这一回合的正文要过一道闸**

- `qq_close` 成功或失败后，给该 target 打一个标记（复用 `rhythm.js` 的
  `suppress` 机制即可，它本来就是"这回合别转发"）。
- `outbound.js` 的 `flushOutbound` 里，`consumeSuppress` 命中后**保持现有行为**
  （正文写了真话照发 —— 这是 0.16.x 的既有决策，别改，有测试钉着）。
- 但新增一条：如果本回合调用过 `qq_close` 且**失败**，则这一回合的正文
  即便是「真话」也不转发，只记日志。理由：失败意味着模型处在"判断模式"，
  它输出的东西大概率是元话语。
  ⚠️ 这条要**慎重**：不能吞掉用户真正需要的话。所以只拦「调用过 qq_close 且
  返回 `ok: false`」这一种组合，其余一律照旧。

### 3.2 `assessClosure` 的判定要修：别把附和当成"还在问"

`lib/closure.js:56` 的 `QUESTION_RE`：

```js
const QUESTION_RE = /[?？]$|(?:吗|呢|吧)$|怎么|怎么办|怎么样|是什么|为什么|是不是|能不能|有没有|要不要|可不可以|几点|多少|多久|还得|是谁|哪|谁/
```

问题在 `(?:吗|呢|吧)$` 这条：**「好吧」「行吧」「这样吧」全被判成 question**，
于是 `openQuestion = true` → 硬规矩生效 → 永远收不了。

实测会踩到的误判（**已在 0.16.12 上跑过，结果如下，请照此写测试**）：

| 输入 | 当前判定 | 应该是 |
|---|---|---|
| `好吧` | `question` ❌ | `ack` |
| `行吧` | `question` ❌ | `ack` |
| `就这样吧` | `question` ❌ | `ack` |
| `随你吧` | `question` ❌ | `ack` |
| `好的` | `ack` ✅ | `ack` |
| `嗯嗯` | `ack` ✅ | `ack` |
| `晚安` | `ending` ✅ | `ending` |
| `那先这样` | `ending` ✅ | `ending` |
| `好吧，那我先睡了` | `ending` ✅ | `ending` |

**根因**：`QUESTION_RE` 里那条 `(?:吗|呢|吧)$` 把**所有以「吧」结尾的句子**都算成疑问。
而中文里「吧」绝大多数是附和/让步（好吧、行吧、就这样吧），不是提问。

**修法**：把 `吧$` 从 `QUESTION_RE` 拿掉，改成 `(?:吗|呢)$`。
「吧」结尾的句子自然落进 `ack`（长度 ≤ 8 且在 `ACK_WORDS` 里）或 `substantive`。

⚠️ **反向保护（改完必须验，这是最容易翻车的地方）**：

真疑问靠的是疑问词，不是「吗/呢」结尾。以下是当前**已经是** `question` 且**必须保持**
`question` 的用例 —— 它们在改 `吧` 规则后不会受影响，但仍要写进测试防止误伤：

- `怎么办`（靠 `怎么办` 命中）
- `你说呢`（靠 `呢$` 命中）
- `要不要来`（靠 `要不要` 命中）
- `是不是真的`（靠 `是不是` 命中）
- `能不能帮我看下`（靠 `能不能` 命中）

另外这条**当前就是错的**，顺手一起修（可选，但建议）：
`什么时候走` 现在判成 `substantive` —— 因为 `QUESTION_RE` 里只有 `是什么`，没有 `什么`。
建议加 `什么时候` 到疑问词表。不修不算缺陷（`substantive` 不会触发 `openQuestion` 硬规矩），
但会影响 `topicClosure` 打分。

### 3.3 给她一个"说完就走"的出口

现在 `qq_pass` 要连续 2 次才关窗（`WINDOW_MAX_PASSES = 2`），
`qq_close` 又被 `openQuestion` 卡住。结果是**想停的时候没有可用工具**。

新增规则（改 `notePass` 或加新函数，二选一，见 §4.3）：

- 如果模型在**同一个回合**里既表达了收尾（`qq_send` 发了收尾式语句，或 `qq_pass`），
  又调用了 `qq_close`，那么即使 `assessClosure` 说 `openQuestion`，
  **也允许关窗** —— 只是不记 `saveClosing`（因为不算真正闭环）。

理由：`openQuestion` 的设计意图是"别为了收尾而丢下没答的问题"（见 `closure.js:14` 的设计红线）。
但如果模型主动调了 `qq_close` 且同回合还说了话/划走了，说明它已经处理过了。
替她把门，不该替她把自己锁在屋里。

### 3.4 连续收尾失败要给退路

如果同一个窗口内 `qq_close` 连续失败 N 次（建议 N=3），
自动关窗并把原因记进日志（`closeWindow(groupId, 'close-refused-x3')`）。

理由：防止 §2.4 的死循环。宁可这次收得不体面，也不能无限转。

### 3.5 提示词要改（这是"概率"的直接来源）

`qq_close` 的 description（`tool.js:967-976`）现在写的是：

> 不用它的情况：**对方还在问你、还在求你办事** —— 这时候先回答，
> 桥接会直接拒绝这次收尾（不是信你，是替你把门）。

问题：它把"会被拒绝"讲得太清楚了，模型反而会**先去试探**（调一次看看会不会被拒），
失败后拿到那句话，就开始元讨论。

**改法**：把"会被拒绝"的表述从 description 里**删掉**，改成正向指导：

> 不用它的情况：对方还在问你、还在求你办事 —— 这时候先回答。
> 工具会告诉你现在还不能收；**那是状态提示，不是要你说的话，别把它写进正文。**

第二句是关键：显式告诉模型"这不是话"。

同时 `qq_pass` 的 description 要补一句收尾用法：

> 想结束话题但不确定该不该收尾时，用 qq_pass 划走，别为了凑一句而硬聊。

失败计数用模块内的 `Map`，进程重启就清零，这是**可接受**的
（重启后重新数三次，不影响正确性）。

## 11. 已知坑（先看，省时间）

1. **`loadState()` 会吃掉 `windows` 里的新键** —— 见 §6。这是最容易静默翻车的地方。
2. **`throw` 比 `return ok:false` 更糟** —— `throw` 会让 DSH 把整轮判成错误，
   模型拿到的错误信息更容易被它复述。**本任务全程用 `return`**。
3. **`describeClosure` 有测试依赖** —— 别删，新增一个函数。
4. **改 `QUESTION_RE` 极容易误伤** —— 那个正则同时被 `classifyUtterance` 的
   question 判定和 `assessClosure` 的 `openQuestion` 用。改完必须跑反向用例。
5. **`suppress` 是一次性消费** —— 别指望它留到下一回合；`consumeSuppress` 命中即删。
6. **窗口批次也走 `deliver`** —— 会带记忆卡和收尾提示，别自己拼正文绕过。
7. **`noteReply` 计的是"她说了几句"** —— 不要在 `sendOneToQQ` 里计数（分条会重复）。
