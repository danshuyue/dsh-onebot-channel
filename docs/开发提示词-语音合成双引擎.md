## 2. 四档到底控制什么（最容易理解错的一节）

### 2.1 四档 = 提示词 + 工具可见性的组合，不是运行时代码判断

这是本设计的核心。**不要**在 `qq_tts` 或 `qq_send` 里写
`if (mode === 'active') { 强制语音 }` —— 那个判断做不对，因为
「这句话适不适合用语音」是语义问题，代码判不了。

正确做法：**四档决定两件事**

| 档 | `qq_tts` 工具是否注册 | 系统提示词怎么说 |
|---|---|---|
| 禁用 | ❌ **不注册**（模型根本看不到这个工具） | 不提语音 |
| 被动 | ✅ 注册 | 「除非对方明确要求你说出来／发语音，否则不要用」 |
| 自由 | ✅ 注册 | 「你自己判断该不该用语音 —— 长句、有情绪、想被听见的时候可以；一两句能说完的事打字更合适」 |
| 主动 | ✅ 注册 | 「尽量都用语音说，除非对方要求文字、或者这句话不适合念出来」 |

**为什么「禁用」要多一步「不注册」**：仓库里已经踩过这个坑（`tool.js:251-253` 的注释）——
「留着参数、调用时报错」会让模型反复试、白烧 token。
**参数不存在，它根本不会想到去传。** 这条纪律对工具本身同样成立。

### 2.2 「禁用」时 `qq_send` 的 `voice` 参数也一起消失

现在 `voice` 参数由 `features.voiceOut` 控制。改成由四档控制：
**只有「禁用」档把它从 schema 里摘掉**，其余三档保留
（因为 `qq_tts` 产出的路径要靠它发出去，而且第 4 条定论说「不拦 MCP」——
模型自己调 MCP 拿到路径也得能发）。

⚠️ 但「三档都保留 voice 参数」会遇到一个真实问题：
**「被动」档下模型如果从别处搞到一个 wav 直接发，就绕过了四档限制。**
这是可接受的 —— 用户第 4 条明确说「只是默认引擎，不拦 MCP」。
如果要拦，得在 `sendVoiceToQQ` 里加档位判断，那会把「不拦」变成「拦」。
**不做。** 记在这里备查。

### 2.3 四档与名单的关系

```
能不能发语音 = 四档 ≠ 禁用  AND  当前对话对象在名单里
```

名单**只对「插件自己的 TTS 产出」生效吗？不。** 名单是「能使用语音的对象」，
`qq_tts` 和 `qq_send(voice=)` 都该查。

⚠️ 但名单查在哪儿会决定实现复杂度：
- 查在 `qq_tts`：合成阶段就拒，省一次 API 调用（**省钱**，选这个）
- 查在 `qq_send`：要动 `voiceout.js` 的主链路（风险大）

**只在 `qq_tts` 查。** `qq_send` 不动。
理由：`qq_tts` 是「花钱的那一步」，闸就该设在这里；而 `qq_send` 已经有
白名单（`allowlist.js`）挡着，不是敞开的。

### 3.2 删除的配置项

| 键 | 处置 | 理由 |
|---|---|---|
| `toolFeatures.voiceOut` | **删** | 被四档取代（用户第 15 条） |
| `voiceOutputDir` | **保留** | 仍是信任根，`voiceout.js` 靠它做 containment。用户说的「取代」指旧开关语义，不是删目录 |

⚠️ **迁移**：老配置里 `toolFeatures.voiceOut === true` 的用户，升级后应该得到

### 3.3 为什么没有 `voiceBreezeGuidance` / `instructions` 之类

Breeze 有 `instructions`（表演指令）和 `guidance_scale`（贴合强度）。
**本次不暴露。** 理由：

- QQ 聊天的语音是「顺口说一句」，不是配音。写表演指令属于过度设计
- 每多一个旋钮，模型就多一个填错的机会
- 想要表演感的人会去用 Breeze 官网的 Studio

留给以后。真需要时加两个字段就行，不影响现有结构。

## 4. 新模块：`lib/tts.js`

### 4.1 职责

**只做一件事：文本 → 本地音频文件路径。** 不发送、不管名单、不管额度。

```
qq_tts(text, engine?)
   ↓
   ├─ 档位检查（'off' 时工具根本没注册，这里是二道保险）
   ├─ 名单检查（目标不在名单 → 拒）
   ├─ engine = 参数 或 配置默认
   ├─ 串行队列（全局一个，Free 档并发 1）
   ├─ 额度检查（仅 breeze）
   ├─ 分支合成
   │    ├─ gptsovits → POST 9872（复用 MCP 的 payload 形状）→ 拿 wav 字节
   │    └─ breeze     → POST api.breeze.blue → 拿 wav 字节
   ├─ 内容审计（复用 sensitive.js，别让凭据被念出去）
   ├─ 落盘到 voiceOutputRoot()（文件名 tts_<时间戳>_<rand>.wav）
   └─ 返回 { ok, path, bytes, engine, ms, chars }
```

### 4.2 为什么不写在 `voiceout.js` 里

`voiceout.js` 已经 392 行，管的是「发」。合成是「造」——
两边共享的只有一个 `voiceOutputRoot()`（信任根）。塞一起会让
「读本机文件」和「写本机文件」两条权限在同一个模块里，审计时说不清。

### 4.3 GPT-SoVITS 那一路的具体形状

**必须照抄 MCP 的 payload**，否则 9872 会以 500 回你（Gradio/FastAPI 对错参数只回 500）。
MCP 的 `build_inference_args()`（`E:\AI\文转语音\gptsovits-mcp\gptsovits_mcp_server.py:305`）
拼的是 23 个位置参数。**施工时照抄，不要凭记忆写。**

参数顺序（实测有效的最小集，来自 MCP 源码）：

```
text, text_lang, ref_audio_path, prompt_text, prompt_lang,
top_k, top_p, temperature, text_split_method, batch_size,
speed_factor, ref_free, seed, parallel_infer, repetition_penalty
```

⚠️ **这一路有真实风险**：MCP 那套参数是 Python 侧维护的，
如果哪天 GPT-SoVITS 升级改了签名，MCP 会跟着改，而插件里这份拷贝不会。
**缓解：把参数表集中在一个常量里，并在合成失败时把服务端原文（含 500 的 body）原样记日志。**

### 4.4 Breeze 那一路的具体形状

见 `docs/调研-Breeze-TTS-API.md` §12.7 的十条硬结论。最关键三条：

1. **`output_format` 在 query，不在 body**（写进 body → 422 `extra_forbidden`）
2. **成功是二进制、失败是 JSON** → 靠 `content-type` 分流，不要 `res.json()`
3. **本地先做 1000 字符校验**，别等 422 白跑一次网络

```js
const url = `https://api.breeze.blue/v1/text-to-speech/${encodeURIComponent(voiceId)}`
          + `?output_format=${encodeURIComponent(format)}`
const res = await fetch(url, {
  method: 'POST',
  headers: { 'xi-api-key': key, 'content-type': 'application/json' },
  body: JSON.stringify({ text, language_code: 'zh', ...(model ? { model_id: model } : {}) }),
  signal: AbortSignal.timeout(30000)   // 1000 字实测 5.8s，15s 会误杀（见 §12.5 的 12s 观测）
})
```

### 4.5 串行队列（Free 档只能 1 条并发）

```js
let chain = Promise.resolve()
let pending = 0
const MAX_PENDING = 3

function enqueue(task) {
  if (pending >= MAX_PENDING) throw new Error('语音合成排队太长了（一次最多 3 条），等一等再要')
  pending++
  const run = chain.then(task).finally(() => { pending-- })
  chain = run.catch(() => {})     // 失败不能卡死队列
  return run
}
```

⚠️ **`chain = run.catch(() => {})` 这一行是关键**：不加的话，
一次失败会让整条链变成 rejected，之后所有合成全部瞬间失败。
这是 Promise 链队列的经典坑。

⚠️ 队列**只管 Breeze 吗？** 不。两条路都排 —— 9872 是单进程 `uvicorn`（`workers=1`，
见 `GPT-SoVITS-api-v1-接口文档.md` §0），并发打过去一样会排队甚至 500。

## 5. 新工具：`qq_tts`

### 5.1 什么时候注册

`lib/index.js`，紧挨着现有的 `if (features.voiceIn) registerVoiceTool(...)`：

```js
// 语音合成：四档里只有「禁用」不注册
if (config.voiceMode !== 'off') void registerTtsTool(ctx, toolRegistration.signal)
```

⚠️ 顺序问题：`config` 在 `apply` 里读一次就固定了，改档位要**重启 DSH**。
这和现有 `toolFeatures` 的纪律一致（`client.js:593-597` 已经写明）。
**设置页必须同样写「要重启」。**

### 5.2 schema

```js
{
  name: 'qq_tts',
  description:
    '把一段文字合成为语音文件，返回一个本机路径 —— 再把这个路径填进 qq_send 的 voice 参数才会真发出去。'
    + '\n\n这是一条独立的路：它只负责"造出声音"，发不发、什么时候发由你自己决定。'
    + '\n\n什么时候用：'
    + '\n· 这句话你想让人"听见"而不是"读到"—— 长句、有情绪、想被记住的话'
    + '\n· 对方明确要求你说出来'
    + '\n\n不要滥用：一两句能说完的事打字更合适，语音在群里是「冒头」的动作。'
    + '\n\n' + engineHint,     // ← 按当前引擎动态拼，见下
  parameters: {
    type: 'object',
    properties: {
      text: {
        type: 'string',
        description: '要念出来的字。上限 ' + limit + ' 字（引擎硬限，超了会被拒，请自己缩写）。'
      }
    },
    required: ['text']
  }
}
```

### 5.3 `engine` 参数**不给模型**

用户第 2 条：「配置里选定一个默认引擎，模型无感」。
所以 schema 里**没有** `engine` 字段。模型只说「我要这段声音」，
走哪家由配置决定。

⚠️ 这带来一个真实限制：**模型没法在「这句值得花钱」和「这句随便念念」之间选**。
用户认了这个（他要的就是「无感」）。记在这里，将来想改时知道从哪改。

### 5.4 `engineHint` 按引擎动态拼

| 引擎 | 拼进 description 的话 |
|---|---|
| gptsovits | `用的是本机 GPT-SoVITS（免费，不走网络）。` |
| breeze | `用的是 Breeze 商业接口，按字数计费 —— 有每日额度，用完当天就没了，别浪费。` |

**为什么要说「计费」**：模型不知道这事就会乱用。这不是提示词洁癖，
是省钱。

### 5.5 输出

```js
// 成功
{ ok: true, path: 'D:\\...\\tts_20261107_004512_a3f2.wav', engine: 'breeze', chars: 21, ms: 2866 }
// 失败（不抛 —— 让模型看见原因）
{ ok: false, error: '今天 Breeze 的语音额度用完了（1000 字/天），可以改用本机引擎或等明天' }
```

⚠️ **失败一律不抛**，理由同 `voice.js:47-49`：抛错会被宿主翻成一条没有上下文的
`ToolError`，模型不知道该怎么应对。

## 6. 设置页（`lib/client.js`）

### 6.1 新增分区「语音」

现有 7 个分区：`overview / binding / stance / proactive / memory / ws / advanced`。
插在 `memory` 和 `ws` 之间 —— 它在逻辑上属于「行为」而不是「连接」。
（`client.js:280-286` 的数组要同步改。）

### 6.2 四档控件（必须是 radio，不是 select）

理由：四个档位各有长文案，`<select>` 的下拉里塞不下，而且
「悬浮说明」在 `<option>` 上不生效（浏览器限制）。

```
○ 禁用        这个模式下ai无语音工具调用权限，无法发语音
○ 被动        这个模式下除非你要求，否则ai不会发语音
○ 自由        这个模式下ai可以发语音，且直接考虑该不该发语音，实际效果可能和被动模式类似
○ 主动        这个模式下ai将尽可能全部用语音回复你，除非你要求用文字或者不适合用语音
```

文案**逐字用**（§1.1）。改成 `title=` 悬浮 + 一行摘要也行，
但摘要不能替代原文 —— 用户明确要求「详细举例介绍」。

### 11.3.1 ⚠️ 实测发现：`sensitive.js` 抓不到 Breeze 的 key 形态

**这是本次调研时顺手验出来的真漏洞，施工时必须一起修。**

用真实 key 形态跑 `findSensitive()` 的结果：

| 输入 | 结果 |
|---|---|
| `brz_AAAA1111BBBB2222CCCC3333DDDD4444`（裸 key） | ❌ **漏** |
| `api key: brz_...`（api 和 key 之间有空格） | ❌ **漏** |
| `API KEY = brz_...`（大写 + 空格 + 等号） | ❌ **漏** |
| `key: brz_...` | ❌ **漏** |
| `the api key is brz_...` | ❌ **漏** |
| `apikey: brz_...` | ✅ 抓到 |
| `xi-api-key: brz_...` | ✅ 抓到 |

**两个根因**（看 `lib/sensitive.js:44` 的正则）：

1. 关键词是 `api[_-]?key` —— 只允许 `api-key` / `api_key` / `apikey`，
   **不允许 `api key`（带空格）**。而人写英文时最自然的恰恰是带空格那个。
2. **裸的 `brz_xxx` 完全不在特征库里**。现有正则靠「关键词 + 赋值」匹配，
   没有任何一条能识别 token 本身的形状。

**为什么这次必须修**：本功能一上线，模型手里就有一个 `brz_` 开头的 key，
而它经常在解释「我在干嘛」时顺嘴写出来。这条路径正是 `sensitive.js`
文件头声明的存在理由（「agent 完全可能在回答里顺嘴写出…token 是 xxxx」）。

**建议修法**（最小改动）：

```js
// 1. 允许 api 与 key 之间有空格（不影响「api key 是什么意思」这类正常聊天，
//    因为后面还要求有赋值关系/长串）
+ '|(?:api\\s+key)'
// 2. 加一条独立的 token 形状特征（Breeze 的 brz_ 前缀足够独特，误伤面小）
```

⚠️ 但**别照抄 `/[0-9a-f]{32}/` 那种宽正则** —— `sensitive.js` 文件头明确警告过：
表情包文件名是 MD5、图片 URL 全是十六进制串，宽正则会误伤正常消息。
`brz_` + 32 位字母数字这个组合精度够高，可以单独加。

⚠️ 修完要补测试 `tests/sensitive-breeze-sim.mjs`，至少覆盖上面表格的 7 行，
**并且做变异验证**（把新规则删掉，确认「裸 key」那行变红）。

### 11.3.2 实际修法与第三处漏洞（施工时补充，2026-11-07）

修的时候发现原清单漏了一条，**而且它比前两条更隐蔽**：

| 场景 | 修前 | 说明 |
|---|---|---|
| `the api key is <长串>` | ❌ 漏 | `api\s+key` 后面要求 `[:=：]`／`是/为`，**英文的 `is` 不在其中** |

也就是说：`api key: xxx` 能抓，`api key is xxx` 抓不到 —— 而后者是英文里更自然的写法。

**但修它有个陷阱**：如果只是把 `is` 加进连接词那组，`this key is important to me`
会立刻被误伤（`key` + `is` + `important`，而 `important` 恰好 ≥4 个字母）。
所以 `is` 必须是**单独一条更严的分支**，要求后面跟的是**凭据形状**
（≥16 位字母数字，且不是纯小写单词）：

```js
+ '|\\s+is\\s+["\']?(?=[A-Za-z0-9_-]{16,}\\b)(?=[^\\s]*[A-Z0-9_-])' + ASSIGN_VALUE
```

**这条被变异验证抓出来过一次**：第一版把 `api\s+key` 删掉之后所有测试照样绿 ——
因为 `brz_` 形状规则把带 key 的用例全接住了。所以
`tests/sensitive-breeze-sim.mjs` 的「1b 节」**必须用不带已知前缀的串**
（如 `the api key is qqqqwwwwEEEERRRR1234`）来测，否则测的其实是前缀规则。
