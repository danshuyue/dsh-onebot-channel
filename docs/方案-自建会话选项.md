# 「自建会话」选项 —— 方案（未实现）

> 2026-11-06。用户需求：「绑定中为 qq 绑定会话之外只有未绑定，这就意味着用户需要自己新建会话，
> 新增一个自建会话选项。这个选择会自己绑定下一个生成的会话或者此时如果有 qq 消息，
> 正好是指向这个群或者这个私聊，则创建一个新的会话，默认模型得用户配置，
> 如果用户没配置默认模型就用 DSH 默认模型。」
>
> **本文只出方案，没写一行代码。** 结论在 §6。

---

## 1. 现状

绑定表格的会话下拉现在只有两类选项（`lib/client.js` 的 `renderTable`）：

- `— 未绑定（忽略）—`（值 `''`）
- 现有会话列表（来自 `/api/qq-bridge/state` 的 `sessions`，`sessions.js:listWorkspaceSessions` 合并「活着的 + 扫盘的」）

用户想加第三类：**自建会话**。选了之后不用先去 DSH 手动建一个再回来绑。

---

## 2. 需求翻译成规格

用户那段话有点绕，我拆成三条：

| 编号 | 行为 |
|---|---|
| **A** | 下拉里多一个选项「自建会话」。选中后**不立刻建**，只存一个「待建」标记 |
| **B1** | 之后**下一个生成的会话** → 自动绑给它 |
| **B2** | 或者，此时若正好有 QQ 消息指向这个群/私聊 → **为它新建一个会话** |
| **C** | 新建会话用的模型：用户可配；没配就用 DSH 默认模型 |

---

## 3. 三个硬约束（都是踩过的坑，不是推测）

### ① 插件直接建会话 = 侧栏里看不见

`docs/维护索引.md` 坑 11 原文：

> **新建的会话在侧栏找不到** → `agents.create` 建的会话不登记进 `workspace.json`。
> 修法：**别在插件里建会话**，在 DSH 里建好再回来绑。

`lib/sessions.js` 顶部注释也写着同样的话。**这是当年真实翻车过的地方。**

### ② 群聊换会话 id 会让窗口状态指向错误目标

`docs/开发提示词-跨工作区会话进度.md` §2：

> 群聊切会话会让 `window.js` 的 pending 和 `batchHolds` 指向错误目标。

如果 B2 发生在群里，而那个群正有 pending 攒批中，换 id 会让那批消息投到新会话去。

### ③ 模型配置现在界面上没有控件

`lib/config.js:132` 有 `agentOptions: { provider, model }`，但
`tests/ui-wiring.mjs:139` 把它列进了 `DELIBERATE`：

> `agentOptions: '冷启动的模型选择，属于部署级配置'`

用户这次明确要求「默认模型得用户配置」，所以这条白名单要动。

### ④ 补一条我刚查到的：`inject` 里没有 `workspaceRegistry`

`lib/index.js:78`：

```js
export const inject = ['agents', 'tools', 'webServer', 'llm', 'sessions', 'attachments', 'agentPresets']
```

要真建会话并登记，得加 `workspaceRegistry`。而且**加 inject 是有代价的**：
`lib/index.js` 的注释写着「少一个就会 `without inject` 抛错」，
所以这个服务在旧宿主上不存在时，整个插件会加载失败 —— 不能无脑加。

---

## 4. 两条路线

### 路线甲：只做 B1（绑定下一个生成的会话）

**做法**：
1. 下拉里加一个特殊值，比如 `sessionId: '@new'`（哨兵值，不是真 id）
2. 在投递入口（`deliver.js` 的 `pickSessionId` 之后）检测到哨兵值时，**不投递**，
   记一条 `note('route', '群 975663147 在等一个新会话')`
3. 监听 `agent/created`（或 `sessions.list()` 差分），把第一个新会话绑上并清掉哨兵值
4. 哨兵值要持久化（在 `routes` 里），重启后不丢

**优点**：
- **完全不碰 `agents.create`**，绕开坑 ①
- 不碰 `window.js` 状态机，绕开坑 ②
- 不需要加 `inject`，绕开坑 ④

**缺点**：
- 用户还是得去 DSH 里手动建会话（只是不用再回来绑）
- 这正是用户想省掉的那一步

**B2 的降级版**：检测到哨兵值且有消息进来时，**在 QQ 那头回一句**
「这个群还没绑定会话，去 DSH 建一个，建完自动绑上」。
安全、零风险，但没有真正解决用户的诉求。

### 路线乙：做完整的 B2（收到消息时真建会话）

**做法**：
1. `inject` 加 `workspaceRegistry`（有坑 ④）
2. `agents.create()` 建会话，然后**手动登记进 workspaceRegistry**
3. 群聊场景要处理 `window.js` 的 pending（有坑 ②）
4. 模型配置用 `agentOptions`，界面上加选择器

**优点**：真正满足用户诉求，一步到位。

**缺点 / 风险**：
- **坑 ① 是当年真实翻车的**。要正确登记 workspaceRegistry，得先搞清楚
  它的 v2 数据结构和写入 API —— 而 `lib/archive.js` 的注释写着
  「`ctx.get('workspaceRegistry')` 会直接抛 `cannot get property X without inject`」，
  说明这个服务的用法有门槛
- 加 `inject` 会让插件在**不支持该服务的宿主上直接加载失败**
- 群聊场景要改 `window.js`，那是「入站与对话窗口」的领域，风险最高的模块之一

---

## 5. 我的建议

**分两期：先甲后乙，但甲要先问用户能不能接受。**

理由：
1. 路线乙的坑 ① 是**真的删过数据/丢过会话**的那一类（不是理论风险）。
   要做就得先把 `workspaceRegistry` 的写入方式搞清楚，这本身是一个独立任务。
2. 路线甲能立刻交付「不用回来绑」这个价值的一半，而且零风险。
3. 用户要的「没配模型就用 DSH 默认模型」—— 这条在两期里都要处理，
   但 `agentOptions` 现在是部署级配置，**改成用户可配之前要先确认一件事**：
   界面上的模型列表从哪来？`/state` 里没有 provider/model 目录，
   得新加一个接口去问宿主。这也是一个独立工作量。

**如果只能做一件事**：做路线甲 + B2 的降级提示。
它解决「用户不知道要先建会话」这个信息差（那才是他真正卡住的地方），
而「插件替我建会话」这件事的风险收益比不划算。

---

## 6. 需要用户拍板的问题

1. **接受路线甲吗**（不自动建会话，只在 QQ 里提示你去建，建完自动绑）？
   还是坚持要路线乙（插件替你建）？
2. 如果走乙：**模型选择器放哪个标签页**？「配置」还是「高级」？
   现在 `agentOptions` 是部署级配置，放出来会多一个需要维护的下拉。
3. 如果走乙：**群聊里 pending 攒批中时收到消息**，是拒绝建会话（等这批投完），
   还是把 pending 一起转到新会话？后者会打乱对话顺序。
4. 「自建会话」这个标记，**多久没绑上就自动放弃**？（建议 24 小时，
   否则一个永远不来的会话会让那个群一直哑着）
