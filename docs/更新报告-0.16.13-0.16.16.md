# 0.16.13 → 0.16.16 更新报告

> 一轮修三个用户实测缺陷，外加一轮独立审核后的返工。
> 基线 `0.16.12`（`53ef75e`），终点 `0.16.16`（`3b7a12a`）。
> 三个缺陷来自用户在真实群聊里的观察，不是测试发现的。

## 一、三个缺陷与修法

### 1. 旧话题被翻出来（0.16.13）

**现象**：对方持续 @ 或间歇 @ 时，一些不带 @ 的句子堆在队列里，等当前这轮结束才成批投递 ——
模型一边回新话题、一边收到几轮之前的旧话，接着旧话题往下聊。

**真因**：`@` 走直达路径立刻唤醒模型，而不带 @ 的续聊要等满 8 秒或攒够 3 条才成批投递。
`deliver` 没有任何串行化，两条路径的顺序完全由时序决定。

**修法**：`@` 到达时先把积压投完，再投这条 `@`。投递统一收口到 `window.js` 的
`flushPendingNow`（`flushing` 保护 + 门控判断 + 剔除，三件事在一处），
不让调用方直接调 `deliverWindowBatch` —— 那样两条路会各投一遍同一批消息。

**顺手修的**：`startWindowLoop` 原来不把 handler 记进 `batchHandler`
（`index.js` 是显式传参），所以新加的那行 flush 会**静默不做事**。
这个只有写探针才看得见 —— 测试全绿，缺陷一点没修。

### 2. 从来不发表情包（0.16.14）

**现象**：「依旧没有发收藏表情包的倾向」。用户怀疑是提示词模板。

**实测推翻了「只改模板」**：真实收藏夹 22 个，协议端**不返回 summary**，
22 个里 21 个的 `desc` 是**句子**（「穷光蛋思考中」「拿棒球棍打死，对付油腻男用」）。
按「委屈 / 撒娇 / 无语」去搜，8 次里 6 次落空 —— 而落空时旧代码 `throw`，
**整次 `qq_send` 失败，连话都发不出去**。模型学到的是「别碰 custom_emoji」。

| 改法 | 说明 |
|---|---|
| 降级 | 表情没匹配上只跳过表情、文字照发，返回值 + 日志 + `[系统]` render 三处可观测 |
| `qq_face_pick` | 按情绪列候选，**永不抛错**。把「想一想」变成「查一下」 |
| `qq_face_rename` | **用户提的**：让模型看图自己起名，把句子改成「名称 \| 2-4 个情绪词」 |

第三项是正解 —— 问题不在搜索算法（打分一直是对的），在**标签本身没有可搜的语义**。

### 3. 结束不了话题，还把判断念出来（0.16.15 → 0.16.16）

**现象**：对方想结束话题时她收不了尾，还会把「该不该结束」这个判断本身当话发出去。
对端也是 AI 时两边互相顺着元讨论回，谁都不肯先停。

**三层成因**（0.16.15 修了前两层半）：

1. `QUESTION_RE` 里的 `(?:吗|呢|吧)$` 把「好吧/行吧/就这样吧/随你吧」全判成疑问
2. `qq_close` 拒绝时 `verdict` 返回**一句自然语言**，模型当成「我该说的内容」
3. 被拒回合的正文照常自动转发

**然后发现 0.16.15 整个挂在不成立的前提上**：日志里**从来没有一次真实的 `qq_close` 调用**。
她走的是另一条路 —— 判断该结束 → 没有「不回复」这个出口 → 写一句正文 → 自动转发发出去。

所以 0.16.16 补了真正的出口：**`qq_skip`**（这条不该有回复，本回合正文一律不发），
并修正了提示词里一句**假话**（原文说「你自言自语的正文永远停在会话里」，
而 `flushOutbound` 实际会转发回合最后一条 assistant 正文）。

## 二、独立审核后的返工（0.16.16）

三个子代理分别审了这三轮改动。**发现的问题全部属实**，最严重的几个是我在测试全绿时写出来的：

| # | 问题 | 严重度 |
|---|---|---|
| ① | 我把 `吧$` 从疑问正则删了，**而自己的文档写着「不要删」** → 「这样可以吧 / 对吧」失去疑问保护，可被当成「聊完了」 | 高 |
| ② | 一次性标志在早退分支（`qq_send` 已发过、TTL 丢弃等）泄漏 → **静默吞掉下一回合** | 高 |
| ③ | 提示词里又留了一句假话（「只有参数里的内容才发到 QQ」），与同段前文矛盾 | 高 |
| ④ | `sendCustomFace` 自身失败时**文字已经发出去了**却报整次失败 → 模型可能重发，用户收到两遍 | 中 |
| ⑤ | 「先投积压」加的 `await` 让**并发 @ 顺序反了**（#104 → #103，0.16.12 是 #103 → #104） | 中 |

⑤ 是我自己写并发探针时发现的 —— 单条 @ 的测试、79 条 window-batch 断言全绿，缺陷照样存在。

其余一并修的：`rankCustomFaces` 的 `limit` 下界、`noteCloseRefused` 私聊误报与计数跨窗口残留、
`turnHandled` 缺回合边界（10 分钟内可绕开收尾红线）、两条**空断言/假绿**测试。

## 五、这一轮最值钱的教训

1. **先量一下那条路通不通，再改文案。** 「她不发表情」的三层原因里，提示词只是第三层；
   前两层（标签搜不到、搜不到就整句失败）才是决定性的。
2. **给模型的每一句说明都会被当成事实来推理。** 同一轮里我写错了两句描述系统行为的话，
   两次都让模型形成了错误的心智模型。写提示词时要能对着代码逐字核验。
3. **「在一条路径上加 await」要问一句：这会不会让后来的请求插队？**
   并发顺序问题单线程测试永远抓不到。
4. **自审通过 ≠ 审核通过。** 五个洞里有四个是我测试全绿时写出来的，其中两个我还在文档里
   写了正确结论。测试绿只证明「测到的路径对」。
