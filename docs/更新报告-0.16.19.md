# 0.16.19 更新报告：忙的时候不再排队

更新时间：2026-11-03 19:00（Asia/Shanghai）
基线：`0.16.18`（`3896b26`）→ `0.16.19`（`13d3fb5`）

---

## 一、用户报的现象

> 「会卡排队。排队的消息都是旧的，因为本次会话其实正常的推进且持续回复。」
>
> 「表现为 `qq_wait` 和 `qq_msg_history` 交替工作。就在一个会话中持续对话了。
> 新的 @ 和非 @ 语句在 history 中包含了。而 @ 触发进入了队列中进行排队。」

三句话对应三个事实：

1. **会话在正常跑**（所以不是卡死、不是掉线、不是 outbound 堵住）；
2. **新消息已经在 history 里了**（她自己在回合内查过 `qq_msg_history`）；
3. **`@` 却还在排队**（队列里那些是旧话）。

---

## 二、根因

宿主（`dsh-agent-loop`）的两个入口进的是**两个不同的队列**：

```js
followup(input) { this.send(input, 'next-turn', true) }   // 回合边界认领，一次只认领 1 条
steer(input)    { this.send(input, 'next-step', true) }   // 步骤边界认领，整队全取
```

```js
claim(target, turn) {
  const claimed = this.mutate('next-step', 0, this.nextStep.length, [], false)   // 全取
  if (target === 'next-turn') claimed.push(...this.mutate('next-turn', 0, 1, [], false))  // 只取 1
}
```

而插件**只有一条投递路径**：`agent.followup()`（`lib/deliver.js`）。于是：

```
她一个回合：qq_wait 40s → qq_msg_history → qq_send → qq_wait 40s …
这期间进来的每条消息 → followup → next-turn 排队
回合结束 → 一条开一个新回合 → N 条消息要 N 个回合才清空
```

**双重浪费**：她早在当前回合里用 `qq_msg_history` 看过这几条了（用户原话
「新的 @ 和非 @ 语句在 history 中包含了」），回合结束后又被单独唤醒，
对着同一段已经过时的话再回一遍。

界面上那个「N 条排队消息」就是这套 inbox 的投影 —— 宿主 UI 里 `queue.steer`
的文案「Steering is available only while the agent is running」也印证了
「忙的时候本来就该用 steer」这个设计意图。

### 先排除的三个方向（都不是）

- **outbound 队列堵住**：日志里 `[out]` 没有超时丢条目，`已转发回复` 正常。
- **窗口门控没释放**：`batchHolds` / `openingReservations` 都在正常结算。
- **游标卡住**：`lastDeliveredSeq` 在推进，`skip (no at/window)` 正常刷。

## 三、修复方案

### 3.1 核心：按状态分流（`lib/deliver.js`）

新增 `pushIntoAgent(agent, message, sessionId)`：

```js
if (status === 'running' && typeof agent.steer === 'function') {
  agent.steer(message)     // next-step：当前回合的下一步就交上去，整队全取
  return 'steer'
}
agent.followup(message)    // 空闲：行为与改动前逐字一致
```

| 状态 | 入口 | 进哪个队列 | 什么时候到她手上 |
|---|---|---|---|
| 空闲 | `followup` | `next-turn` | 开新回合（**与改动前完全一致**） |
| 正在跑 | `steer` | `next-step` | **当前回合的下一个步骤边界**，且多条一起交 |

**回退**：宿主没有 `status` 字段或没有 `steer` 方法 → 自动退回 `followup`，不丢消息。

### 3.2 配套：单回合等待总量（`lib/rhythm.js` + `lib/tool.js`）

回合长度是排队问题的**上游**：回合越长，这期间进来的消息排队窗口越大。
原来的 `waitMaxMs` 只夹「一次」等多久，她可以连打四次 40000ms。

新增配置 `waitTurnMaxMs`（默认 60000，0 = 不限）：

- 按 target key（`group:123` / `private:456`）记账；
- **每次有新消息投给她就重置**（有新东西要处理，就该给新预算）；
- 用完了**不报错** —— `qq_wait` 立刻返回当前情况 + 一句
  「额度用完了，现在开口，或者 `qq_pass` / `qq_skip` 收掉这一轮」；
- 带 10 分钟 TTL 兜底，避免「昨天的额度」卡今天。

## 五、需要你做的事

**重启 DSH** 才会加载新模块代（`~/.dsh/profiles/desktop/node_modules/dsh-onebot-channel`
是独立副本，不是硬链接）。

重启后怎么确认它在生效：

1. `~/.dsh/qq-bridge-load.log` 里出现 `[module] loaded pid=<新pid>`
2. 她跑回合时（比如正在 `qq_wait`），群里再来一条 @ —— 日志里应出现
   `[deliver] agent 正在跑，改用 steer 投递（不排 next-turn）session=…`
3. 界面上**不再出现**「N 条排队消息」越积越多；如果出现，数量应该很快归零

## 六、还没解决 / 需要观察的

1. **同一个群连发多条时的合并**：`steer` 会整队全取，所以同一回合内多条消息会一起交上去
   （这是想要的）。但如果她一个回合跑得很久、期间来了 20 条，那 20 条会一次性涌进去 ——
   要不要再做一个「回合内单次最多带几条」的上限，等实测再定。
2. **`qq_msg_history` 与投递的重复**：她查过的内容仍可能通过 steer 再收到一次。
   steer 至少保证了「是新的、当回合的」，不会隔几轮才到；彻底去重需要把「查过哪些
   message_id」也记进会话状态，属于更大的改动，先不做。
3. **截图里那个会话不是当前实例**（用户确认）。所以这次没有用那份日志做对照，
   结论来自代码路径 + 宿主源码。等重启后真实复现一次，可以再核一遍日志时序。
