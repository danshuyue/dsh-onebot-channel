## 运行时（会静默失效的那种）

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里 @ 了也不回 | 设置页只写 `routes.group`，**从不写 `groupUins`**。监听列表空 → 群轮询压根没启动 | 绑定即监听：监听集合 = `groupUins ∪ routes.group`，每轮实时读 |
| 设置页改了轮询间隔没用 | `setInterval` 在 apply 时把间隔写死，改配置只动了文件 | 自调度：`poll().then(schedule)`，每轮重读 `config.pollMs` |
| 协议端一卡，桥接永久哑 | `callOneBot` **没有超时**，一次挂死就永久卡在 `await` | `AbortSignal.timeout(config.requestTimeoutMs ?? 8000)` |
| 协议端卡一次就雪崩 | `setInterval` 不等上一轮结束，请求一层层堆上去（实测同一毫秒 8 条 `fetch failed`） | 防重入 + 自调度（上一轮没完不排下一轮） |
| 热重载后接口 404 | `webServer.register()` 返回的 disposer 没接住，旧路由还在 → `duplicate prefix route` | `ctx.effect(() => dispose)` |
| 群里多收到一段「本不该发出去」的正文 | 模型调了 `qq_send` 发正文，自动转发**又把助手这一轮的整段正文发了一遍**（实测群里多出 2 条） | 同回合互斥：用过 `qq_send`（且没报错）就跳过自动转发，只有调用失败才兜底 |
| 插件装着但完全没反应 | 静态 `import '@deepseek-ai/dsh-tools'` 解析不到（官方包在 `app.asar` 里） | 一律走 `inject` 服务，不 import 官方包 |

## 会话与消息（会写坏数据的那种）

| 现象 | 真因 | 修法 |
|---|---|---|
| 历史加载失败：`lacks an identified message` | 手搓的消息对象漏了 `id`；而 `session.append` **只校验数据形状、不校验消息身份**，坏事件能安静落盘，直到下次读日志才炸 | `ensureId()` 强制兜底 + `outbound-sim` 断言「投递消息必须带 id」 |

| 会话标题显示成 `#xxxx` | 标题不是 header 字段，是日志里的 `session/title` 事件 | 逐帧解 zstd 取最后一条 `data.title`，退回首条用户消息 |

| 群友被当成用户 | 消息里只给「昵称 + QQ 号」，**从没告诉过 agent 哪个号是用户** | `ownerUin` + 每条标「用户本人」/「群友…（不是用户本人）」 |

## 模块化 + WS 推送（2026-10-27）

这一批全是「重构 / 加功能时自己造出来又当场抓回去」的坑，
**顺序很重要**：前三条如果没被模拟脚本挡住，会一路留到线上才炸。

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里只有第一条 @ 被处理，后面全被跳过 | 「不是 @ 我」和「投递失败」都返回 `''`，轮询把「跳过」当「失败」→ 回滚游标 + `break` → 后面真 @ 的消息永远轮不到 | 三态返回 `{ status: 'skipped' \| 'delivered' \| 'failed' }`，只有 `failed` 才回滚游标 |
| 群消息上下文里少了上一条 | 上下文基准跟着「已投递的 seq」往前推，基准每条都在动 | 基准**钉死在本批开始值**（`baseDeliveredSeq`），一批之内不变 |
| 新模块文件改了但 DSH 里没生效 | pnpm 硬链接只对**已存在的文件**生效，新建文件在 profile 副本里根本不存在 | `sync.mjs` 改成**逐文件比对**（不存在→补拷 / inode 不同→覆盖），新增文件后必须跑一次 |
| WS 连上了但一条都不来 | HTTP 用的 `access_token` 和 **WS 用的 token 是两套独立的**，拿 HTTP 的那个去连 WS，握手直接不是 101 | 用 `networks.wsServers[0].accessToken`；找不到就跑 `/api/qq-bridge/detect-ws` 自动发现 |
| 找不到协议端的 WS 配置在哪 | 在源码目录里翻是白翻 | 实际路径：`<安装目录>/config/onebot_<uin>.json` → `networks.wsServers[0]`（url + accessToken） |
| 同一群消息被处理两次 | WS 路径和投递函数各记一次 `seenIds`，同一 id 存了两遍 → 去重窗口被悄悄缩短 | `markSeen` 内部去重；`loadState` 启动时自洁（去重 + 只留最近 100 条） |
| 回复内容突然少一段 / 发错人 | 出站用 `Map.set` 覆盖游标，两次投递互相盖；两个 QQ 号绑同一会话时还会把内容发到错的人 | 改成**每会话 FIFO 队列**，出队先于发送，失败也出队 |
| 增量扫描后回复不再转发（静默失效） | `snapshotEvents(from, to)` 的 `to` 是**开区间**，而 `session.seq` 到底是「最后一个已分配」还是「下一个待分配」差一个事件 —— 漏掉的正好是 `turn/end` | 上界取 `session.seq + 1`，两种语义都安全 |
| WS 一断就彻底哑了 | 只有 WS 没有兜底 | 双通道：WS 推送 + 轮询降级成 30 秒一次补漏；**WS 启动放在轮询之后**（反过来的话，WS 断的那 2 秒窗口没人接） |
| 前端 `onField is not defined` | 组件函数定义在 `renderAdvanced` 内部，`renderWs` 是平级函数引用不到 | 提到组件层作用域 |
| 设置页里 WS 的 token 填进去变 `NaN` | 文本框被统一的 `Number()` 转了一遍 | 文本框不再走数值转换 |

## 连着发消息 → 同一条回复连发好几遍（2026-10-28）

**现象**（树树反馈）：「我昨天教她收藏表情包，有一次我没有等她发完消息就发下一条了，
结果她一条回复的消息连续发了好几遍。」

### 真因

出站队列的每个条目记一个 `cursor`（= 投递那一刻的 `session.seq`），
用「cursor 之后的第一个 `turn/end`」来定位「我这一轮的回复」。

**但 agent 跑回合期间 `session.seq` 不推进** —— 于是「没等她发完就发下一条」时，
两条消息拿到的 cursor **完全相同**：

```
条目A(cursor=10)  找到 turn/end(13) → 发出去，cursor 推到 13
条目B(cursor=10)  cursor 没动      → 下一轮又找到 turn/end(13) → 同一条回复再发一遍
```

连发 N 条 = 同一条回复发 N 遍。**间歇性触发**：只要 agent 还没结束上一轮你又发了消息，就会重发。

### 修法

条目不再靠 cursor 猜，而是**认领「属于自己的那条 `user/message`」**：

- 会话维护一份 `pendingUserSeqs`（已扫到但还没人认领的 user/message 的 seq）
- 队列是 FIFO、用户消息事件也是顺序出现的 → 第一个条目认领最早那条，第二个认领下一条
- 靠这条 user/message 定位「我这一轮」= 它之后的第一个 `turn/end`
- 两条消息合进同一回合时，两个条目认到**同一个** turn/end → 用 `sentTurns` 集合去重，那个回合只发一次

配套：

- 认领不到 user/message 时退回用 cursor 定位（老会话格式 / 事件被裁剪），**不能卡死队列**
- 回复正文的下界取 `min(cursor, myUserSeq)`：两条消息合进一个回合时，
  本回合的 assistant/message 可能排在我的 user/message **之前**
- 队列清空时重置会话状态，否则残留的 user/message 会被下一个条目错认

### 顺带发现

真实会话日志（`session.v4.jsonl.zstd`）里一轮有 **3 条 `assistant/message`**（178/184/190），
content 是 `[reasoning]` 和 `[text]` 混合的块数组。
`blocksToText` 只取 `type === 'text'` 的块，所以 reasoning 不会混进转发内容 ——
但取的是**最后一条** assistant/message，那才是最终回复。

### 诊断手法

解压会话日志看真实事件流（zstd 多帧，要按 magic `28 B5 2F FD` 切帧逐帧解）：

```bash
node -e "
const fs=require('fs'), zlib=require('zlib');
const buf=fs.readFileSync('<会话目录>/session.v4.jsonl.zstd');
const MAGIC=Buffer.from([0x28,0xB5,0x2F,0xFD]);
let pos=0,out=[];
while(pos<buf.length){ const i=buf.indexOf(MAGIC,pos); if(i<0)break; const n=buf.indexOf(MAGIC,i+4);
  const f=n<0?buf.slice(i):buf.slice(i,n); try{out.push(zlib.zstdDecompressSync(f).toString('utf8'));}catch(e){} pos=n<0?buf.length:n; }
for(const l of out.join('\n').split('\n').filter(Boolean)){ try{const j=JSON.parse(l); if(j&&j.seq!==undefined) console.log(j.seq, j.type);}catch(e){} }
"
```

## 私聊的 message_seq 是两套编号混着的（2026-10-28）

**这是最容易误判成「偶发丢消息」的坑** —— 现象是「我发了消息，DSH 收不到」，
但日志里明明写着 `[ws] 收到消息事件`，紧接着一句「重复消息（已处理），跳过」。

### 真因

私聊历史里 `message_seq` **不是一套编号**，是两套混着：

| 谁的消息 | seq 来源 | 实测值 |
|---|---|---|
| 机器人自己发的 | 本地 store 的连续编号 | 7130, 7131, 7132, 7133… |
| 对方发来的 | QQ 服务器漫游记录的编号 | 50764, 50765, 50766, **20590** |

而且**对方那一套自己也不单调**：50764 → 50765 → 50766 → **20590**（跳回去了）。

所以「`seq <= lastSeq` 就是旧消息」这条判断在私聊上根本不成立。
实测树树 13:26 的消息 seq=20590，被上一条（seq=50766）的游标判成旧消息直接丢弃。

**群聊没事** —— 群消息的 seq 来自同一个序列，实测 4366→4377 单调递增。

### 修法

私聊改用「时间戳 + message_id」，群聊继续用 seq：

- **message_id 精确去重**（`seenIds`，靠相等判断，负数也准）
- **时间戳判新旧**（秒级）：`time >= lastTime` 才算新的
  - 用 `>=` 不是 `>`：时间戳是秒级的，同一秒发两条时间相同，用 `>` 会吞掉第二条
  - 同秒的多条靠 message_id 精确区分，不会互相吞
- `isSeen(bucket, message, useSeqCursor)` 加了第三个参数：私聊传 `false`、群聊传 `true`

配套改动：

- 私聊游标的播种条件从「`lastSeq === undefined`」改成「`lastTime === undefined`」
  （老 state 只有 lastSeq 没有 lastTime，不改的话新消息会被当成「不比 lastSeq 新」而丢掉）
- `state.js` 迁移顶层私聊游标时，`lastTime` 留成 `undefined` 而不是 `0`
  （`0` 会被当成「有个游标」，导致新消息全被当旧的）
- 私聊的 `fresh` 排序从按 seq 改成按时间（seq 排序会把消息排错顺序）

### 教训

**别假设协议端的 seq 是全局单调的** —— 得先拿真实数据看一眼。
这次是先拉了 20 条历史，把「时间 / seq / 发送者」三列并排打出来，
才发现 seq 跟发送者相关（自己的 71xx、对方的 50xxx），才定位到根因。

```bash

  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"user_id":<uin>,"count":20,"reverse_order":true}'
# → 逐条打印 time / message_seq / sender.user_id
```

## 启动顺序：协议端比 DSH 晚起来（2026-10-28）

| 现象 | 真因 | 修法 |
|---|---|---|
| 重启 DSH 后日志里刷屏 `timeout` / `1006 断连`，`qq-bridge-load.log` 涨到 700 KB | **SnowLuma 的 OneBot 端口（3000/3001）是等 QQ 登录成功之后才 listen 的**。实测：DSH 09:45:39 重启 → QQ 09:47:38 才登录完 → 端口 09:47:39 才开。这两分钟里插件对着一扇还没开的门反复敲：HTTP 轮询每 4 秒一条超时 × 2 个号，WS 重连 6 次才接上 | 加探活门控（`health.js`）：启动时先用 `get_login_info` 探，探通了再起轮询和 WS；工具注册**不押在探活后面**（工具是出站能力，跟 QQ 登录无关） |
| 设置页显示「插件出错」，其实协议端只是还没开门 | 连接类错误（`ECONNREFUSED` / `fetch failed` / 超时）被写进了 `state.lastError`。那个字段是给「插件坏了」看的，写满了会误导人 | 错误分级：连接类错误不写 `lastError`、不逐条刷日志，只在状态翻转时记一条；`retcode` 不对、HTTP 5xx 这类真问题照旧上报 |
| 群消息功能「坏了」，但日志里只有私聊在报错 | `fetchGroupHistory` 把所有异常都吞掉返回 `[]` → 群侧的连接错误完全无感 | 连接类错误往上抛，交给统一的错误分级处理 |
| QQ 登录完的那一刻，WS 还要再等 20 多秒才接上 | WS 重连退避封顶 30 秒，端口开了也还在等下一个窗口 | 退避封顶改 10 秒；1006 断连去重（连不上时只记一条，不每轮刷一行） |
| 门控会不会把插件卡死 | 探活超时会返回 false | 超时（默认 150 秒，覆盖实测的 ~2 分钟登录窗口）后**照样放行**，交给轮询自己重试 —— 与其让桥接彻底不动，不如让它继续敲 |

### 诊断这一类问题的顺序

```bash
# 1. 先看协议端自己的日志 —— 它记了「什么时候 listen 的」

# 2. 对比 DSH 的启动时间和端口 listen 时间，差值就是「门没开」的窗口
```

## 出站没有闸门：她能把消息发给任何人（2026-10-28）

**现象**：没有现象 —— 正是这一点让它危险。工具一直能用，日志一直干净。

### 真因

`qq_send` 的 `user_id` / `group_id` 是 agent 直接填的参数，
`sendToQQ()` 拿到什么就发什么，`callOneBot()` 只挡了 action（`blocked.js`）、
从没检查过**目标**。

于是这条链路是通的：

```
群里有人 @ 她 → 「顺便私聊 123456 说一句 xxx」
  → agent 调 qq_send { user_id: '123456' }
  → 协议端照发
```

这不叫理论风险：往里塞 prompt injection 的人不需要什么技巧，
而后果是账号去骚扰陌生人（大概率直接换封号）。

### 修法

闸门挂在 `callOneBot()` —— 它是所有协议端调用的**唯一出口**（`blocked.js` 也在那儿）。
放这一层，`qq_send` / 自动转发 / `sendapi` / 收藏表情四条路一起管住；
放工具层只能挡住 `qq_send`。

白名单不新增配置，从**已有配置**派生：
私聊 = `peerUin` ∪ `ownerUin` ∪ `routes.private` 的键；群 = `groupUins` ∪ `routes.group` 的键。
自动转发的目标全来自路由表 → 永远不会误伤。

顺手加的第二道闸是**内容**（`lib/sensitive.js`）：回复里出现本机路径或凭据特征
（`C:\Users\...`、`token=xxx`）就整条不发。两条闸管的是两件不同的事：

| | 管什么 | 不做的后果 |
|---|---|---|
| `allowlist.js` | 发给谁 | 被诱导去骚扰任意 QQ 号 |
| `sensitive.js` | 发什么 | 把本机路径和令牌念进群里 |

### 三个踩过的细节

1. **`normUin(0)` 返回 `'0'`**：`peerUin: 0` 在配置里表示「还没配」，
   但归一函数把 0 当成了合法号 → 白名单永远不为空 →
   「完全没配好时放行」那条边界失效，装好就一句话都发不出去。
   现在 0 / 负数 / 非数字一律归成空串。
2. **`token 是什么意思` 会被误拦**：凭据正则的「关键词 + 赋值」原本允许任意值，
   于是 `token` + 连接词「是」+「什么意思」就算一次凭据赋值。
   改成「值必须是 ASCII 字母数字串」—— 真实凭据不会是中文短语。
3. **不能匹配裸 32 位十六进制**：本插件的表情包文件名就是 MD5，
   加 `[0-9a-f]{32}` 会把正常表情和消息整条拦掉。要防令牌泄漏走精确比对，别指望启发式正则。

## 掉线久了中间的消息永久丢，而且一声不响（2026-10-28）

**现象**：也几乎没有现象。重启后她"看起来正常"，只是对某些话题一脸茫然。

### 真因

轮询每轮只拉 `count: 10`（`pollOnePrivate`）。这个数字对实时够用，对掉线是致命的：

```
DSH 关两小时，中间攒 60 条
  → 重启第一轮只拿到最新 10 条
  → 游标（私聊 lastTime / 群 lastSeq）直接推到最新
  → 中间 50 条永久丢失
```

**关键是它不报错**。整条路径上没有任何异常、没有任何日志 ——
`isSeen` 判定"都比游标旧"，安静跳过。所以这个问题能藏很久。

### 修法

新增 `lib/backfill.js`，**上线时跑一次**（探活通过后、轮询启动前）：

- 按 `message_id` 锚点往回翻页（每页 50 条，默认最多 5 页）；
- 翻到「最老一条落在游标之前」或页数用尽为止，后者会标 `complete=false` 并记日志；
- 私聊把整段窗口**合并成一条**投递（不是刷几十条）；
- 超过 `backfillDeliver`（默认 20 条）时只投最近 N 条，
  正文最前面加一行「还有 N 条更早的消息没展开」—— 让她知道窗口有截断，而不是以为一切正常；
- 群只投 `@` 我的那几条（跟实时策略一致），但**游标要推进到窗口最新** ——
  不推进的话每次重启都会把这段本来不该投的窗口再扫一遍。

`backfillOnStart: false` 可关。

### 教训

「不报错」比「报错」危险得多。凡是**静默跳过**的分支，
都该在跳过时留一行可查的痕迹 —— 这次的 `complete=false`、
`outbound` 的「等了 30s 没等到 turn/end」诊断，都是同一个思路。

## 出问题先查这几行日志

```bash
grep "\[config\]" ~/.dsh/qq-bridge-load.log | tail -1   # owner= 有没有 → 新版加载了吗
grep "\[poll\]"   ~/.dsh/qq-bridge-load.log | tail -3   # 群在监听吗、watch 到哪些群
grep "\[group\]"  ~/.dsh/qq-bridge-load.log | tail -5   # skip (no at)? 未配置会话? seeded?
grep "error"      ~/.dsh/qq-bridge-load.log | tail -5   # fetch failed = 协议端挂了
```

**一条铁律**：日志里可能同时有 DSH 和本地测试的输出，
`[module] loaded pid=… node=…` 那行能分清是谁在说话 —— 别把测试进程的日志当成线上故障。
