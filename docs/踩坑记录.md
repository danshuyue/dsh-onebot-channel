## 运行时（会静默失效的那种）

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里 @ 了也不回 | 设置页只写 `routes.group`，**从不写 `groupUins`**。监听列表空 → 群轮询压根没启动 | 绑定即监听：监听集合 = `groupUins ∪ routes.group`，每轮实时读 |
| 设置页改了轮询间隔没用 | `setInterval` 在 apply 时把间隔写死，改配置只动了文件 | 自调度：`poll().then(schedule)`，每轮重读 `config.pollMs` |
| 协议端一卡，桥接永久哑 | `callOneBot` **没有超时**，一次挂死就永久卡在 `await` | `AbortSignal.timeout(config.requestTimeoutMs ?? 8000)` |
| 协议端卡一次就雪崩 | `setInterval` 不等上一轮结束，请求一层层堆上去（实测同一毫秒 8 条 `fetch failed`） | 防重入 + 自调度（上一轮没完不排下一轮） |
| 热重载后接口 404 | `webServer.register()` 返回的 disposer 没接住，旧路由还在 → `duplicate prefix route` | `ctx.effect(() => dispose)` |
| 群里多收到一段「本不该发出去」的正文 | 模型调了 `qq_send` 发正文，自动转发**又把助手这一轮的整段正文发了一遍**（实测群里多出 2 条） | 同回合互斥：用过 `qq_send`（且没报错）就跳过自动转发，只有调用失败才兜底 |
| 插件装着但完全没反应 | 静态 `import '@deepseek-ai/dsh-tools'` 解析不到（官方包在 `app.asar` 里） | 一律走 `inject` 服务，不 import 官方包 |
| 分条间隔设了却没停顿，多条消息照样秒连发 | 停顿只写在 `sendToQQ` 的分条循环里（`if (i > 0) await sleep(...)`）——它只覆盖「**一次调用拆成 N 条**」。模型连着调 N 次 `qq_send`、每次正文只有一行时，每次调用 `markedParts.length === 1`，循环里的 `i > 0` 永远不成立，一秒都不等 | 停顿下沉到**唯一单条出口** `sendOneToQQ`：按目标记 `lastSendAt`，发之前补齐「距上一条的差额」（`waitForGap`），并用 `withSendLock` 按目标串行化（否则同一步里并发两个 `qq_send` 会同时读到同一个 `lastSendAt`、同时补等、同时发出，等于没节流） |

## 模块化 + WS 推送（2026-10-27）

这一批全是「重构 / 加功能时自己造出来又当场抓回去」的坑，
**顺序很重要**：前三条如果没被模拟脚本挡住，会一路留到线上才炸。

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里只有第一条 @ 被处理，后面全被跳过 | 「不是 @ 我」和「投递失败」都返回 `''`，轮询把「跳过」当「失败」→ 回滚游标 + `break` → 后面真 @ 的消息永远轮不到 | 三态返回 `{ status: 'skipped' \| 'delivered' \| 'failed' }`，只有 `failed` 才回滚游标 |
| 群消息上下文里少了上一条 | 上下文基准跟着「已投递的 seq」往前推，基准每条都在动 | 基准**钉死在本批开始值**（`baseDeliveredSeq`），一批之内不变 |
| 新模块文件改了但 DSH 里没生效 | pnpm 硬链接只对**已存在的文件**生效，新建文件在 profile 副本里根本不存在 | `sync.mjs` 改成**逐文件比对**（不存在→补拷 / inode 不同→覆盖），新增文件后必须跑一次 |
| WS 连上了但一条都不来 | HTTP 用的 `access_token` 和 **WS 用的 token 是两套独立的**，拿 HTTP 的那个去连 WS，握手直接不是 101 | 用 `networks.wsServers[0].accessToken`；找不到就跑 `/api/qq-bridge/detect-ws` 自动发现 |
| 找不到协议端的 WS 配置在哪 | 在源码目录里翻是白翻 | 实际路径：`<安装目录>/config/onebot_<uin>.json` → `networks.wsServers[0]`（url + accessToken） |
| 同一群消息被处理两次 | WS 路径和投递函数各记一次 `seenIds`，同一 id 存了两遍 → 去重窗口被悄悄缩短 | `markSeen` 内部去重；`loadState` 启动时自洁（去重 + 只留最近 100 条） |
| 回复内容突然少一段 / 发错人 | 出站用 `Map.set` 覆盖游标，两次投递互相盖；两个 QQ 号绑同一会话时还会把内容发到错的人 | 改成**每会话 FIFO 队列**，出队先于发送，失败也出队 |
| 增量扫描后回复不再转发（静默失效） | `snapshotEvents(from, to)` 的 `to` 是**开区间**，而 `session.seq` 到底是「最后一个已分配」还是「下一个待分配」差一个事件 —— 漏掉的正好是 `turn/end` | 上界取 `session.seq + 1`，两种语义都安全 |
| WS 一断就彻底哑了 | 只有 WS 没有兜底 | 双通道：WS 推送 + 轮询降级成 30 秒一次补漏；**WS 启动放在轮询之后**（反过来的话，WS 断的那 2 秒窗口没人接） |
| 前端 `onField is not defined` | 组件函数定义在 `renderAdvanced` 内部，`renderWs` 是平级函数引用不到 | 提到组件层作用域 |
| 设置页里 WS 的 token 填进去变 `NaN` | 文本框被统一的 `Number()` 转了一遍 | 文本框不再走数值转换 |

## 连着发消息 → 同一条回复连发好几遍（2026-10-28）

**现象**（树树反馈）：「我昨天教她收藏表情包，有一次我没有等她发完消息就发下一条了，
结果她一条回复的消息连续发了好几遍。」

### 真因

出站队列的每个条目记一个 `cursor`（= 投递那一刻的 `session.seq`），
用「cursor 之后的第一个 `turn/end`」来定位「我这一轮的回复」。

**但 agent 跑回合期间 `session.seq` 不推进** —— 于是「没等她发完就发下一条」时，
两条消息拿到的 cursor **完全相同**：

```
条目A(cursor=10)  找到 turn/end(13) → 发出去，cursor 推到 13
条目B(cursor=10)  cursor 没动      → 下一轮又找到 turn/end(13) → 同一条回复再发一遍
```

连发 N 条 = 同一条回复发 N 遍。**间歇性触发**：只要 agent 还没结束上一轮你又发了消息，就会重发。

### 修法

条目不再靠 cursor 猜，而是**认领「属于自己的那条 `user/message`」**：

- 会话维护一份 `pendingUserSeqs`（已扫到但还没人认领的 user/message 的 seq）
- 队列是 FIFO、用户消息事件也是顺序出现的 → 第一个条目认领最早那条，第二个认领下一条
- 靠这条 user/message 定位「我这一轮」= 它之后的第一个 `turn/end`
- 两条消息合进同一回合时，两个条目认到**同一个** turn/end → 用 `sentTurns` 集合去重，那个回合只发一次

配套：

- 认领不到 user/message 时退回用 cursor 定位（老会话格式 / 事件被裁剪），**不能卡死队列**
- 回复正文的下界取 `min(cursor, myUserSeq)`：两条消息合进一个回合时，
  本回合的 assistant/message 可能排在我的 user/message **之前**
- 队列清空时重置会话状态，否则残留的 user/message 会被下一个条目错认

### 顺带发现

真实会话日志（`session.v4.jsonl.zstd`）里一轮有 **3 条 `assistant/message`**（178/184/190），
content 是 `[reasoning]` 和 `[text]` 混合的块数组。
`blocksToText` 只取 `type === 'text'` 的块，所以 reasoning 不会混进转发内容 ——
但取的是**最后一条** assistant/message，那才是最终回复。

### 诊断手法

解压会话日志看真实事件流（zstd 多帧，要按 magic `28 B5 2F FD` 切帧逐帧解）：

```bash
node -e "
const fs=require('fs'), zlib=require('zlib');
const buf=fs.readFileSync('<会话目录>/session.v4.jsonl.zstd');
const MAGIC=Buffer.from([0x28,0xB5,0x2F,0xFD]);
let pos=0,out=[];
while(pos<buf.length){ const i=buf.indexOf(MAGIC,pos); if(i<0)break; const n=buf.indexOf(MAGIC,i+4);
  const f=n<0?buf.slice(i):buf.slice(i,n); try{out.push(zlib.zstdDecompressSync(f).toString('utf8'));}catch(e){} pos=n<0?buf.length:n; }
for(const l of out.join('\n').split('\n').filter(Boolean)){ try{const j=JSON.parse(l); if(j&&j.seq!==undefined) console.log(j.seq, j.type);}catch(e){} }
"
```

## 私聊的 message_seq 是两套编号混着的（2026-10-28）

**这是最容易误判成「偶发丢消息」的坑** —— 现象是「我发了消息，DSH 收不到」，
但日志里明明写着 `[ws] 收到消息事件`，紧接着一句「重复消息（已处理），跳过」。

### 真因

私聊历史里 `message_seq` **不是一套编号**，是两套混着：

| 谁的消息 | seq 来源 | 实测值 |
|---|---|---|
| 机器人自己发的 | 本地 store 的连续编号 | 7130, 7131, 7132, 7133… |
| 对方发来的 | QQ 服务器漫游记录的编号 | 50764, 50765, 50766, **20590** |

而且**对方那一套自己也不单调**：50764 → 50765 → 50766 → **20590**（跳回去了）。

所以「`seq <= lastSeq` 就是旧消息」这条判断在私聊上根本不成立。
实测树树 13:26 的消息 seq=20590，被上一条（seq=50766）的游标判成旧消息直接丢弃。

**群聊没事** —— 群消息的 seq 来自同一个序列，实测 4366→4377 单调递增。

### 修法

私聊改用「时间戳 + message_id」，群聊继续用 seq：

- **message_id 精确去重**（`seenIds`，靠相等判断，负数也准）
- **时间戳判新旧**（秒级）：`time >= lastTime` 才算新的
  - 用 `>=` 不是 `>`：时间戳是秒级的，同一秒发两条时间相同，用 `>` 会吞掉第二条
  - 同秒的多条靠 message_id 精确区分，不会互相吞
- `isSeen(bucket, message, useSeqCursor)` 加了第三个参数：私聊传 `false`、群聊传 `true`

配套改动：

- 私聊游标的播种条件从「`lastSeq === undefined`」改成「`lastTime === undefined`」
  （老 state 只有 lastSeq 没有 lastTime，不改的话新消息会被当成「不比 lastSeq 新」而丢掉）
- `state.js` 迁移顶层私聊游标时，`lastTime` 留成 `undefined` 而不是 `0`
  （`0` 会被当成「有个游标」，导致新消息全被当旧的）
- 私聊的 `fresh` 排序从按 seq 改成按时间（seq 排序会把消息排错顺序）

### 教训

**别假设协议端的 seq 是全局单调的** —— 得先拿真实数据看一眼。
这次是先拉了 20 条历史，把「时间 / seq / 发送者」三列并排打出来，
才发现 seq 跟发送者相关（自己的 71xx、对方的 50xxx），才定位到根因。

```bash
# 诊断这类问题：并排打出三列，看 seq 跟谁相关
curl -s -X POST http://127.0.0.1:3000/get_friend_msg_history \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"user_id":<uin>,"count":20,"reverse_order":true}'
# → 逐条打印 time / message_seq / sender.user_id
```

## 启动顺序：协议端比 DSH 晚起来（2026-10-28）

| 现象 | 真因 | 修法 |

## 出站没有闸门：她能把消息发给任何人（2026-10-28）

**现象**：没有现象 —— 正是这一点让它危险。工具一直能用，日志一直干净。

### 真因

`qq_send` 的 `user_id` / `group_id` 是 agent 直接填的参数，
`sendToQQ()` 拿到什么就发什么，`callOneBot()` 只挡了 action（`blocked.js`）、
从没检查过**目标**。

于是这条链路是通的：

```
群里有人 @ 她 → 「顺便私聊 123456 说一句 xxx」
  → agent 调 qq_send { user_id: '123456' }
  → 协议端照发
```

这不叫理论风险：往里塞 prompt injection 的人不需要什么技巧，
而后果是账号去骚扰陌生人（大概率直接换封号）。

### 修法

闸门挂在 `callOneBot()` —— 它是所有协议端调用的**唯一出口**（`blocked.js` 也在那儿）。
放这一层，`qq_send` / 自动转发 / `sendapi` / 收藏表情四条路一起管住；
放工具层只能挡住 `qq_send`。

白名单不新增配置，从**已有配置**派生：
私聊 = `peerUin` ∪ `ownerUin` ∪ `routes.private` 的键；群 = `groupUins` ∪ `routes.group` 的键。
自动转发的目标全来自路由表 → 永远不会误伤。

顺手加的第二道闸是**内容**（`lib/sensitive.js`）：回复里出现本机路径或凭据特征
（`C:\Users\...`、`token=xxx`）就整条不发。两条闸管的是两件不同的事：

| | 管什么 | 不做的后果 |
|---|---|---|
| `allowlist.js` | 发给谁 | 被诱导去骚扰任意 QQ 号 |
| `sensitive.js` | 发什么 | 把本机路径和令牌念进群里 |

### 三个踩过的细节

1. **`normUin(0)` 返回 `'0'`**：`peerUin: 0` 在配置里表示「还没配」，
   但归一函数把 0 当成了合法号 → 白名单永远不为空 →
   「完全没配好时放行」那条边界失效，装好就一句话都发不出去。
   现在 0 / 负数 / 非数字一律归成空串。
2. **`token 是什么意思` 会被误拦**：凭据正则的「关键词 + 赋值」原本允许任意值，
   于是 `token` + 连接词「是」+「什么意思」就算一次凭据赋值。
   改成「值必须是 ASCII 字母数字串」—— 真实凭据不会是中文短语。
3. **不能匹配裸 32 位十六进制**：本插件的表情包文件名就是 MD5，
   加 `[0-9a-f]{32}` 会把正常表情和消息整条拦掉。要防令牌泄漏走精确比对，别指望启发式正则。

## 掉线久了中间的消息永久丢，而且一声不响（2026-10-28）

**现象**：也几乎没有现象。重启后她"看起来正常"，只是对某些话题一脸茫然。

### 真因

轮询每轮只拉 `count: 10`（`pollOnePrivate`）。这个数字对实时够用，对掉线是致命的：

```
DSH 关两小时，中间攒 60 条
  → 重启第一轮只拿到最新 10 条
  → 游标（私聊 lastTime / 群 lastSeq）直接推到最新
  → 中间 50 条永久丢失
```

**关键是它不报错**。整条路径上没有任何异常、没有任何日志 ——
`isSeen` 判定"都比游标旧"，安静跳过。所以这个问题能藏很久。

### 修法

新增 `lib/backfill.js`，**上线时跑一次**（探活通过后、轮询启动前）：

- 按 `message_id` 锚点往回翻页（每页 50 条，默认最多 5 页）；
- 翻到「最老一条落在游标之前」或页数用尽为止，后者会标 `complete=false` 并记日志；
- 私聊把整段窗口**合并成一条**投递（不是刷几十条）；
- 超过 `backfillDeliver`（默认 20 条）时只投最近 N 条，
  正文最前面加一行「还有 N 条更早的消息没展开」—— 让她知道窗口有截断，而不是以为一切正常；
- 群只投 `@` 我的那几条（跟实时策略一致），但**游标要推进到窗口最新** ——
  不推进的话每次重启都会把这段本来不该投的窗口再扫一遍。

`backfillOnStart: false` 可关。

### 教训

「不报错」比「报错」危险得多。凡是**静默跳过**的分支，
都该在跳过时留一行可查的痕迹 —— 这次的 `complete=false`、
`outbound` 的「等了 30s 没等到 turn/end」诊断，都是同一个思路。

## 合并窗口把「已读」提前记了，投递失败会丢游标（2026-10-29）

**现象**：连发合并那条链路如果投递失败，重试时要么**重复投**、要么**回退不干净漏已读**，
偶尔还把别的号也标了已读。平时完全正常，一失败就乱。

**真因**：合并队列的设计是「来信先记账（`markSeen` + 游标推进）再入池」，等窗口攒够或超时触发一个回合。
记账比投递早一步，是为了不让同一个人连发被轮询重复扫到。但副作用是**记账和投递不是原子** ——
投递失败那一瞬间，游标已经往前走了，重试时一致性全乱。

**修法**：`merge.js` 入池时存一份 `mergeSnapshots`（游标 + seen 集合的快照），投递失败就整体回滚到快照，
让这一个人重新回到「未读」，下一轮重来。回滚是整段链路的事，不是只撤一条。

**教训**：「先记账后投」省了重复扫描，但把一致性成本挪到了失败路径。凡是把状态提前推进的设计，
都必须配一个能在失败时点原样退回的快照，否则平时没事、一失败就丢。

## 主动搭话「对谁开口」写死第一个候选（2026-10-29）

**现象**：设置页点「对 TA 试一次」并指定 347，消息却发到了 321。重启 DSH 之后又好了。

**真因**：两件事叠一起 ——
1. `runProactiveOnce(force:true)` 打候选时**直接取名单第一个**，不尊重 `only` 也不轮转；名单是对象键序，
   永远固定那个人，所以「给 347 试」和「给 321 试」结果一样。
2. 事后查到**主进程是上午 11:08 启动的，加载的还是 0.9.0 老代码**。问题 2 比问题 1 更隐蔽，
   只靠改代码永远查不出「为什么还是错」。

**修法**：`proactive.js` 新增 `orderByStalest()`，按 `lastProactiveAt` 升序轮转 —— 谁最久没被主动开口就先轮到谁；
`only` 仍优先（指定谁就谁）。设置页显示「下一个轮到 XXX」，轮转看得见了。

测试专用分支最容易被拿去当正式路径。**改完代码行为没变，第一反应应是「主进程还在跑旧代码吗」，不是「我改错了」**。

## qq_pass 把整回合的正文吞掉了（2026-10-29）

**现象**：她在对话框里写了话、日志也没报错，但 QQ 对面**一条都没收到**。

**真因**：出站闸门里 `qq_pass` 的判定是「只要有 `qq_pass` 整回合就静默不发」。但 `qq_pass` 的本意是

老逻辑把那句正文连同 `qq_pass` 一起丢掉，等于她写了却没说。

**修法**：`outbound.js` 改成：正文里有**实在的话**（非纯括号动作、非纯标点）就照发，

正文里写了真话就当成「开口了」。

**教训**：「沉默权」和「删话」是两件事。工具描述也改了 ——「管的是这次不开口，不是把刚写的话删掉」。
语义边界要在注释和工具描述里都写清，否则模型会按字面误解。

**真因**：出站抑制用 `targetOf()` 推断「这次发给谁」，无参时它从某处随便取一个目标，

## 关系卡和主动搭话状态写盘太频繁（2026-10-29）

**现象**：没有明显现象，但 I/O 监控会看到群消息密集时每秒好几次 `writeFileSync`。

**真因**：`touchPeer()`（memory.js）和 `notePeerSpoke()`（proactive.js）在每条消息投递成功后都调用 `persist()`，

**修法**：两个模块都加写节流（30 秒内只写一次），脏数据攒在内存里。插件卸载时通过 `flushPersist()` 兜底写一次。

**教训**：凡是「每条消息 / 每次事件」都触发的写盘，都该问一句：中间态有人读吗？没有就该节流。
`poll.js` 里的 `lastHeartbeat`（30 秒落一次盘）早就在用这个模式，但当时没推广到 memory 和 proactive。

## 0.16.1 对话窗口复查：状态、回填与无损消息编号（2026-11-02）

这次对话窗口功能经过独立只读交叉审核后，补了几类容易被单元测试漏掉的边界：

- **内存队列不能假定会跨重启存在。** 窗口的 `pending` 原本只在内存，落盘的 `active` 却会恢复，重启后就会出现「窗口还开着、消息已经没了」。现在 pending 与批次起始时间随窗口状态保存；启动时优先恢复可恢复批次，无法恢复的活动窗口才关闭。
- **backfill 不能只看是否 @ 机器人。** 活动窗口期间，触发者普通消息、再次 @、引用机器人窗口回复都可能属于同一窗口。回填应先按窗口资格筛选，再推进游标；否则会在 `runBackfill()` 先于实时循环启动时越过应处理的普通消息。
- **`message_id` 是协议标识，不是安全整数。** WS 归一化、seenIds、reply_to、窗口自发消息集合、出站回执都必须保留字符串；任何 `Number(message_id)` 都可能让超大 ID 失真。
- **一次模型回复可能对应多条 QQ 消息。** 分条发送后不能只登记最后一条 `message_id`，否则用户引用较早分段时窗口资格判断失败。发送结果保留全部成功 ID，回复计数仍只增加一次。
- **失败批次要退避。** pending 保留而计时不变，会在批次超时后每秒重试；协议端故障时会形成请求风暴。现在失败按指数退避，成功或关窗时清除退避状态。
- **关闭新功能必须真的恢复旧行为。** `windowEnabled=false` 时不能继续无条件启用窗口专属的 @ 限频，否则「关闭窗口」仍会改变旧版发送行为。
- **模拟测试必须自带隔离 HOME。** 测试若直接读写真实 `~/.dsh`，会覆盖用户状态，且与运行中的 DSH 并发时可能互相回写。测试应创建临时 HOME，结束后递归清理。
- **配置回读不能用 `Number(x) || default`。** `0` 可能是合法配置语义，API 和设置页都要用有限数判断或 nullish 逻辑保留它。

发布前固定检查顺序：隔离 HOME 跑完整 `npm test`，对所有 `lib/*.js` 和测试脚本跑 `node --check`，执行 `git diff --check`，最后 `npm pack` 检查 tgz 内容。不要为了验证插件而直接安装进正在运行的 DSH；安装和重启由使用者在确认包后进行。

## 「@ 后继续聊在关闭/超时后仍唤醒」——一次误报的排查记录（2026-11-02）

现象：使用者报告「已经关掉对话窗口、且间隔超过默认 2 分钟，AI 仍被唤醒」，并附截图（群里一条**没有 @** 的合并转发出现在机器人发言之后）。

### 结论：误报。代码不改，只留档。

### 排查过程里被证伪的三个假设

1. **「windowEnabled 不热加载，要重启才生效」——错。**
   `api.js` 的 `/save` 直接改 `getConfig()` 返回的同一个对象，保存后立即生效。实测：保存后读到 `false`，无需重启。
2. **「超时是按整体算的，群 A 静默、群 B 触发也算数」——错。**
   窗口状态按群号存在 `state.windows[groupId]`，两个群是两个独立对象；`touchWindow(群B)` 不会改写群 A 的 `lastActivityAt`。实测确认。
3. **「没 @ 的合并转发被误判成 @」——错。**
   拉真实群历史验证：合并转发在协议里就是单个 `forward` 段，**不含 `at` 段**
   （`[{"type":"forward","data":{"id":"..."}}]`），而 `isAtMe()` 只认 `type:'at' && qq === selfUin`。

### 真正发生的事

日志里那两次「没有新投递却在说话」，是**另一个会话里正在跑的回合**调用了 `qq_send`，而 `qq_send` 在没传 `group_id`/`user_id` 时，落到了全局兜底：

```js
rhythm.js:57   let lastDelivery = null          // 全进程一个，不分会话
rhythm.js:63   lastDelivery = { target, key }   // 每次投递都覆盖
tool.js:786    const recent = recentDelivery()  // 没给号时无条件用它
```

即「最近一次投递到哪个群，没写号的 qq_send 就发到哪个群」。

### 为什么这**不是**缺陷

工具注册是进程级的，`execute` 拿到的 `exec.agent.id` 目前没被这些工具使用，所以「按会话隔离」在插件侧做不到（宿主 `ToolDefinition.execute(args, exec)` 是给了的，但改成必填会让工具在别处静默失效）。

更重要的是：**「没绑定也能发」是被刻意保留的能力**。本机多条定时会话就是靠 `qq_send`/sendapi 往固定号发消息，强制「必须先绑定才能发」会把这些自动化安排一并打断。看上去像 bug，实际是有用且有意为之的设计。

### 唯一需要守住的边界（使用者定的）

不要出现「A 群绑定的会话里，群友的交流答复跑到 B 群，让 B 群群友莫名其妙」。
判断依据：**工具发消息必须显式指定目标，或明确知道自己在给谁发**。串群风险来自「没写号 + 全局兜底」，不是来自窗口功能。

### 顺带查实的两个真缺陷（本次未修，使用者决定不改）

- **0.16.2 装的是旧代码**：`~/.dsh/profiles/desktop/node_modules/dsh-onebot-channel` 里 `poll.js` 的 `deliverWindowBatch()` 用了未声明的 `windowMode`（0.16.3 的 `b55faff` 才补上声明），所以每次窗口批投递都抛 `ReferenceError`，被当成投递失败后指数退避 12 次（1s→2s→…→60s），消息一直卡在 pending。现场日志：`[window] batch handler threw group=...: windowMode is not defined`。
- **关开关不关窗**：`windowOf()` 不看 `windowEnabled`，所以关掉开关后 `state.windows[key]` 里 `active:true` 的记录仍然挂着（只是被 `poll.js` 里一道闸挡住不投递）。若以后要修，注意 `closeWindow()` 不清理 `openedToday/peersToday`（日配额天然保留），但 `sweep()` 里对每条历史记录逐条 `closeWindow` 会因它无条件 `saveWindows()` 变成每秒 N 次全量同步写盘 —— 先判 `activeOf` 且只在真的关了才落盘。

### 排查方法论（下次直接用）

1. 先确认**跑的是哪一版**：`curl /api/qq-bridge/state | jq .runtime`，再和源码 `package.json` 对比；安装副本和源码目录不是硬链接，改完必须 `node sync.mjs` 并重启。
2. 日志里区分「谁在说话」：自动转发会打 `[out] 已转发回复 N 字 -> group`；`qq_send` 工具只打 `[out] 按模型分段发 N 条` / `[out] 分 N 条发送`。**后者前面没有 `[deliver]`，就说明是别的回合在发，不是新消息唤醒的。**
3. `[group] ... skip (no at/window)` 说明这条消息**没有唤醒任何人**，不要把它当成唤醒源。
4. 拉真实协议历史验证段结构，别靠文档或记忆推断（`get_group_msg_history` 一次 100 条就够）。

## 合并转发的卡片读不出来（0.16.7，2026-11-02）

现象：别人在群里转发一段「群聊的聊天记录」，模型只看到 `[转发消息]`，等于什么都没读到。

### 真因

不是拿不到数据，而是**根本没去拿**。`onebot.js` 的 `SEGMENT_LABELS` 把 `forward` 段直接渲染成常量：

```js
forward: '[转发消息]',   // 旧版到此为止，内容一概不展开
```

而协议端其实一条命令就能取回全文。

### 协议事实（真机实测 SnowLuma 2.2.1）

群历史里，一张卡片就是**单个 forward 段**，不带 at：

```json
[{"type":"forward","data":{"id":"JzBzMIYHiNYZDIYdDQ6lwo9..."}}]
```

`get_forward_msg { id }` 返回 `{ retcode:0, data:{ messages:[…95 条…] } }`，
每一条**和普通群消息同构**（`sender.nickname` / `time` / `message` 段数组齐全），所以渲染能直接复用同一套逻辑。

实测那张卡片的规模，比预想的大得多，**这决定了每一项都必须有上限**：

| 指标 | 实测值 |
|---|---|
| 条数 | 95 条 |
| 文字量 | 712 字（最长单条 41 字） |
| 嵌套 forward | **8 条**（转发里还有转发） |
| 图片 | 11 张（带真实 url，能下载） |
| 时间跨度 | 38 分钟 |

### 修法

新增 `lib/forward.js`，把「取」和「渲染」拆开：

- `prefetchForwards()` —— 唯一的 async 部分，走 `callOneBot`（因此白名单/封禁/超时照旧生效）。**递归**取嵌套层，同 id 只请求一次（跨层去重，所以深嵌套不会指数爆炸）。
- `renderSegments()` —— 纯函数，不发请求。forward 段去 Map 里找预取结果，有就展开、没有就占位。

之所以拆成两步而不是把 `textOf()` 改成 async：`textOf` 被正文拼接、群上下文、历史工具十几个地方同步调用，变 async 后漏一个 await 就静默拿到 `[object Promise]`。

接入的四条正文路径：私聊、群上下文、群主消息、窗口批次、`qq_msg_history` 工具。

### 五个自己踩的坑

1. **`renderForward` 没把 `forwards` 往下传** → 嵌套渲染时查不到内层缓存，永远占位。递归预取取回来了也用不上。
2. **深度算两次** → `renderSegments` 传 `depth+1`，`renderForward` 里又 `+1`，maxDepth=2 时内层实际算到 3 层，**永远超限**。现在统一：`renderSegments` 传 `depth`，由 `renderForward` 判断「这一层还能不能钻」。
3. **字数上限写死下限 200** → 设置页填 40 会被 `Math.max(200, …)` 静默抬到 200，配置看着生效其实没有。下限改成 20。
4. **「第一条无论多长都收」会撑破字数上限** → 单条超长时必须自己截断并说明（`…（此条过长，已截断 N 字）`）。
5. **`ok:false` 的 pending 占位被当成内容渲染** → 递归预取会先写 `{ok:false, error:'pending'}` 占位防止重复请求。如果守卫写成 `hit === undefined` 而不是 `hit.ok !== true`，这个占位会被当成有效卡片渲染出一段空内容。这条是**变异测试抓出来的**，不是我自己想到的。

### 测试

`tests/forward-sim.mjs`（42 项）+ `tests/forward-mutation.mjs`（9 个变异，9/9 被抓到）。

变异测试特别值得留着：它证明断言不是恒真的 —— 第一版就有 8/9，漏掉的那个正好是上面第 5 条真实缺陷。

⚠️ 变异测试**不能直接改 `lib/forward.js`**：本机插件目录 ACL 断过继承，低完整性令牌（普通 shell）改不了里面的文件，只会 EPERM。所以它把整个 `lib/` 复制到仓库外临时目录，在副本上做变异。

### 真机验收（不是模拟）

拿协议端里真实那条卡片跑完整链路：

```
预取耗时 81~94ms，拿到 9 张卡片展开结果（1 外层 + 8 嵌套）
正文长度 1396 字
[转发消息 · 共 95 条，还有 45 条未展开]
10-26 13:18 崩兔子: 我们主任去年给人开止痛贴
…
```

对照旧版：`[转发消息]` —— 一句话，什么都没有。

### 审核（独立只读交叉审核）抓出的四个问题

自己写的时候没发现，都是审核员指出来、我复现后才改的：

1. **表情退化（真回归）**。`renderSegments` 原本自己复制了一套段渲染 `switch`，漏了 `face`/`mface`。
   于是「一批消息里有**任意**一张卡片」时，整批消息的 `[表情:呲牙]` 全退化成 `[表情]`（因为 `forwards.size > 0` 会让整批都走 `renderSegments`）。
   修法：把 `onebot.js` 的段渲染抽成导出的 `segmentToText()`，两边共用同一个函数。补了 8 条「两条路径逐字一致」的断言。
   **根因是「两套逻辑并存」** —— 这正是「复制一份稍微改改」必然的结局。

2. **`forwardConcurrency` 被当成总数上限**。旧代码 `ids.slice(0, concurrency)` 让第 4、5 张卡片**永久丢弃**，只留占位，用户不知道为什么不展开。
   修法：按 `concurrency` 分批（批内并发、批间串行），所有卡片都取到。

3. **`maxDepth` 无上限时请求数失控（最严重）**。关键点：`forwardMaxChars`/`forwardMaxMessages` **只管渲染、不管抓取**，抓取只受 `depth` 约束。
   而这段跑在**串行投递链**上（`poll.js` 逐条 `await`，定时器是「跑完再排下一次」）。
   所以 `maxDepth=1000` 时不是「慢一点」，是**整条群投递停摆**（群间隔本来只有 3 秒）。
   修法：加两个预算闸 —— `forwardMaxRequests`（单次投递请求数，默认 16）+ `forwardBudgetMs`（墙钟，默认 6s）。
   **不动 `maxDepth` 语义**（用户明确要求不设上限、成本自负），只把单次投递的花费变成常数上界，超预算的卡片按占位并在日志里明说。

4. **畸形数据会穿透、导致整条 @ 消息永久丢失**。路径：`prefetchForwards` 抛错 → 冒到 `handleGroupMessage` 之外 → 被 `pollGroup` 的 `catch` 吞掉，
   而游标在那之前**已经前进并落盘** → 这条消息既没投递、也不会再被捞回来。
   实测能触发：展开结果里 `message` 是 getter 抛错。
   修法：`prefetchForwards` 整段 try/catch（只降级不抛）+ `lineOf` 里单独兜 `item.message` 的读取。
   这类「装饰性动作把主链路弄死」的坑，跟当年「图片下载卡住整条私聊轮询」是同一类。

审核还确认了两件**不用改**的事，理由值得记：

- **卡片图不算新的 SSRF 面**。`buildForwardImageBlocks` 最终仍走 `fetchImageBytes`，它在**每一跳重定向**前都 `assertPublicHost(target)`，和入站图、收藏图是同一道闸。在 `collectForwardImages` 里再叠一层是重复。真正要补的是超时（`fetchImageBytes` 不接 `timeoutMs` 时落回 16 秒/张，6 张串行最坏 96 秒）—— 所以给 `buildForwardImageBlocks` 加了墙钟预算。
- **`forwards.size === 0` 那个分支已经没语义了**，只是「跳过每消息一次 `cfgOf()`」的性能快路径（两边共用 `segmentToText` 后，空 Map 下两条路径逐字等价）。保留，但注释改成说明它是快路径，禁止再往里加逻辑 —— 上次的表情退化正是从「一个看起来像语义开关的分支」里长出来的。

最终：`forward-sim` 64 项、`forward-mutation` **14/14 变异被抓到**。

## 卡片内容与本群历史分不清（0.16.8，2026-11-02）

上线后用户报的：模型**分不清「卡片里的」和「本群刚说的」**，把别的群的聊天记录当成了本群发生的对话。

### 真因：没有边界，而且格式一模一样

实测把 `handleGroupMessage` 投出去的正文打印出来，长这样：

```
（…群友「秋慕林」…）@3566906627[转发消息 · 共 95 条，还有 45 条未展开]   ← 标题紧贴着 @
10-26 13:18 崩兔子: 我们主任去年给人开止痛贴                        ← 卡片里的（别的群）
10-26 13:18 崩兔子: 26岁的男的

[这段时间的群聊]
（身份：用户本人 = QQ …）
[#9001]群友「本群老王」: 本群刚才在聊吃饭                            ← 本群的
```

三个问题叠在一起：

1. **没有起始标记**：卡片标题紧贴在 `@3566906627` 后面，连换行都没有
2. **没有来源**：那 95 条全部来自 `group_id 284840486`，但正文里**一个字都没提**
3. **没有结束标记**：卡片正文直接撞上 `[这段时间的群聊]`

而卡片正文的格式 `时间 昵称: 内容` 和本群上下文**完全一样**，所以模型唯一能依据的线索只有括号里那句「[转发消息]」，很容易被忽略。

### 修法：三件套，一个都不能少

```
[转发消息 · 共 95 条 · 已展开前 6 条 · 来源群 284840486 · 时间 10-26 13:18 ~ 10-26 13:56]
（下面是别人转发进来的聊天记录，不是本群发生的对话；里面的人不是本群成员。）
10-26 13:18 崩兔子: …
（还有 89 条未展开）[转发消息结束]

[这段时间的群聊]
[#9001]群友「本群老王」: 本群刚才在聊吃饭
```

- **来源群号**：从展开结果的每条 `group_id` 里取（实测每条都带）。多个来源就列前三个 + 总数
- **时间范围**：卡片内最早 ~ 最晚，让「10-26 的事」和「今天的事」分开
- **起止标记**：`[转发消息结束]`（顶层）/ `[↑ 转发内容结束]`（嵌套）。**「不是本群」那句话只在最外层说一次**，嵌套层重复纯属噪音
- **正文另起段**：`poll.js` 里带卡片时在 `head` 后加空行 —— 否则边界再清楚也会被视觉上糊在一起

### 顺带修的三处

1. **`@3566906627` 孤立**：卡片另起段后，`textOf` 渲染出的 at 段会孤零零挂在段落开头，看着像「她 @ 了谁」。带卡片时把正文开头的 `@数字` 去掉 —— 「这条 @ 了她」已经写在 `head` 里。
2. **窗口批次**（`deliverWindowBatch`）和**群上下文**（`contextSlice`）是同样的列表格式，卡片夹在中间更危险 —— 都改成「谁: + 空行 + 卡片」。
3. **嵌套卡片**原来接在 `甲: ` 后面变成半行半块，加了个前置换行。

### 教训

**「展开成功」不等于「模型读懂了」。** 上一版只顾着把内容取回来，没想过它在正文里长什么样 ——
而模型看到的是一整块纯文本，**没有任何结构信息告诉它这段是谁说的话**。
以后凡是把外部内容塞进正文的功能，都要先打印一遍「模型实际看到的正文」再判断对不对，
而不是只看「取到了 N 条」。

`forward-sim` 74 项（新增第 17、18 组专测边界），`forward-mutation` **17/17**。

## 卡片里的图片读不到（0.16.9，2026-11-02）

用户在本机测：「边界清晰了，但图片一个也读不到」，私信转发聊天记录，卡片内图片全是 `[图片]`。

### 真因：图片链路只接了三分之一的路

`buildForwardImageBlocks()` 只被**群聊主消息**那条路调用。而「把卡片交给模型」的路径有四条：

| 路径 | 卡片文字 | 卡片图片 |
|---|---|---|
| 私信 | ✅ | ❌ **漏了** |
| 群聊主消息 + 上下文 | ✅ | ✅ |
| 群聊窗口批次 | ✅ | ❌ **漏了** |
| `qq_msg_history` 翻历史 | ✅ | ❌ 仍未接（见下） |

用户测的正是私信 —— 所以他看到一片 `[图片]`。

**为什么单测没抓到**：`forward-sim` 只测了 `collectForwardImages()`（能不能把图从展开结果里捞出来），
没测「**各条投递路径有没有用它**」。捞得出来和交得出去是两件事。

### 修法

私信和窗口批次各补两行（复用已经预取好的 `forwards` / `batchForwards`，零额外网络请求）：

```js
const forwardImages = await buildForwardImageBlocks(ctx, messages, forwards)
deliver(..., [...imageBlocks, ...forwardImages], ...)
```

### 审核抓出的另外三个问题

1. **预算闸放错粒度（最严重）**。`forwardBudgetMs` 的 deadline 只在「两条消息之间」判一次，
   而一张卡片的几十张图是在**同一次** `buildImageBlocks` 调用里串行下载的

   修法：改成**一张一次** `buildImageBlocks`，死线判断放在每张之前。
   实测验证：12 张图 + 预算 1 秒 → 只下 3 张、总耗时 1216ms 就被切断。
2. **`forwardImageLimit` 没夹上限**。`forward.js` 的 `cfgOf()` 里夹了 30，

3. **卡片图污染「最近收到的图片」索引**。`saveImageCopy` 无条件 `rememberImage()`，

   修法：`buildImageBlocks(ctx, messages, { remember })` 透传，卡片这条路传 `remember: false`

## 从上游 0.15.2 搬回来的三个修复（0.16.18，2026-11-03）

上游 `danshuyue/dsh-onebot-channel` 的 PR 合不进来：它停在 **0.15.2**，
`lib/` 只有 39 个文件、**没有 `window.js`**（对话窗口是 0.16.x 才有的），
`poll.js` 是 909 行且不 import `window.js`，我们的是 1299 行、整个窗口功能建在它上面。
20 个共有文件全不一样 —— 两条历史没有可用的 merge base。

所以按「挑取修复、不合并历史」处理，把上游 0.15.2 那 6 处改动逐条搬进我们的代码。

### ① `inject` 少声明 `agentPresets`（最严重，我们一模一样）

`sessions.js` 的 `composeSetup` 用 `serviceOf(ctx, 'agentPresets')` 把会话记录的 preset
重新挂到冷启动的 agent 上。但 `index.js` 的 `inject` 里**没有它** →
取不到 → 那个函数**静默**返回空 setup → 冷启动出来的 agent 没有 preset，
工具只剩「全局插件」那一层（`qq_*` 都在，`read`/`write`/`glob`/`grep`/`pwsh` 全没了）。

**症状特别像「插件坏了」，日志里却一个字都没有。** 现在是补上 `agentPresets` +
每一种降级各留一行日志。

### ② 空闲起算点用错了字段（真实的「额度几分钟烧光」）

`shouldNudge` 原来算 `eligibleAt = lastIncomingAt + idleMs`。问题：**她自己主动说完一句之后，
`lastIncomingAt` 一动不动**，于是下一次 tick（60 秒后）依然算「已经空闲 8 小时」，照样放行 ——
表现就是静默一解除、一分钟一条，把当日额度几分钟烧光。

上游的注释说得很准：「空闲应该理解为『这段关系安静了多久』，她自己开口也算打破安静。」
修法：`idleFrom = Math.max(lastIncoming, lastProactive)`。

⚠️ 之前这条是靠 `unanswered` 退避兜的，但 `backoffMax` 配成 1 就等于把退避关了，兜不住 ——
所以基准必须自己对。

### ③ 主动搭话没有「当前时间」

`composeNudge` 只说「距上次说话已经 8 小时」，不说现在几点。模型不知道是深夜还是上午，
就会写出「今天过得怎么样」这种不分场合的问候（**凌晨三点问这个很怪**）。
加了 `formatClock()`：`2026-11-02 22:01（周一）` —— 星期几一起给，
因为「周末」和「工作日」该说的话不一样。

### 顺带搬的

`proactiveIdleMaxHours` + `rollBetween()`：空闲门槛可以是一个区间，按这段安静期的起点
摇号（FNV + murmur3 收尾混合，**同一 seed 稳定**）。为什么要稳定：钟每 60 秒看一次，
每次重摇的话门槛会在区间里来回跳，看起来像「随机根本没生效」。

### 测试

`proactive-sim` 47 → **60 条**。变异验证：把 `idleFrom` 改回只看 `lastIncoming`
→ 2 条变红（证明这条断言不是空的）。

### 教训

**上游不是「另一个版本」，可能是另一条开发线。** 这次能搬是因为那 6 处改动
正好落在我们没动过的地方（`inject`、`sessions.js` 的降级分支、`proactive.js` 的判定）。
判断能不能搬，看的是「这段代码在我们这儿长什么样」，不是「版本号谁大」。

## 第一号审核员抓到的 8 条（0.16.16 收尾，2026-11-03）

@-flush 那条线的审核员回来得最晚，报的却最狠：**8 条真问题，79 条断言全绿时它们全都在**。
共同点是既有断言只测「主路径走没走」，没测并发 / 退避 / skipped / 基准回拨 / 落盘。

| # | 问题 | 后果 |
|---|---|---|
| 5 | handler 返回 `{status:'skipped'}`（没投）被当成成功剔除 | 队列与 @ 上下文**两边都剔 = 消息彻底消失** |
| 1 | `flushing` 正在投时直接返回 `skipped`，@ 不等就走 | 满 3 条正在投是常态 → **「旧话后到」原样复现**，0.16.13 白修 |
| 6 | `flushPendingNow` 完全不看 `pendingRetry` | 每来一条 @ 就把失败批次重打一次，退避全废（实测 5 次 @ → 重打 5 次） |
| 3 | `stop()` 不清 `batchHandler` | 卸载/热重载后**旧闭包**仍被 @ 触发的那条路调用（握着已 dispose 的 ctx） |
| 8a | `lastDeliveredSeq` 无条件赋值，会回拨 | 82 → 81 之后，已投过的旧 @ 又作为上下文出现一遍 |
| 8b | `closeWindow` 只清内存 `clearPending`，不删盘上 `win.pending` | 关窗 → 重开 → 重启，**上个窗口丢弃的旧话复活**（基线 53ef75e 起就有） |
| 4 | `idOf` 把 `message_seq: null` 变成 `seq:0`；WS/HTTP 两种形状身份不一致 | 两条无 id 消息撞号 → 第二条被当重复**静默丢弃**；跨通路剔除失败 → 投两遍 |
| 8c | 循环投掉的批次不进 `flushedIds` | 常态路径下，@ 正文里仍重复已投批次 |
| 7 | `removeDelivered` 无条件 `pendingSince = now` | 剩余老消息的「攒了多久」被抹成 0，给模型的提示是错的 |

### 修法要点

- **#5**：只有 `delivered` 才 `removeDelivered`；`skipped` 与 `failed` 一样保留队列。
- **#1**：`flushing` 时**挂 Promise 等它投完再重试**（`flushWaiters`），不是返回 skipped。
  每秒轮询既延迟又费，直接挂 Promise、flush 结束唤醒。
- **#6**：加 `pendingRetry` 检查，但**不能复用 `shouldFlush`** —— 它还有条数/时长条件，
  会把「@ 是话题边界」这个语义一起挡掉。
- **#3**：`stop()` 里 `if (batchHandler === explicitHandler) batchHandler = null`
  （只在还指着自己时清，避免误清后来者）。
- **#8a**：`Math.max(maxSeq, previous)`，基准只前进。
- **#8b**：`closeWindow` 里连 `delete win.pending / win.pendingSince` 一起做。
- **#4**：`idOf` 自己判 `^-?\d+$` 且非 0/-0、`seq > 0`（与 `openingIdOf` 对齐）；
  新增 `messageIdentities()` 返回**全部**身份，剔除时 id 与 seq 各比一次。
- **#8c**：`flushDue` 投成功后 `rememberDelivered()`，@ 到达时 `takeRecentlyDelivered()` 并入剔除集。
- **#7**：入队时给每条打不可枚举的 `__queuedAt`，`removeDelivered` 用「剩余里最早那条」的时刻。

### 测试

`window-batch-sim` 84 → **107 条**。变异验证：skipped 当成功（3 红）、退避被绕过（2 红）、
stop 不清 handler（3 红）、不删盘上 pending（2 红）—— 全部捕获。

### 教训

**「主路径测试全绿」和「这条路是对的」是两件事。** 这 8 条里有 5 条在
**常态**下就会发生（满 3 条正在投、退避期内又来 @、循环正常投掉一批），
不是边角场景。凡是加了「等待/串行/剔除」的代码，都要专门测**并发**与**失败后重试**。

## 判断「不用回」时没有出口，只能写一句话（0.16.16，2026-11-03）

用户在 0.16.15 之后追问：「LLM 完全可以自己判断该结束了。看日志会发现它把**思考内容**发了出去，
导致聊天被继续。理论上判断无需回复的内容就不该触发回复。是提示词没写好吗？」

### 先排除的东西

`blocksToText`（`outbound.js:456`）只取 `type === 'text'` 的块，**不碰 reasoning**。
所以发出去的不是隐藏的思考，是它**真写在正文里的字**。这不是"思考泄漏"，是"正文里写了元判断"。

### 真正的原因：没有「这条不该回」的出口

查日志：`qq-bridge-load.log` 里**从来没有一次真实的 `qq_close` 调用**（只有 `qq_close registered`）。
也就是说 0.16.15 那三层修复（判定 / 状态码 / 出站拦截）**全程挂在「她会调 qq_close」这个前提上，
而这个前提根本不成立**。她走的是另一条路：

```
判断「该结束了」→ 没有「不回复」这个一等公民 → 只能写一句正文 → 自动转发把它发出去
```

为什么她不会选 `qq_pass`？因为它的说明写着「正文里写了真话照样发」——
这个规则本身是对的（保护「她真说了话但用户没收到」），但它让「我想闭嘴」变得需要小心翼翼。
于是最省事的路就是写一句解释。

### 更糟的一点：提示词原来在**骗**她

`qq_send` 的说明里原本写着：

> 反过来：**只有调了这个工具，消息才会出去**。你自言自语的正文永远停在会话里。

**这是假的。** `flushOutbound` 会把这一回合最后一条 `assistant/message` 的正文自动转发出去。
模型照这句话推理，就会认为「我写点分析没关系，反正不会发出去」——然后它就发出去了。
**一句不实的说明，等于给了她一个错误的心智模型。**

### 修法

1. **`qq_skip`**：判断「这条不该有回复」时用，**本回合正文一律不发**（不看内容、一律拦）。
   和 `qq_pass` 的分工：
   | 工具 | 语义 | 正文 |
   |---|---|---|
   | `qq_skip` | 这条不该有回复 | 不发 |
   | `qq_pass` | 我看了，这次先不开口 | 有真话就发 |
   标志一次性消费，不会吞掉下一回合；已经用 `qq_send` 发出去的话不受影响。
2. **提示词改实话 + 给行动**：删掉那句「正文停在会话里」，改成
   「你的正文会成为发到 QQ 上的内容」「判断不用回时直接调 `qq_skip`，**不要在正文里解释**」
   「想结束，就别产出文字」。

### 测试

`close-refuse-sim` 69 → **79 条**。变异验证：关掉出站那道 skip 闸 → 2 条红。

```
判断「该结束了」→ 没有「不回复」这个一等公民 → 只能写一句正文 → 自动转发把它发出去
```

为什么她不会选 `qq_pass`？因为它的说明写着「正文里写了真话照样发」——
这个规则本身是对的（保护「她真说了话但用户没收到」），但它让「我想闭嘴」变得需要小心翼翼。
于是最省事的路就是写一句解释。

### 更糟的一点：提示词原来在**骗**她

`qq_send` 的说明里原本写着：

> 反过来：**只有调了这个工具，消息才会出去**。你自言自语的正文永远停在会话里。

**这是假的。** `flushOutbound` 会把这一回合最后一条 `assistant/message` 的正文自动转发出去。
模型照这句话推理，就会认为「我写点分析没关系，反正不会发出去」——然后它就发出去了。
**一句不实的说明，等于给了她一个错误的心智模型。**

### 修法

1. **`qq_skip`**：判断「这条不该有回复」时用，**本回合正文一律不发**（不看内容、一律拦）。
   和 `qq_pass` 的分工：
   | 工具 | 语义 | 正文 |
   |---|---|---|
   | `qq_skip` | 这条不该有回复 | 不发 |
   | `qq_pass` | 我看了，这次先不开口 | 有真话就发 |
   标志一次性消费，不会吞掉下一回合；已经用 `qq_send` 发出去的话不受影响。
2. **提示词改实话 + 给行动**：删掉那句「正文停在会话里」，改成
   「你的正文会成为发到 QQ 上的内容」「判断不用回时直接调 `qq_skip`，**不要在正文里解释**」
   「想结束，就别产出文字」。

## 结束不了话题，还把判断念出来（0.16.15，2026-11-03）

用户实测：对方想结束话题（没 @ 她，走对话窗口）时，她**有概率结束不了**，
还会把「我该不该结束」这个判断本身当成话发出去。
对端也是 AI 时，两边顺着这段元讨论互相回，谁都不肯先停。

### 三层成因，缺一层都修不好

**第一层（判定）：`吧` 结尾被判成疑问。**
`QUESTION_RE` 里有 `(?:吗|呢|吧)$`，于是「好吧」「行吧」「就这样吧」「随你吧」
全被判成 `question` → `openQuestion` 恒真 → `level` 被硬压成 `continue` → 永远收不了。

⚠️ **只删掉 `吧$` 不够，反而更糟**（实测）：删掉后「好吧」「行吧」落进 `ack`，
但「就这样吧」「随你吧」会落进 **`substantive`** —— 而 substantive 的
`topicClosure` 是 0.4、`theirIntent` 是 0.8，分数只有 0.556（`linger`），
比 `ack` 的 0.8 差一大截。**光删规则，这两个最典型的收尾句反而更难收。**
所以正确做法是把「吧」的**让步语义**识别出来（`YIELD_PATTERNS` + 长度闸），
排在疑问判定之前，而不是把它从疑问里删掉。

**第二层（工具）：拒绝时返回的是一句话。**
原来 `verdict` 写的是自然语言「对方还在问/还在求，这会儿不能收摊 —— 先把话说完再说」。
模型拿到之后很自然地把它当成「我该说的内容」写进正文。
现在改成**状态码**（`open-question` / `closed` / `forced-closed`…），
自然语言放到 `output.render` 里，用 `[系统]` 前缀 + 明确写「这不是你要说的话，别写进正文」。

**第三层（出站）：被拒回合的正文照常转发。**
前两层都只是"降低概率"。真正兜底的一道闸在 `outbound.js`：
这一回合 `qq_close` 返回过 `ok:false`，正文就一律不转发（只记日志）。
⚠️ 只拦这一种组合 —— 别扩大成「调过 qq_close 就拦」，
成功收尾的回合她要留的最后一句话照发（`qq_pass` 的既有语义也一个字没动）。

### 另外两个「给她出口」的改动

- **同回合已处理 → 放行关窗**：她这回合说过话（`qq_send`）或划走过（`qq_pass`），
  再调 `qq_close` 就被放行 —— 只是不记收尾（没闭环，不该说「上次聊到哪儿」）。
  `openQuestion` 本意是替她把门，但不该替她把自己锁在屋里。
- **连续被拒 3 次强制收摊**（`close-refused-x3`）：宁可这次收得不体面，也不无限转。

### 测试

`rhythm-sim` 50 → **86 条**（判定层），新增 `close-refuse-sim` **69 条**（工具/出站层）。
变异验证 4 个：禁掉让步句识别（4 条红）、verdict 换回自然语言（1 条红）、
去掉强制收摊（5 条红）、**删掉出站那道闸**。

⚠️ 最后一个变异**第一轮存活了** —— 因为第一版测试只覆盖了工具层，没测出站。
补了三个场景（被拒→不转发 / 没被拒→照发 / 成功收尾→最后一句话照发）才抓住。
**这跟 0.16.9「卡片图片只接了一条路」是同一类错误：能力做了，但没验证每条路径。**

### 教训

**「拒绝」这件事的返回文案，本身就是产品设计。**
拒绝时返回一句自然语言，等于给模型递了一句台词；它念出来不奇怪，不念才奇怪。
凡是工具用「返回一段话」来表达失败，都要问一句：这段文字会不会被当成内容消费？
状态码 + `[系统]` 前缀的 render，是这个问题的最低成本解法。

## 她从来不发收藏表情（0.16.14，2026-11-03）

用户观察：「依旧没有发收藏表情包的倾向，大概是提示词模板的问题。」

### 诊断：不是模板写得不够多，是那条路走不通

原先的假设是提示词把收藏表情写成"次选"、又埋在中段。照着改模板**只会更糟** ——
因为模型越积极用 `custom_emoji`，撞 `throw` 的次数就越多。

拿真实收藏夹查了一次（`fetch_custom_face_detail`，22 个）：

```
协议端根本不返回 summary 字段，summary 全靠 desc 兜底；
22 个里 21 个的 desc 是**句子**而不是标签：
  穷光蛋思考中 / 问号呆脸 / 拿棒球棍打死，对付油腻男用 / 这是你的私人癖好
只有 1 个是规范格式：「荧·脸红满足 | 得意 满足 害羞」
```

模拟模型按情绪去搜：

| 搜的词 | 结果 |
|---|---|
| 疑惑 / 卖萌 | 命中 |
| 委屈 / 撒娇 / 无语 / 好笑 / 懵逼 | **全落空** |

而落空时旧代码 `throw` —— **整次 `qq_send` 失败，话也发不出去**。
模型学到的不是"换个词"，是"别碰 custom_emoji"。这就是负向强化的来路。

### 三处改动

1. **降级**：`custom_emoji` 匹配不上时跳过表情、**文字照发**（返回值 `custom_emoji_missed`
   + 日志 + `[系统]` 前缀的 render，三处可观测）。只有"仅表情、无文字、表情也没匹配上"
   才抛错 —— 那种情况确实没东西可发，静默成功会让她以为发出去了。
2. **`qq_face_pick`**：按情绪列候选，**永不抛错**（查询不是命令），把"想一想"变成"查一下"。
   `rankCustomFaces` 必须滤掉 `score === 0` 的项，否则模型会收到一堆毫不相关的候选。
3. **`qq_face_rename`**（这一条是用户提的，比我原方案更根本）：
   让模型**看图自己起名**，把「穷光蛋思考中」改成「思考 | 疑惑 穷 无语」。
   自动切词或套模板都不准 —— 图长什么样，只有看得见的人知道。
   分两步：不带 `desc` 时只把图送到眼前，带 `desc` 时校验格式再写入。

### 为什么"改名"是正解而不是"改搜索"

搜索算法本身没问题（`findCustomFace` 的打分一直是对的），**是没人调它**；
而调了也搜不到，因为**标签本身没有可搜的语义**。
把标签修好之后，同一条打分路径立刻就能命中 —— 测试里专门钉了这条闭环：
改名后按「无语」能搜到，且 `findCustomFace` 也找得到（`qq_send` 那条路才通）。

### 顺带修正的一处旧断言

`collect-sim` 原来钉的是「先用 custom_emoji 从收藏夹找语义合适的表情包」——
那正是被判为"被动式、不触发"的旧文案。断言改成钉**意图**（有明确动作、有防滥用、
有容错说明），而不是钉字面。这类"钉字面值"的测试会在文案迭代时逼人改回旧写法。

### 教训

**先量一下那条路通不通，再改文案。** 这次的顺序反了：文档先断言"是提示词的问题"，
而实际上提示词只是第三个原因，前两个（标签无法搜、搜不到就整句失败）才是决定性的。
一个能力"实现了"但"用不起来"，中间通常隔着一条**失败即劝退**的路径。
凡是有 `throw` 的用户可选能力，都要问一句：这次失败会让模型以后不敢用它吗？

## @ 之后的旧话题被翻出来（0.16.13，2026-11-02）

用户实测：@ 之后的连续对话里，如果对方**持续 @ 或间歇 @**，一些不带 @ 的句子会堆在队列里，
等当前这轮结束才成批投递 —— 模型于是一边回新话题，一边收到几轮之前的旧话，接着旧话题往下聊。

### 真因：两条投递路径的节奏差，没有任何顺序协调

| 路径 | 什么时候到模型 |
|---|---|
| 带 @ | 立刻（`agent.followup`，`deliver.js:136`） |
| 不带 @（窗口内） | 攒够 3 条或等满 8 秒才成批投递 |

`deliver` 本身**没有串行化**，所以 `@` 会不断插到攒批队列前面，队列里的旧话还在按自己的 8 秒计时器等。

### 修法：@ 是话题边界，先把它之前攒的投完

`handleGroupMessage` 里 `atMe && win !== null` 时先 `flushPendingNow`，再投这条 @。
投递一律收口到 `window.js` 的 `flushPendingNow`（`flushing` 保护 + 门控判断 + 剔除 三件事都在这一处），
**不要**让调用方直接调 `deliverWindowBatch` —— 那样两条路会各投一遍同一批消息。

### 探索时踩到的四个坑（都是「看着对，其实没修」）

1. **`startWindowLoop` 不把 handler 记进 `batchHandler`**（最隐蔽）。
   `index.js` 是 `startWindowLoop(ctx, deliverWindowBatch)` 显式传参，而 `batchHandler`
   只在 `setWindowBatchHandler` 里赋值 —— 于是 `flushPendingNow` 拿不到处理器，静默跳过。
   **测试也会「通过」**：循环照常 8 秒后 flush，断言只要不断言顺序就全绿。现在 `startWindowLoop` 会记。
2. **只 flush 不剔除，同一批话投两遍**。
   `handleGroupMessage` 会把缓冲里的群消息当「未读上下文」塞进 `@` 的正文
   （`[这段时间的群聊]`）。pending 里的消息正是其中一部分 —— 先整批投一遍，
   再作为 `@` 的上下文投第二遍，等于把「旧话重复」从时序问题变成了内容问题。
   修法：flush 成功后按**消息身份**（`idOf`：有 message_id 用 id，否则用 seq）
   把这批从「未读上下文」里剔掉。
   ⚠️ 第一版我写的是「把上下文基准抬到那批的 `maxSeq`」，**这是错的**：
   基准是 seq **区间**过滤，会把夹在队列消息之间、但没进队列的消息
   （没 @ 也没引用她的群友发言）一起删掉 —— 那本来是有效上下文，删了就是丢消息。
   按身份剔除只删真的投过的那几条。测试里专门有一条「夹杂场景」钉住这个区别。
   ⚠️ **轮询路径的基准是这一批消息开始前的旧快照**（`pollGroup` 的 `baseDeliveredSeq`），
   比 pending 里那些消息的 seq 更老 —— 所以身份剔除必须自己做，
   不能指望 `lastDeliveredSeq` 已经前进。
3. **门控要不要跳过**。文档原写「有门控就不 flush」，但那是错的：
   门控挡的是「续聊抢在开窗 @ 前面」，而**@ 自己就是那个「前」**。照文档走的话
   一次 @ 只会带出一条 @，积压继续等 —— 缺陷根本没修。现在 `flushPendingNow` 照常判断门控
   （`held` 时不动），调用方不特殊处理。
4. **失败不能阻塞 @**。积压投不出去时那条 @ 仍要投递成功，pending 留着等重试。

### 测试

`window-batch-sim` 从 44 条涨到 **79 条**。顺序类断言必须断言 `followup` 的**调用次数和先后**，
只断言「批次投出去了」是空的。变异验证 8 个变异（去掉 flush / 不剔除已投那批 / 忽略门控 /
不记 handler / 不剔除队列 / 不标头部 / 失败阻塞 @ / 按区间误删上下文）全部被捕获。

### 教训

**「加了一行调用」不等于「这条路径真的走了」。** handler 没被记住、门控方向搞反、
上下文重复投递 —— 这三个都不会让任何一条既有测试变红。
凡是「A 路径要插到 B 路径前面」的改动，断言必须同时钉住**次数**和**顺序**，
并且要有**旧基准**场景的用例（真实轮询的形状和测试里手搓的形状经常不一样）。

## 「卡排队，排队的消息都是旧的」（0.16.19，2026-11-03）

用户实测：「会卡排队。排队的消息都是旧的，因为本次会话其实正常的推进且持续回复。」
「表现为 `qq_wait` 和 `qq_msg_history` 交替工作……而 @ 触发进入了队列中进行排队。」

### 先排除的东西

- 不是 outbound 队列堵了：日志里 `[out]` 没有超时丢条目，`已转发回复` 正常。
- 不是窗口门控没释放：`batchHolds` / `openingReservations` 都在正常结算。
- 不是游标卡住：`lastDeliveredSeq` 在推进，`skip (no at/window)` 正常刷。

### 真正的原因：`followup` 只能排 `next-turn`

宿主（`dsh-agent-loop`）里两个入口进的是**两个不同的队列**：

```js
followup(input) { this.send(input, 'next-turn', true) }   // 回合边界认领，一次只认领 1 条
steer(input)    { this.send(input, 'next-step', true) }   // 步骤边界认领，整队全取
```

```js
claim(target, turn) {
  const claimed = this.mutate('next-step', 0, this.nextStep.length, [], false)   // 全取
  if (target === 'next-turn') claimed.push(...this.mutate('next-turn', 0, 1, [], false))  // 只取 1
}
```

而插件**只有一条投递路径**：`agent.followup()`（`deliver.js`）。于是：

```
她一个回合：qq_wait 40s → qq_msg_history → qq_send → qq_wait 40s …
这期间进来的每条消息 → followup → next-turn 排队
回合结束 → 一条开一个新回合 → N 条消息要 N 个回合才清空
```

用户看到的「N 条排队消息」就是这套 inbox 的投影（宿主 UI 里 `queue.steer`
的文案「Steering is available only while the agent is running」也印证了这个设计意图）。

**更糟的是重复**：她早在当前回合里用 `qq_msg_history` 看过这几条了（用户原话
「新的@和非@语句在history中包含了」），回合结束后又被单独唤醒对着同一段话再回一遍。

### 修法

`deliver()` 里按状态分流（`pushIntoAgent`）：**忙 → `steer`，闲 → `followup`**。
闲时行为与改动前逐字一致；宿主没有 `status` / `steer` 时退回 `followup`，不丢消息。

配套加 `waitTurnMaxMs`：回合长度是排队问题的**上游**，只夹「单次等待」不够 ——
她可以连打四次 40000ms。额度按 target key 记，**每次投递新消息就重置**（有新东西
要处理就该给新预算），用完了 `qq_wait` 立刻返回并提示「现在开口，或者收掉这一轮」。

### 坑

1. **`steer` 进的是 next-step，空闲时没有「当前回合」** —— 消息会一直躺在 next-step 里
   没人唤醒（宿主只在回合内认领它）。所以**必须**先判 `status === 'running'`，
   不能无条件 steer。
2. **`agent.status` 是 `'idle' | 'running'` 两个值**，别写成 `'busy'` / `'active'`。
3. **不要为了「更实时」去 `cancel` 重投**：那会丢掉她正在写的那一段，
   而且 `cancel` 默认 `keepInbox: false`，连排队的一起清掉。

### 测试

新建 `tests/deliver-mode-sim.mjs`（30 条，已进 `npm test` 串）。四组变异全部被抓：
永远 followup（3 条红）、去掉 `steer` 存在性判断（1 条红）、额度永不递减（3 条红）、
`qq_wait` 忽略额度（3 条红 —— 其中一条实测等满 40015ms，正好证明它真的在测接线）。

⚠️ **`qq_wait` 的 execute 路径此前一条测试都没有**。只在 `rhythm.js` 里单测
`waitBudgetLeft` 是假绿：那证明不了额度真的接进了工具。新测试走 `registerWaitTool`
拿到的**真工具对象**，并断言「额度只剩 1 秒时请求等 40 秒，实际只等了 1 秒」。

## 直接跑 progress-sim 删掉了真实 `~/.dsh`（2026-11-06）

**现象**：DSH NEXT 2.0.22 启动失败，报
`Renderer recovery exhausted: web boot: 1 entry did not activate @deepseek-ai/dsh-experimental-client-ui-cot-translation: loading`；
安全模式能进。

**根因**：`tests/progress-sim.mjs` 被直接执行（没有走 `run-isolated.mjs` 的隔离 HOME）。
它的 `reset()` 删除了真实 `~/.dsh/sessions` 与 `storages/session_projcache`，并把
`storages/workspace.json` 覆盖成 **version 1** 空表。新版 `dsh-workspace` 只接受 v2，
`workspaceRegistry` 起不来 → `sessionController` 一直 pending → `cot-translation` 永远
`loading` → 渲染恢复 3 次后放弃启动。

**代价**：481 个会话 / 约 680 MB 被删；只能从 10/25 的备份恢复，之后 11 天的会话丢失。

**修法**：新增 `tests/sandbox-guard.mjs` 白名单守卫（`DSH_TEST_HOME` + 隔离标记 +
`os.userInfo().homedir` 对比）；`progress-sim.mjs` 顶部强制检查；`run-isolated.mjs`
写标记并传 `DSH_TEST_HOME`；新增安全入口 `npm run test:progress`。

**别做**：不要直接 `node tests/progress-sim.mjs`；不要只改 `HOME`
（Windows 上 `os.homedir()` 看 `USERPROFILE`，只改 `HOME` 不生效）。

详见 `docs/事故复盘-2026-11-06-测试误删真实DSH目录.md`。
