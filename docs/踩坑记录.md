# 踩坑记录

> 每一条都是真踩过的，不是理论风险。改这个插件之前先扫一遍，能省掉大半天。

## 运行时（会静默失效的那种）

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里 @ 了也不回 | 设置页只写 `routes.group`，**从不写 `groupUins`**。监听列表空 → 群轮询压根没启动 | 绑定即监听：监听集合 = `groupUins ∪ routes.group`，每轮实时读 |
| 设置页改了轮询间隔没用 | `setInterval` 在 apply 时把间隔写死，改配置只动了文件 | 自调度：`poll().then(schedule)`，每轮重读 `config.pollMs` |
| 协议端一卡，桥接永久哑 | `callOneBot` **没有超时**，一次挂死就永久卡在 `await` | `AbortSignal.timeout(config.requestTimeoutMs ?? 8000)` |
| 协议端卡一次就雪崩 | `setInterval` 不等上一轮结束，请求一层层堆上去（实测同一毫秒 8 条 `fetch failed`） | 防重入 + 自调度（上一轮没完不排下一轮） |
| 热重载后接口 404 | `webServer.register()` 返回的 disposer 没接住，旧路由还在 → `duplicate prefix route` | `ctx.effect(() => dispose)` |
| 群里多收到一段「本不该发出去」的正文 | 模型调了 `qq_send` 发正文，自动转发**又把助手这一轮的整段正文发了一遍**（实测群里多出 2 条） | 同回合互斥：用过 `qq_send`（且没报错）就跳过自动转发，只有调用失败才兜底 |
| 插件装着但完全没反应 | 静态 `import '@deepseek-ai/dsh-tools'` 解析不到（官方包在 `app.asar` 里） | 一律走 `inject` 服务，不 import 官方包 |

## 会话与消息（会写坏数据的那种）

| 现象 | 真因 | 修法 |
|---|---|---|
| 历史加载失败：`lacks an identified message` | 手搓的消息对象漏了 `id`；而 `session.append` **只校验数据形状、不校验消息身份**，坏事件能安静落盘，直到下次读日志才炸 | `ensureId()` 强制兜底 + `outbound-sim` 断言「投递消息必须带 id」 |
| 设置页 0 个可选会话 | `inject` 少了 `sessions`，`ctx.get` 抛 `without inject` 被外层 catch 吞成 `[]`；而且 `sessions.list()` **只返回活着的会话** | `inject` 加 `sessions`；列表 = live ∪ 扫 `~/.dsh/sessions/<编码 cwd>/` |
| 会话标题显示成 `#xxxx` | 标题不是 header 字段，是日志里的 `session/title` 事件 | 逐帧解 zstd 取最后一条 `data.title`，退回首条用户消息 |
| 新建的会话在侧栏找不到 | `agents.create` 建的会话**从不登记进 `workspace.json` 的 `sessionIds`**，侧栏按注册表列，所以永远看不见 | 别在插件里建会话；在 DSH 里建好再回来绑 |
| 重启后第一次 @ 没反应 | `seedOnFirstRun` 把已有历史一次性标记成已读（防刷屏），启动前的消息被跳过 | 再 @ 一次；或把 `seedOnFirstRun` 关掉 |
| 群友被当成用户 | 消息里只给「昵称 + QQ 号」，**从没告诉过 agent 哪个号是用户** | `ownerUin` + 每条标「用户本人」/「群友…（不是用户本人）」 |

## 前端与工程

| 现象 | 真因 | 修法 |
|---|---|---|
| 设置页整块白屏、面板消失 | 函数组件里 `throw` **接不住**；原来的「错误边界」也是函数组件，异常冒到最外层 | 真边界：`class extends React.Component` + `getDerivedStateFromError` |
| 组件里一个异常干掉整个面板 | 直接读没 inject 的服务（`ctx.sessions`）会抛 | 读这类服务整段包 `try/catch`，取不到就降级 |
| 配置和路由表莫名被清 | 配置放在插件目录，`file:` 依赖重装会覆盖插件目录 | 数据全部搬到 `~/.dsh/qq-bridge.*` |
| 跑 `sync.mjs` 报 EPIPE | pnpm 对 `file:` 目录依赖是**硬链接**（同一 inode），整目录 cp 等于拷自己 | 先判 inode，相同就跳过；不同再逐文件覆盖 |

## 模块化 + WS 推送（2026-10-27）

这一批全是「重构 / 加功能时自己造出来又当场抓回去」的坑，
**顺序很重要**：前三条如果没被模拟脚本挡住，会一路留到线上才炸。

| 现象 | 真因 | 修法 |
|---|---|---|
| 群里只有第一条 @ 被处理，后面全被跳过 | 「不是 @ 我」和「投递失败」都返回 `''`，轮询把「跳过」当「失败」→ 回滚游标 + `break` → 后面真 @ 的消息永远轮不到 | 三态返回 `{ status: 'skipped' \| 'delivered' \| 'failed' }`，只有 `failed` 才回滚游标 |
| 群消息上下文里少了上一条 | 上下文基准跟着「已投递的 seq」往前推，基准每条都在动 | 基准**钉死在本批开始值**（`baseDeliveredSeq`），一批之内不变 |
| 新模块文件改了但 DSH 里没生效 | pnpm 硬链接只对**已存在的文件**生效，新建文件在 profile 副本里根本不存在 | `sync.mjs` 改成**逐文件比对**（不存在→补拷 / inode 不同→覆盖），新增文件后必须跑一次 |
| WS 连上了但一条都不来 | HTTP 用的 `access_token` 和 **WS 用的 token 是两套独立的**，拿 HTTP 的那个去连 WS，握手直接不是 101 | 用 `networks.wsServers[0].accessToken`；找不到就跑 `/api/qq-bridge/detect-ws` 自动发现 |
| 找不到协议端的 WS 配置在哪 | 在源码目录里翻是白翻 | 实际路径：`<安装目录>/config/onebot_<uin>.json` → `networks.wsServers[0]`（url + accessToken） |
| 同一群消息被处理两次 | WS 路径和投递函数各记一次 `seenIds`，同一 id 存了两遍 → 去重窗口被悄悄缩短 | `markSeen` 内部去重；`loadState` 启动时自洁（去重 + 只留最近 100 条） |
| 回复内容突然少一段 / 发错人 | 出站用 `Map.set` 覆盖游标，两次投递互相盖；两个 QQ 号绑同一会话时还会把内容发到错的人 | 改成**每会话 FIFO 队列**，出队先于发送，失败也出队 |
| 增量扫描后回复不再转发（静默失效） | `snapshotEvents(from, to)` 的 `to` 是**开区间**，而 `session.seq` 到底是「最后一个已分配」还是「下一个待分配」差一个事件 —— 漏掉的正好是 `turn/end` | 上界取 `session.seq + 1`，两种语义都安全 |
| WS 一断就彻底哑了 | 只有 WS 没有兜底 | 双通道：WS 推送 + 轮询降级成 30 秒一次补漏；**WS 启动放在轮询之后**（反过来的话，WS 断的那 2 秒窗口没人接） |
| 前端 `onField is not defined` | 组件函数定义在 `renderAdvanced` 内部，`renderWs` 是平级函数引用不到 | 提到组件层作用域 |
| 设置页里 WS 的 token 填进去变 `NaN` | 文本框被统一的 `Number()` 转了一遍 | 文本框不再走数值转换 |

## 表情包这条链路（2026-10-27）

| 现象 | 真因 | 修法 |
|---|---|---|
| 发 `[表情:晕]` 整条消息消失（`OIDB error 11000: id 17 sysemojis cfg not found`） | 内置表情表是**社区通用编号**，不是 QQ 官方编号。表里 109 个 id 官方目录查无此、另有 11 个**名字对得上但 id 错位**（晕 内置 17 → 官方 34）。协议端 `makeFaceElem` 无条件先 resolve，查不到就**整条消息失败** | 三层防护：id 有效性校验（`isKnownSysFaceId` 查官方目录）→ 解析失败**跳过表情只发文字** → 发送层兜底重发纯文字 |
| 表情包收不到 / 收藏夹是空的 | 协议端**没有**「收到图片自动收藏」的逻辑（查过 SnowLuma 源码，`addCustomFace` 只被 `add_custom_face` action 调用，没有自动触发点） | 显式调 `qq_collect_face` 写入收藏夹 |
| 收藏表情包起不了名 | QQ 发来的图片**文件名全是 MD5 哈希**（`05C1B8CD….jpg`），没有任何可读名字；而 QQ 收藏表情的备注（desc）才是以后按名字找回的唯一线索 | 新增 `qq_face_preview`：把本地副本读出来 → 附件库 → 工具结果里带 **image 块**，模型能真的看到图，才起得了名 |
| 收到的表情包看着像 `.jpg`，其实是动图 | QQ 发来的文件名**一律**是 `<MD5>.jpg`，但内容经常是 GIF（实测 43 张里 5 个 GIF、1 个 PNG）。之前原样保留扩展名，「看到的格式」和「实际格式」对不上 | 落盘时按**嗅探出的真实格式**改写扩展名（`withExt`），不看 QQ 给的后缀 |
| 工具返回了 schema 里没有的字段 → 工具调用直接失败 | `output.schema` 是 `additionalProperties:false`，多一个字段宿主就判 `ToolOutputError` | 返回值字段必须跟 schema 逐字对齐（`qq_collect_face` 的收藏分支曾返回 `recent:[]`，已修） |
| `delete_custom_face` 明明存在，agent 却说「不能删收藏夹里的表情」 | agent 只看了旧文档 | 已做成受控入口 `qq_collect_face` 的 `delete=` 参数，文档同步改正 |
| 每条 QQ 消息后面都跟一段「表情怎么用」的说明 | 提示被拼在**用户消息正文**里，同一段话在会话日志里重复 92 次；还跟树树的原话混在一起，agent 可能自己复述给他 | 删掉提示，改放 `QQ对话说明.md` 和 `qq_send` 工具描述，各说一次 |
| 同步日志显示「工具注册成功」，agent 那边却**只有 qq_send** | 插件在 DSH 里有**两个**副本：`~/.dsh/plugins/dsh-onebot-channel/`（pnpm `file:` 依赖的**源**）和 `~/.dsh/profiles/desktop/node_modules/dsh-onebot-channel/`（**DSH 运行时真正 import 的**）。`sync.mjs` 之前只同步前者，两者又不是硬链接 → 运行副本一直是旧的（实测 DSH 18:35 启动时加载的是 12:50 的副本，里面只有 `qq_send`） | `sync.mjs` 改成**两个都同步**；新增 `tests/sync-sim.mjs` 直接检查运行副本的模块完整性和工具注册，防止再漏 |
| 设置页里**找不到「QQ 桥接」**入口（但 API 和工具都正常） | `package.json` 的 `name` 跟插件的**安装目录名**不一致。DSH 按目录名去 node_modules 找包（`nearestPackage`），并校验 `package.json` 的 name **等于**目录名，对不上就**跳过整个包** → 插件不进 boot graph → 浏览器侧拿不到 client bundle → 设置页没入口。**服务端 API 和 6 个工具全正常**（cordis 是按 patch 文件里的 name 加载的），所以现象是「功能都在、就是设置页找不到」，极难定位 | 三处名字对齐（`package.json` / `cordis.patch.yml` / `lib/index.js` 导出）；`sync.mjs` 同步前校验 name == 安装目录名，不一致直接拒绝同步；`tests/sync-sim.mjs` 加断言守住 |

## 启动顺序：协议端比 DSH 晚起来（2026-10-28）

| 现象 | 真因 | 修法 |
|---|---|---|
| 重启 DSH 后日志里刷屏 `timeout` / `1006 断连`，`qq-bridge-load.log` 涨到 700 KB | **SnowLuma 的 OneBot 端口（3000/3001）是等 QQ 登录成功之后才 listen 的**。实测：DSH 09:45:39 重启 → QQ 09:47:38 才登录完 → 端口 09:47:39 才开。这两分钟里插件对着一扇还没开的门反复敲：HTTP 轮询每 4 秒一条超时 × 2 个号，WS 重连 6 次才接上 | 加探活门控（`health.js`）：启动时先用 `get_login_info` 探，探通了再起轮询和 WS；工具注册**不押在探活后面**（工具是出站能力，跟 QQ 登录无关） |
| 设置页显示「插件出错」，其实协议端只是还没开门 | 连接类错误（`ECONNREFUSED` / `fetch failed` / 超时）被写进了 `state.lastError`。那个字段是给「插件坏了」看的，写满了会误导人 | 错误分级：连接类错误不写 `lastError`、不逐条刷日志，只在状态翻转时记一条；`retcode` 不对、HTTP 5xx 这类真问题照旧上报 |
| 群消息功能「坏了」，但日志里只有私聊在报错 | `fetchGroupHistory` 把所有异常都吞掉返回 `[]` → 群侧的连接错误完全无感 | 连接类错误往上抛，交给统一的错误分级处理 |
| QQ 登录完的那一刻，WS 还要再等 20 多秒才接上 | WS 重连退避封顶 30 秒，端口开了也还在等下一个窗口 | 退避封顶改 10 秒；1006 断连去重（连不上时只记一条，不每轮刷一行） |
| 门控会不会把插件卡死 | 探活超时会返回 false | 超时（默认 150 秒，覆盖实测的 ~2 分钟登录窗口）后**照样放行**，交给轮询自己重试 —— 与其让桥接彻底不动，不如让它继续敲 |

### 诊断这一类问题的顺序

```bash
# 1. 先看协议端自己的日志 —— 它记了「什么时候 listen 的」
grep -E "listening|login detected" /d/software/SnowLuma/logs/snowluma-$(date +%F).log

# 2. 对比 DSH 的启动时间和端口 listen 时间，差值就是「门没开」的窗口
grep "\[module\] loaded" ~/.dsh/qq-bridge-load.log | tail -1

# 3. 确认现在到底通不通（要带 Bearer，token 在 qq-bridge.config.json 的 token 字段）
curl -s -X POST http://127.0.0.1:3000/get_login_info \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{}'
# → {"status":"ok","retcode":0,"data":{"user_id":...}} 就是通了
```

⚠️ `get_friend_msg_list` 这个 action **不存在**（会报 `unknown action`），
`get_friend_msg_history` 才是对的 —— 两个名字只差一个词，别写错。

## 诊断「设置页插件入口消失」的手法（可复用）

```bash
# 1. 找到 DSH 的 web 端口（Electron，端口不固定）
Get-NetTCPConnection -State Listen | Where-Object { $pids -contains $_.OwningProcess }

# 2. 拉 boot manifest —— 这条 SSE 直接吐出完整的插件清单
curl -s http://127.0.0.1:<port>/plugins/events | head -1
#    → data: {"type":"graph","graph":{"entries":[{"id":"...",...}]}}
#    一看 entries 里有没有自己的插件 id，就知道是「没进 graph」还是「进了但渲染崩了」
```

`/plugins/events` 是 DSH 的 SSE 通道，返回的 `graph.entries` 就是浏览器侧会加载的全部插件 id。

## 出问题先查这几行日志

```bash
grep "\[config\]" ~/.dsh/qq-bridge-load.log | tail -1   # owner= 有没有 → 新版加载了吗
grep "\[poll\]"   ~/.dsh/qq-bridge-load.log | tail -3   # 群在监听吗、watch 到哪些群
grep "\[group\]"  ~/.dsh/qq-bridge-load.log | tail -5   # skip (no at)? 未配置会话? seeded?
grep "error"      ~/.dsh/qq-bridge-load.log | tail -5   # fetch failed = 协议端挂了
```

**一条铁律**：日志里可能同时有 DSH 和本地测试的输出，
`[module] loaded pid=… node=…` 那行能分清是谁在说话 —— 别把测试进程的日志当成线上故障。
